# Makhtoot — Audit, 2026-08-05

Scope: the **iOS app only** (`Makhtoot/`, `MakhtootKit/`, `Makhtoot.xcodeproj`).
Android was explicitly excluded from this pass.

This audit is deliberately **incremental over `AUDIT_2026-07-28.md`**. That audit's
findings are labelled `S-#`/`P-#`/`UX-#`/`EU-#`/`FC-#`; where a finding below restates
one of those, it is marked *(prior, still open)*. Everything else is new. Findings this
pass **confirmed as fixed** are listed in §8 so they are not re-audited next time.

Method: static read of 570 Swift files / ~84k LOC, plus resolved Xcode build settings
(`xcodebuild -showBuildSettings`) and a scripted codepoint-coverage check of the joining
table. No device or simulator run was performed — findings marked *(unverified at
runtime)* where that matters.

Severity: **Severe** = ships wrong output or a security hole · **High** = user-visible
failure or submission blocker · **Medium** = degraded behaviour · **Low** = hardening.

> **Adversarial review, 2026-08-05.** Every finding in this document was adversarially
> re-verified against source the same day. Outcome: **14 confirmed** as written,
> **6 overstated** and corrected in place (C8-1, C8-2, S8-1, S8-2, P8-1, R8-1), and
> **5 withdrawn** (C8-4, C8-5, P8-3, P8-4, U8-4 — see §10). Severities, statistics, and
> citations below reflect the corrected state.

## 1. Security

### (A) Bugs

#### S8-1 · `MKFontDownloader` has no response size cap — Severity: **Low**

**Explanation.** `MKCatalogManifestFetchService` was hardened with
`defaultMaxManifestBytes` (5 MB) plus an `expectedContentLength` pre-check. The
downloader that runs *immediately after it*, against a URL taken from that same
manifest, got no equivalent treatment. It calls
`accumulated.reserveCapacity(Int(http.expectedContentLength))` on a server-declared
value, then accumulates the whole body in memory with no ceiling at any point. A
`Content-Length: 9999999999` causes an immediate multi-GB reservation; a chunked
response with no declared length streams until the app is jetsammed.

**Risk/importance.** The defect is real, but this is **unwired** code, not
dormant-but-wired: `MKFontDownloader`, `MKCatalogManifestFetchService`, and
`MKPremiumDelivery.current` have **zero production call sites**, so flipping the FC-5
delivery enum wires nothing by itself — nothing can reach this path until the FC-5
integration work is actually written. Keep it as a **mandatory pre-wiring hardening
item** gated on that integration: mirror the sibling fetcher's `maxBytes` cap and clamp
the `reserveCapacity` call.

**Files touched.**
- [MKFontDownloader.swift:76–101](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:76)
- Reference implementation to mirror: [MKCatalogManifestFetchService.swift:69–91](MakhtootKit/Sources/MKFonts/MKCatalogManifestFetchService.swift:69)

#### S8-2 · Keychain writes ignore their `OSStatus` — Severity: **Low**

**Explanation.** `MKKeychainStore.write` calls `SecItemUpdate`/`SecItemAdd` and discards
the return code. `delete` discards `SecItemDelete`'s. A failed write (device locked
before first unlock, keychain full, `errSecInteractionNotAllowed`) is indistinguishable
from success. This does **not**, however, stop the clock high-water mark advancing:
`MKTrialManager` writes to **both** stores, `MKUbiquitousStore` persists locally
regardless of entitlement, and `mergedRecord()` takes the max of the two — so a
silently-failing Keychain write degrades redundancy, not the guard itself. The earlier
claim that this "degrades D-224 to the freeze branch permanently" misread `clockNow`:
the freeze fires only on an actual rollback (wall < mark); a stale mark *weakens
rollback detection*, it does not pin the trial.

**Risk/importance.** Diagnosability only: discarding the `OSStatus` removes the evidence
you would need to diagnose a trial-abuse report. (The referral ledger is unaffected in
shipping builds — the module is compile-excluded from Release.) Fix: log the discarded
`OSStatus`.

**Files touched.**
- [MKSecureStore.swift:53–74](MakhtootKit/Sources/MKStore/Trial/MKSecureStore.swift:53)
- Consumer (dual-store writes): [MKTrialManager.swift:148–149](MakhtootKit/Sources/MKStore/Trial/MKTrialManager.swift:148)

#### S8-3 · Import validation does not consider symlinks — Severity: **Medium**

**Explanation.** `DocumentPackage.validateForImport(at:)` (the S-4 fix) enumerates the
package and enforces byte/file-count caps and a top-level allowlist. It never asks
whether an entry is a symlink. `FileManager.enumerator` does not follow symlinks by
default, so a link's *target* size is never counted against `maxTotalBytes`, and
`copyItem(at:to:)` copies the link itself — so the link survives into
`Documents/Projects/`. The S-3 sync packer then reads through that link when packing the
package for CloudKit upload.

**Risk/importance.** An AirDropped `.makhtoot` package containing
`assets/x.png -> ../../../Library/Preferences/...` can cause app-container files to be
packed and uploaded into the user's own CloudKit container, and to be re-shared if that
project is exported. Impact is bounded by the app sandbox and the destination is the
user's own private database, so this is not exfiltration to a third party — but it is
untrusted input controlling which of the app's files get read, which is squarely what
this validator exists to prevent.

**Fix.** Add `.isSymbolicLinkKey` to the enumerator's `includingPropertiesForKeys` and
reject on any symlink; the allowlist loop should reject one at top level too.

**Files touched.**
- [PackageImportValidator.swift:98–121](MakhtootKit/Sources/MKPersistence/PackageImportValidator.swift:98)
- Caller: [MKPersistenceProjectLibrary.swift](Makhtoot/AppShell/Persistence/MKPersistenceProjectLibrary.swift)

#### S8-4 · Containment check uses a bare `hasPrefix` — Severity: **Low**

**Explanation.** `MKAssetStore.assetURL(for:)`'s S-2 defence asserts
`standardizedPath.hasPrefix(assetsDirPath)`. Without a trailing path separator this
also accepts a sibling directory whose name merely *starts with* the assets directory's
name (`…/assets-evil/…` passes a `…/assets` prefix test). Not reachable today — the
component is always `sha256-<digest>.<ext>` appended to `assetsDirURL`, so escaping
requires `..`, which does fail the check. But this is the canonical weak form of a
containment assertion and it is the only thing standing between a hand-constructed
`MKAssetRef` and the filesystem.

**Risk/importance.** Latent. Costs one character to fix (compare against
`assetsDirPath + "/"`, or compare `pathComponents` prefixes).

**Files touched.**
- [AssetStore.swift:36–43](MakhtootKit/Sources/MKPersistence/AssetStore.swift:36)

#### S8-5 · GPOS coverage cache is keyed on PostScript name — Severity: **Low**

**Explanation.** `MKCursiveCoverageCache` keys `[String: Set<UInt16>]` on
`CTFontCopyPostScriptName`. A user-imported font can declare any PostScript name it
likes, including one already used by a bundled premium font. Whichever loads first wins
the cache entry for the whole process. The cache also never evicts, unlike the sibling
`MKGlyphPathProvider` (capacity 512) and `MKShapingService` (cost-limited LRU).

**Risk/importance.** Consequence is confined to a provenance *annotation* — this parser
feeds no positioning decision (the file header is explicit about that) — so the blast
radius is a wrong cursive-provenance flag, not wrong geometry. Cache growth is bounded by
distinct font names, so unbounded only in the pathological case.

**Files touched.**
- [CursiveAttachment.swift:47–90](MakhtootKit/Sources/MKTextEngine/CursiveAttachment.swift:47)

---

#### S8-6 · GPOS lookup indices are not deduplicated — Severity: **Low**

**Explanation.** `MKGPOSCursiveParser.lookupIndices` collects every `LookupListIndex`
across every `FeatureRecord` tagged `curs`, with no `Set`. A crafted font that points a
few hundred FeatureRecords at the same lookup causes that lookup's subtable walk to run
that many times. Every individual read is bounds-checked (correctly), so this cannot
crash — it is only wasted work, once per font, cached thereafter.

**Risk/importance.** Low. Worth a one-line `Array(Set(...))` since the parser explicitly
walks files "this module did not produce and cannot fully trust".

**Files touched.**
- [CursiveAttachment.swift:124–141](MakhtootKit/Sources/MKTextEngine/CursiveAttachment.swift:124)

### (C) New recommendations

1. **Add `NSPrivacyAccessedAPICategoryUserDefaults` to the privacy manifest.**
   `PrivacyInfo.xcprivacy` declares `SystemBootTime` and `FileTimestamp` but **not**
   `UserDefaults`, which the app reads and writes in at least six files
   (`EditorViewModel`, `AppNavigationModel`, `EditorTourModel`, `GeneralSettingsView`,
   `MKUserDefaultsAssetMetadataStore`, `MKFeatureFlags`). Apple emits **ITMS-91053
   "Missing API declaration"** on upload for this. Reason code `CA92.1` (access only to
   app's own defaults) applies.
   *Files:* [PrivacyInfo.xcprivacy](Makhtoot/Resources/PrivacyInfo.xcprivacy)

2. **Sign the catalog manifest, not just the files it names.** Per-file SHA-256 is
   verified after download, but the manifest supplying those digests is trusted on TLS
   alone. Whoever controls the CDN controls both. A detached signature over the manifest,
   verified against a key in the bundle, closes the loop. Relevant before FC-5 flips.
   *Files:* `MKCatalogManifestFetchService.swift`, `MKFontDownloader.swift`

3. **Give `MKFontDownloader` the same injectable `maxBytes` knob** the manifest fetcher
   has, so the cap is testable without streaming real megabytes.

## 2. Performance

### (A) Bugs

#### P8-1 · Both network paths accumulate **one byte per async iteration** — Severity: **Low**

**Explanation.** Both `MKFontDownloader.download` and
`MKCatalogManifestFetchService.fetch` consume the body as
`for try await byte in byteStream { data.append(byte) }`. `URLSession.AsyncBytes` is an
`AsyncSequence` of `UInt8`, but it buffers internally — the cost is the per-byte call
and single-byte `Data.append` overhead, not (as originally stated) one suspension point
per byte. A 4 MB font file is still four million iterations and appends, and the
downloader additionally does a division and comparison per byte for progress throttling.

**Risk/importance.** Meaningfully slower and more CPU-hungry than a chunked read — but
this is **doubly-dead code**: no production call site constructs `MKFontDownloader` or
`MKCatalogManifestFetchService`, `MKPremiumDelivery.current` is hardcoded
`.bundledFallback`, and the hosted manifest URL is an unresolvable `.invalid` host. File
as a pre-FC-5 gate item alongside S8-1. One caveat for the fix:
`byteStream.chunks(ofCount:)` does **not** exist without adding
`swift-async-algorithms`; `URLSession.download(from:)` with a `URLSessionTaskDelegate`
for progress is the dependency-free option.

**Files touched.**
- [MKFontDownloader.swift:82–96](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:82)
- [MKCatalogManifestFetchService.swift:86–91](MakhtootKit/Sources/MKFonts/MKCatalogManifestFetchService.swift:86)

---

#### P8-2 · `CommandJournal.append` re-opens the file and rebuilds a formatter per command — Severity: **Medium**

**Explanation.** Every journaled command does: `createDirectory` → `fileExists` →
(maybe `createFile`) → `FileHandle(forWritingTo:)` → `seekToEnd` → `write` → `close`,
plus a freshly-allocated `ISO8601DateFormatter()`. `ISO8601DateFormatter` construction is
one of the more expensive Foundation initialisers (it builds an underlying
`CFDateFormatter`); allocating one per record is a well-known hot-path mistake. The file's
own doc comment claims this path is "a single `write(2)`/`ftruncate` call, no scene
re-encode" — it is four-plus syscalls and a formatter build.

**Risk/importance.** The journal is on the D-223 critical path and is appended on **every
mutation**, including every coalesced step of a canvas drag. This is the mechanism that is
supposed to be cheap enough to run during a memory-pressure stage-3 flush. Fix is
mechanical: hoist the formatter to a `static let`, and hold one `FileHandle` open for the
actor's lifetime.

**Files touched.**
- [CommandJournal.swift:46–74](MakhtootKit/Sources/MKPersistence/CommandJournal.swift:46)

#### P8-5 · `MKCompositionRevision` is process-global mutable state pruned from one call site — Severity: **Low**

**Explanation.** A `@MainActor enum` holding a `static var counters: [MKNodeID: Int]`.
`forget(_:)` is only invoked from `MKLayerTreeController.sync(to:)`'s removed-node sweep.
Any node that leaves the scene without that sweep running — editor torn down, project
closed, app backgrounded mid-edit — leaves its counter behind for the process lifetime,
and `duplicateThenRevertForEditing` mints a fresh `MKNodeID` per call.

**Risk/importance.** Small leak (16 bytes/entry), but it is *global* state surviving across
editor sessions, which is a correctness smell as much as a memory one.

**Files touched.**
- [LayerTreeBuilder.swift:49–73](MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:49)

#### U8-2 · 8 of 9 design-system components ship with zero accessibility — Severity: **Medium**

**Explanation.** Per-file `accessibility*` counts in

## 4. Ease-of-use & accessibility

### (A) Bugs

#### E8-1 · ~299 silent error swallows against 20 user-facing error surfaces — Severity: **Medium** *(extends prior UX-5)*

**Explanation.** `try?` appears 152 times in `Makhtoot/` and 147 times in
`MakhtootKit/Sources/`. Against that, the entire app contains **20** total occurrences of
`.alert(`, `ContentUnavailableView`, or `MKBanner(`. Concrete instances where the swallow
is load-bearing:

- `MKCatalogManifestFetchService.writeCache` — `try? data.write(...)`; a failed cache write
  means every launch re-fetches, silently.
- `AutosaveController.scheduleDebouncedSave` — `try? await self.flushNow(...)`. **A failed
  autosave is invisible.** The user has no signal that their work is not being persisted.
- `MKTrialManager.writeRecord` — `guard let data = try? encoder.encode(record) else
  { return }`; encode failure silently skips both stores.
- `MKAssetStore.hasAsset` — `try? assetURL(for:)` converts a path-escape *security*
  rejection into a plain `false`.

**Risk/importance.** The autosave one is the serious member of the set: a document tool
that silently stops saving is the worst failure mode it has. The rest are diagnosability
debt. Not all 299 need surfacing — most are legitimately best-effort — but they are
currently indistinguishable from the ones that are not.

### (C) New recommendations

1. **Classify the `try?` sites.** Introduce a `logged(_:)` helper that swallows but emits

   `fullSaveCount`/`completedFlushCount` for tests; a `lastSaveError` published alongside
   them, rendered as an `MKBanner`, is a small change with a large payoff.

#### N8-2 · No bidi isolation around any interpolated value in Arabic copy — Severity: **Low**

**Explanation.** 14 Arabic string literals interpolate a value directly. None wrap the
inserted run in `U+2068 FSI` / `U+2069 PDI` (or `U+061C ALM`). Under the Unicode
Bidirectional Algorithm, a neutral or weak run adjacent to an interpolated value takes its
direction from surrounding context — so `(3/10)` inside RTL text can reorder or mirror its
parentheses in ways that depend on what precedes it. `MKRTLUtilities` implements a
first-strong heuristic for *probing* direction but offers no *isolation* helper.

**Risk/importance.** Low frequency, and mitigated where `toArabicIndicDigits` is used
(Arabic-Indic digits carry bidi class AN and behave more predictably in RTL context). Most
likely to bite exactly where N8-1 already bites.

- [MKSyncStatus.swift](MakhtootKit/Sources/MKSync/Status/MKSyncStatus.swift), and 13 other interpolation sites

## 7. Information correctness

### (A) Bugs

#### C8-1 · The joining-type table omits three entire Arabic Unicode blocks — Severity: **High**

**Explanation.** `MKJoiningTypeTable`'s `rightJoining` and `dualJoining` range lists cover
**nothing above U+06FF** (verified by script: the maximum covered codepoint is U+06FF).
Letters above that fall through to `return .nonJoining`, the default clause. The
`isMark`/`.transparent` branch runs **before** the range lists, so the combining marks in
the missing blocks — Extended-A's 53 Mn marks and Extended-B's 9 Mn marks, which carry
most of the Quranic annotation content — are classified correctly. What is misclassified
is the *letters*:

| Block | Range | Letters misclassified |
|---|---|---|
| Arabic Supplement | U+0750–U+077F | **48** |
| Arabic Extended-B | U+0870–U+089F | **31** (its 9 Mn marks are handled correctly) |
| Arabic Extended-A | U+08A0–U+08FF | **~43** (its 53 Mn marks are handled correctly) |

**Roughly 120 Arabic letters classified as Non_Joining.** These are not obscure: they
serve the Rohingya, African-language, and Khowar orthographies, among others. Per
`ArabicShaping.txt`, many are `D` (Dual_Joining) — e.g. U+0751 BEH WITH DOT BELOW AND
THREE DOTS ABOVE is `D; BEH`.

The consequence flows into Arrange Mode's *metadata*, not into shaping.
`validForms(for:)` maps `.nonJoining → [.isolated]`, so:

- `MKFormResolver.resolve(letter:form:style:)` **coerces** every requested initial /
  medial / final form to `.isolated` for these letters and sets `wasCoerced = true`.
- `FormSelectorModel` therefore offers the user only the isolated form.

So for these ~120 letters the UI reports wrong joining labels, wrongly disables form
options, and blocks decomposition. This is an **availability/metadata bug in Arrange
Mode, not a shaping break** — rendering goes through Core Text (D-103), which is
unaffected, and no shipped composition is mis-shaped. But Arrange Mode *is* the
differentiator, and its metadata is silently wrong for these letters.

The repo also partially contradicts itself here: `MKRTLUtilities.arabicRanges` **does**
list `0x0750...0x077F` and `0x08A0...0x08FF`, and so does the lint test at
[MKAssetNamingLintTests.swift:18](MakhtootKit/Tests/MKAssetsTests/MKAssetNamingLintTests.swift:18)
— though both of those, like the joining table, omit Extended-B (`0x0870...0x089F`).
Three files in the same codebase disagree about which codepoints are Arabic, and none is
complete. No test covers any codepoint above U+06FF — which is why this survived 1,232
tests.

**Risk/importance.** Highest-priority item in this audit: a silent wrong answer in the
module the product is built around, invisible in review — the failure mode `CLAUDE.md`
warns about with *"shaping regressions are invisible in review."* Downgraded from Severe
after adversarial review because Core Text rendering is untouched and no wrong output
ships; what ships is Arrange Mode lying about ~120 letters' capabilities.

**Fix.** Generate the table from `ArabicShaping.txt` rather than hand-encoding it, and add
a test that asserts, for every codepoint in U+0600–U+08FF, that
`MKJoiningTypeTable.joiningType(of:)` matches the UCD value. Interim: the three missing
blocks can be added by hand from the UCD, but the generator plus the parity test is what
stops this recurring.

**Files touched.**
- [JoiningTypeTable.swift:29–90](MakhtootKit/Sources/MKTextEngine/JoiningTypeTable.swift:29) — the omission
- [FormResolver.swift:85–100](MakhtootKit/Sources/MKTextEngine/FormResolver.swift:85) — coercion consumer
- [JoiningAnalyzer.swift:48](MakhtootKit/Sources/MKTextEngine/JoiningAnalyzer.swift:48) — consumer
- [FormSelectorModel.swift](MakhtootKit/Sources/MKArrange/FormSelectorModel.swift) — UI consumer
- [JoiningAnalyzerTests.swift](MakhtootKit/Tests/MKTextEngineTests/JoiningAnalyzerTests.swift) — where the test belongs

#### C8-2 · `baseDirection` classifies every non-Arabic letter as left-to-right — Severity: **Low**

**Explanation.** `MKRTLUtilities.baseDirection(of:)` implements the UBA P2/P3
first-strong rule, but its "strong" test is: *is it in an Arabic range → RTL; else is it
in `CharacterSet.letters` → LTR*. Hebrew, Syriac, Thaana, N'Ko, Adlam and every other
RTL script therefore resolves to `.leftToRight`.

**Risk/importance.** Latent only: `baseDirection(of:)` and
`semanticContentAttribute(for:)` have **zero production callers** — editor direction
comes from `MKTextStyle.baseDirection` and Core Text's bidi handling per D-109, so the
previously claimed "pasted Hebrew mirrors incorrectly" consequence is unreachable. The
LTR treatment of non-Arabic letters is also a documented scoping decision in the function
itself. This is a trap for a future caller, the same class as C8-3. One caveat for
whoever eventually fixes it: the correct test is the scalar's UCD `Bidi_Class`, which
Swift's `Unicode.Scalar.Properties` does **not** expose — a fix needs a small generated
table or an ICU-backed query, not a stdlib property.

**Files touched.**
- [MKRTLUtilities.swift:80–95](MakhtootKit/Sources/MKFoundation/RTL/MKRTLUtilities.swift:80)

#### C8-3 · `isRTLCharacter` returns `true` for Arabic-Indic digits — Severity: **Low**

**Explanation.** `arabicRanges` includes `0x0600...0x06FF`, which contains
U+0660–U+0669 and U+06F0–U+06F9. So `isRTLCharacter("٣") == true`, even though those
digits carry bidi class AN, a *weak* class. `baseDirection` correctly guards against this
with its own `isArabicDigit` pre-check — but that guard lives in the caller, not in
`isRTLCharacter`, so any other caller inherits the wrong answer. The two functions
disagree about the same codepoint.

**Risk/importance.** No current caller is affected (the only external users are
`toArabicIndicDigits`/`toLatinDigits`, which do not consult it). This is a trap for the
next caller.
