## Executive summary

The codebase is unusually disciplined for its size: 1,101 tests with **zero** skips, three
force-unwraps total, actor-isolated I/O throughout, correct StoreKit 2 `checkVerified` usage, and
genuinely excellent inline documentation of design decisions. Structural quality is not the problem.

The problem is **wiring**. The most serious findings are all the same shape: a correct, tested
component exists, and the composition root hands its consumers a stub or bypasses it entirely.

**The two that matter most:**

1. **FC-1 — Bold and italic have no visual effect anywhere in the app.** The shaping engine, the
   drawer, the inspector UI, and the one font provider that resolves weight/slant axes are all
   correct and tested. `AppContainer` builds that provider and then never passes it to anything;
   every render path gets `SystemFontStubProvider`, which silently discards the variant request.
   The **B** and **I** buttons in the font sheet are inert.

2. **FC-2 — PNG and JPEG export bypass the entire monetization gate.** The two most-used export
   buttons never construct `MKExportCoordinator`, so `MKExportGate` (premium fonts, photo
   backgrounds, preset membership) and `MKFreeTierBudget` (2 MP clamp) never run. A free user can
   place a premium font and export it at full resolution.

Both are small fixes — a handful of argument changes and one routing change — with outsized impact.

## 1. Performance

### P-1 · Content hash re-serializes every node to JSON on every render sync
**Severity: High · Effort: M · ROI: Very high · Approval: No**

**What.** `MKContentHash.hash(of:scaleBucket:)` decides whether a layer needs re-rasterizing by
JSON-encoding the node's content and hashing the resulting string. For `.arranged` nodes it encodes
the **entire composition** — every glyph, every mark, every outline path
([`ContentHash.swift:62`](MakhtootKit/Sources/MKRender/ContentHash.swift:62)). `encodedOrEmpty`
allocates a **fresh `JSONEncoder` on every call**
([`ContentHash.swift:86`](MakhtootKit/Sources/MKRender/ContentHash.swift:86)) — two per arranged
node (style + composition), plus one for the background.

This runs for every node on every `sync(to:)`
([`LayerTreeBuilder.swift:221`](MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:221)), which
fires on every committed mutation, every zoom-bucket crossing, and every eviction-driven re-sync.
Arrange Mode — the product's flagship differentiator — is the worst case: the cost of *checking
whether to redraw* scales linearly with composition size, so the feature gets slower exactly as a
user invests more work in it.

**Fix.** Make `MKNode` structurally content-hashable: feed an FNV accumulator directly from typed
fields rather than round-tripping through `Data` → `String`. If that's too invasive for one pass,
two cheaper steps recover most of it: (a) hoist a single `static let encoder` instead of allocating
per call, and (b) cache the per-node hash keyed on a monotonic composition revision counter bumped
by `MKArrangeInteractionModel` on mutation, so an unchanged composition is never re-encoded.

**Files.** `MakhtootKit/Sources/MKRender/ContentHash.swift:31,62,74-92` ·
`MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:202,221`

### P-2 · Four concurrent polling loops run for the entire editor session
**Severity: Medium · Effort: S · ROI: High · Approval: No**

**What.** While a project is open, four unbounded `Task` loops run continuously:

| Cadence | Loop | Site |
| --- | --- | --- |
| 100 ms | mode + selection poll | [`EditorViewModel.swift:382`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:382) |
| 150 ms | zoom-scale poll | [`EditorViewModel.swift:425`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:425) |
| 1 s | memory banner poll | [`EditorViewModel.swift:308`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:308) |
| 2 s | memory pressure sampling | [`MemoryPressureMonitor.swift:110`](MakhtootKit/Sources/MKRender/MemoryPressureMonitor.swift:110) |

That's roughly 18 main-actor wakeups per second, permanently, whether or not anything changed. None
is gated on `scenePhase`. The inline comments show two prior Observation-storm bugs already fixed
*inside* these loops — the loops themselves are the remaining cost, and they are the reason those
bugs were possible.

**Fix.** The mode/selection poll is replaceable with `withObservationTracking` — both `session.mode`
and `session.selection.ids` are already `@Observable`. The zoom poll is replaceable with the
`scrollViewDidZoom` / `scrollViewDidScroll` delegate callbacks `MKCanvasViewController` already
implements ([`MKCanvasViewController.swift:268`](MakhtootKit/Sources/MKCanvas/MKCanvasViewController.swift:268));
the header comment rejects KVO for Swift 6 strict-concurrency reasons, which don't apply to a plain
`@MainActor` delegate method. At minimum, suspend all four on `.background` / `.inactive`.

**Files.** `Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:304-329,378-408,423-448` ·
`MakhtootKit/Sources/MKRender/MemoryPressureMonitor.swift:98-115`

### P-3 · `setVisibleRect` receives the wrong coordinate space
**Severity: Medium · Effort: S · ROI: High · Approval: No**

**What.** `MKLayerTreeController.lastVisibleRect` is documented as living "in the same (unscaled,
host-layer) coordinate space every layer's `.frame` lives in"
([`LayerTreeBuilder.swift:56-62`](MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:56)). The only
caller passes `vc.scrollView.bounds`
([`EditorViewModel.swift:445`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:445)) — scroll-view
coordinates, offset by `contentOffset`, shifted by the centering insets computed at
[`MKCanvasViewController.swift:189-192`](MakhtootKit/Sources/MKCanvas/MKCanvasViewController.swift:189),
and scaled by `zoomScale`. Layer frames live in `contentHostView` space: unzoomed canvas points,
origin `.zero` ([`MKCanvasViewController.swift:122`](MakhtootKit/Sources/MKCanvas/MKCanvasViewController.swift:122)).

At any zoom ≠ 1, or whenever the canvas is inset-centered, `evictOffscreen()`
([`LayerTreeBuilder.swift:341`](MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:341)) intersects
mismatched rectangles — blanking layers the user is currently looking at and skipping genuinely
offscreen ones. This only fires under memory pressure (D-116 stage 1), which is precisely the
moment it's least recoverable.

**Fix.** Pass `vc.scrollView.convert(vc.scrollView.bounds, to: vc.contentHostView)`. Add regression
coverage at zoom 0.5× and 4× asserting a centered layer survives an `evictOffscreen()` call.

**Files.** `Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:445` ·
`MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:151-180,336-347`

### P-4 · Raster export bypasses the tiled exporter built for exactly this job
**Severity: Medium · Effort: S · ROI: High · Approval: No**

**What.** `MKTiledRasterExporter` exists with an explicit acceptance criterion — "8192×8192 PNG
export peaks < 300 MB resident"
([`TiledRasterExporter.swift:37`](MakhtootKit/Sources/MKExport/TiledRasterExporter.swift:37)) — and
is correctly used by `PDFRasterExporter`, `PDFPrintCMYKExporter`, and `ExportCoordinator`. But
`exportForSharing()` (JPEG) and `exportPNGForSharing()` (PNG) call
`MKSnapshotRenderer.render(...)` directly at `scale: 2`, materialising the full canvas as one
bitmap in one allocation
([`EditorViewModel.swift:482,499`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:482)).

A 2048 × 2048 canvas at scale 2 is a 4096 × 4096 buffer — ~67 MB for the `CGImage`, plus a full
`UIImage` copy, plus the encoded `Data`, all resident simultaneously. On an older device under any
existing memory pressure this is a plausible OOM on the app's most-used button.

**Fix.** Route both through `MKExportCoordinator` (which also fixes **FC-2** — same change).

**Files.** `Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:479-509` ·
`MakhtootKit/Sources/MKExport/TiledRasterExporter.swift:37,68`

### P-5 · The undo stack has no byte budget, and its memory-pressure hook is dead
**Severity: Medium · Effort: M · ROI: Medium · Approval: No**

**What.** `MKUndoStack` caps at 500 entries with 25 % eviction
([`UndoStack.swift:41-50,111-113`](MakhtootKit/Sources/MKPersistence/Undo/UndoStack.swift:41)). The
doc comment is explicit that this is a stand-in: *"A count-based ceiling stands in for a true
byte-size governor registration… it exposes `maxEntries` as the configurable knob WS-07 can tune
down under real memory pressure via `setMaxEntries(_:)`."*

`setMaxEntries(_:)` has **zero call sites** outside its own declaration. `MKUndoStack` does not
conform to `MKMemoryAccountable`, so `MKMemoryGovernor` — which has exactly two registrants, the
layer tree and the asset provider
([`EditorViewModel.swift:253,256`](Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:253)) —
cannot see it or shrink it.

Entry cost is not uniform. Most commands are lean deltas, but the inverse of a delete is an
`MKInsertNodeCommand` holding the **entire removed node**
([`Commands.swift:20-24`](MakhtootKit/Sources/MKPersistence/Undo/Commands.swift:20)) — including a
full arranged composition. Deleting and re-deleting arranged text through a long session can pin
substantial memory that the ladder is structurally unable to reclaim.

**Fix.** Conform `MKUndoStack` to `MKMemoryAccountable` (`accountedBytes()` via the existing
`MKCommandCoder` encode, sampled rather than per-entry), register it with the governor at
`.low` priority, and implement `evictOffscreen()` as `setMaxEntries(maxEntries / 2)`.

**Files.** `MakhtootKit/Sources/MKPersistence/Undo/UndoStack.swift:33-50` ·
`MakhtootKit/Sources/MKFoundation/MKMemoryGovernor.swift:35-135` ·
`Makhtoot/AppShell/Scenes/Editor/EditorViewModel.swift:251-256`

### P-6 · Scene revision hashing walks the whole document byte-by-byte per mutation
**Severity: Medium · Effort: M · ROI: Medium · Approval: No**

**What.** `MKSceneRevision.hash` encodes the full `MKScene` and then iterates every byte in a Swift
`for byte in data` loop ([`PersistenceSupport.swift:46-59`](MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:46)).
It's called for journal `baseRev` and autosave dirty-tracking on every mutation. `MKCRC32.checksum`
does the same per-element walk on every journal line
([`PersistenceSupport.swift:78-85`](MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:78)).

Against the repo's own `fixture-5000-nodes.makhtoot`, that's a multi-megabyte encode plus a
per-`UInt8` loop on every glyph nudge — a per-keystroke cost proportional to total document size
rather than to the size of the edit.

**Fix.** Hash via `data.withUnsafeBytes` over word-sized chunks rather than per element, and gate
the full-scene encode behind a cheap mutation counter so the debounce path doesn't recompute it on
every coalesced gesture step.

**Files.** `MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:45-90`

### P-7 · Orphan sweep tears down and rebuilds a directory on every save
**Severity: Low · Effort: S · ROI: Medium · Approval: No**

**What.** `MKAssetStore.sweepOrphans` unconditionally `removeItem`s the entire `backups/orphans/`
directory, recreates it, enumerates every file in `assets/`, and moves each unreferenced one — on
**every save cycle** ([`AssetStore.swift:61-76`](MakhtootKit/Sources/MKPersistence/AssetStore.swift:61)).
For a document with many assets this is a burst of filesystem syscalls on a ≤ 2 s autosave debounce,
and the remove-then-recreate is a wider window than needed for the one-cycle grace semantics it
implements.

**Fix.** Skip the sweep entirely when the referenced-asset set is unchanged since the last sweep
(the manifest already carries `assetIndexDigest` for exactly this kind of check). Delete only the
prior cycle's orphan files rather than the containing directory.

**Files.** `MakhtootKit/Sources/MKPersistence/AssetStore.swift:53-76` ·
`MakhtootKit/Sources/MKPersistence/DocumentPackage.swift:26-30`

### P-8 · `DegradationController.history` grows without bound
**Severity: Low · Effort: S · ROI: Medium · Approval: No**

**What.** Every memory-stage transition appends to `history`, which is never trimmed
([`DegradationController.swift:108,164`](MakhtootKit/Sources/MKRender/DegradationController.swift:108)).
Each event is small, but the array grows fastest under sustained pressure oscillation — i.e. the
memory-pressure handler itself accumulates memory precisely when memory is scarce.

**Fix.** Cap at the last ~64 events with a ring buffer, or gate retention behind `#if DEBUG` if the
history exists only for diagnostics.

**Files.** `MakhtootKit/Sources/MKRender/DegradationController.swift:104-170`

### P-9 · `hasEvictedContent` scans every layer on each visible-rect change
**Severity: Low · Effort: S · ROI: Low · Approval: No**

**What.** `hasEvictedContent` walks `layers.values` to test for any nil `.contents`
([`LayerTreeBuilder.swift:189`](MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:189)). The doc
comment justifies this as acceptable because it runs on the 150 ms poll, not a hot path — which is
fair. Listed for completeness: it becomes a real cost only once **P-2** replaces the poll with
per-frame scroll callbacks, so fix it *with* P-2, not before.

**Fix.** Track a `Bool` flag set by `evictOffscreen()` / `evictAll()` and cleared at the end of a
full `sync(to:)`.

**Files.** `MakhtootKit/Sources/MKRender/LayerTreeBuilder.swift:182-191`

## 2. Security

### S-1 · Entitlement cache is trusted forever, and stored where iOS can delete it
**Severity: High · Effort: S · ROI: Very high · Approval: No**

**What.** Two coupled defects in `MKEntitlementResolver`, failing in **opposite** directions:

1. **Never expires.** `cacheStalenessTolerance` (default 3 days) is declared, accepted as an init
   parameter, and assigned — and **never read anywhere in the codebase**. An exhaustive grep across
   `Sources`, `Tests`, and the app target returns exactly three hits, all in its own declaration
   ([`MKEntitlementResolver.swift:54,67,71`](MakhtootKit/Sources/MKStore/MKEntitlementResolver.swift:54)).
   `init` decodes the cached record and applies `record.decode()` with no reference to `resolvedAt`
   ([`:85-88`](MakhtootKit/Sources/MKStore/MKEntitlementResolver.swift:85)). The ARCHITECTURE §18.2
   policy that the property's own doc comment describes — *"honored offline until expiry + this
   tolerance, then degrades to `free`"* — is unimplemented. A `subscribed` cache grants premium
   indefinitely offline.

2. **Purgeable location.** The cache is written to `.cachesDirectory`
   ([`:75-79`](MakhtootKit/Sources/MKStore/MKEntitlementResolver.swift:75)), which iOS reclaims
   under disk pressure. A **paying customer launching offline after a purge resolves to `.free`**
   and is shown the paywall. That's the failure mode that generates refund requests and one-star
   reviews.

**Fix.** Apply the staleness check in `init` (exempting `.lifetime`, per T17's "honored offline
indefinitely"), and move the cache to Application Support — which the app already uses for analytics
and font state via `MKFileLocations.applicationSupportDirectory()`.

**Files.** `MakhtootKit/Sources/MKStore/MKEntitlementResolver.swift:49-89,142-146` ·
`MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:162-168`

### S-2 · Path traversal through asset refs in an imported package
**Severity: Medium · Effort: S · ROI: High · Approval: No**

**What.** `MKAssetRef` is a plain `Codable` struct with `digest: String` and `ext: String` and no
validation on either ([`MKNode.swift:247-255`](MakhtootKit/Sources/MKModel/MKNode.swift:247)).
`MKAssetStore.assetURL(for:)` interpolates both straight into a path component
([`AssetStore.swift:21-23`](MakhtootKit/Sources/MKPersistence/AssetStore.swift:21)), and
`appendingPathComponent` does not normalize `..`.

A hand-crafted `.makhtoot` package — arriving via AirDrop, Files.app, or an iCloud share — whose
`scene.json` carries `ext: "png/../../../../Library/Preferences/net.binjamshid.makhtoot.plist"`
causes `assetData(for:)` to read that file and place it as an image node. The blast radius is
bounded by the app sandbox, so this is confidentiality-within-container rather than device
compromise — but it is unvalidated attacker-controlled input reaching the filesystem, and the
import path (**S-4**) makes delivery trivial.

**Fix.** Validate in a hand-written `MKAssetRef.init(from:)`: `digest` must match `^[a-f0-9]{64}$`
and `ext` must be in a lowercase alphanumeric allowlist. Throw on violation so the document is
rejected rather than partially loaded. As defense in depth, assert in `assetURL(for:)` that the
`standardizedFileURL` still has `assetsDirURL` as a prefix.

**Files.** `MakhtootKit/Sources/MKModel/MKNode.swift:247-255` ·
`MakhtootKit/Sources/MKPersistence/AssetStore.swift:21-51`

### S-3 · Sync upload leaks a full plaintext copy of every project into `tmp/`
**Severity: Medium · Effort: S · ROI: High · Approval: No**

**What.** `nextBatch` creates `tmp/MKSyncBatch-<UUID>/<projectID>/`, packs the complete document
package into it — scene plus every asset — and **never removes it**
([`MKSyncEngineController.swift:271-298`](MakhtootKit/Sources/MKSync/Engine/MKSyncEngineController.swift:271)).
The download path in the same file does this correctly with a `defer`
([`:400-402`](MakhtootKit/Sources/MKSync/Engine/MKSyncEngineController.swift:400)), which makes the
omission clearly an oversight rather than a design choice.

Every sync cycle accumulates another full copy of the user's documents. iOS purges `tmp/` only
opportunistically, so a heavy user can silently lose gigabytes — and unpurged copies outlive the
package's own lifecycle, meaning a deleted project's bytes linger outside the store that's supposed
to own them.

**Fix.** Mirror the download path. Because the record-provider closure runs asynchronously after
`nextBatch` returns, cleanup needs to hang off batch completion in `handleEvent`'s
`sentRecordZoneChanges` case rather off `nextBatch` itself. Add a launch-time sweep of stale
`MKSyncBatch-*` directories to reclaim what's already accumulated in the field.

**Files.** `MakhtootKit/Sources/MKSync/Engine/MKSyncEngineController.swift:256-299,486-514`

### S-4 · External package import has no size or shape validation
**Severity: Medium · Effort: S · ROI: Medium · Approval: No**

**What.** `importExternalPackage` validates only that `manifest.json` decodes, then `copyItem`s the
entire externally-supplied directory into `Documents/Projects/`
([`MKPersistenceProjectLibrary.swift:347-376`](Makhtoot/AppShell/Persistence/MKPersistenceProjectLibrary.swift:347)).
There is no cap on total bytes, file count, asset count, or node count, and no rejection of
unexpected entries.

A malicious or merely corrupt `.makhtoot` can fill the device. Anything extra it carries is copied
into the user's document store verbatim — and then packed and uploaded to their CloudKit container
by **S-3**'s sync path. Combined with **S-2**, an imported package is the app's widest untrusted
input surface and currently its least validated.

**Fix.** Before copying, enumerate the source with `FileManager.enumerator` and enforce a
total-bytes cap, a file-count cap, and an allowlist of expected package members (`manifest.json`,
`scene.json`, `thumbnail.png`, `journal.mkj`, `assets/`, `backups/`). Surface distinct errors rather
than collapsing everything into `ProjectImportError.invalidPackage` (see **UX-5**).

**Files.** `Makhtoot/AppShell/Persistence/MKPersistenceProjectLibrary.swift:318-383` ·
`Makhtoot/AppShell/Navigation/RootShellView.swift:81-95`

### S-5 · Export temp files are never cleaned up
**Severity: Low · Effort: S · ROI: Medium · Approval: No**

**What.** Every share writes `makhtoot_export_<UUID>.{jpg,png}` into `temporaryDirectory` and

### S-6 · No file protection class on any document write
**Severity: Low · Effort: S · ROI: Medium · Approval: No**

**What.** No `FileProtectionType` or `NSFileProtectionKey` appears anywhere in the codebase.

### S-7 · Atomic-write temp files are created inside the document package
**Severity: Low · Effort: S · ROI: Medium · Approval: No**

**What.** `MKAtomicIO.write` places `.tmp-<UUID>` in the destination's own directory
([`PersistenceSupport.swift:25`](MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:25)).
That directory *is* the `.makhtoot` package. A crash between the write and the `replaceItemAt`
leaves an orphan inside a user-visible, Files.app-exposed, CloudKit-synced package — and **S-3**'s
packer will then upload it.

**Fix.** Write temps to a sibling scratch directory outside the package, or sweep `.tmp-*` on
package open in `LaunchReconciler`.

**Files.** `MakhtootKit/Sources/MKPersistence/Internal/PersistenceSupport.swift:18-29` ·
`MakhtootKit/Sources/MKPersistence/Metadata/LaunchReconciler.swift:16`

### S-9 · Font downloader: no URL scheme check, and a misordered cleanup
**Severity: Low · Effort: S · ROI: Low · Approval: No**

**What.** Two issues in `MKFontDownloader.download(_:)`, both dormant behind `.bundledFallback`:

- `entry.fileURL` comes from the fetched manifest and is passed to `session.download(from:)` with no
  scheme validation ([`MKFontDownloader.swift:42`](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:42)).
  ATS blocks cleartext HTTP by default, but a `file:` URL is not covered by ATS.
- `defer { try? FileManager.default.removeItem(at: tmpURL) }`
  ([`:53`](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:53)) is registered before
  `moveItem(at: tmpURL, to: destination)` ([`:66`](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:66))
  consumes the file. Harmless in the success path (the `try?` swallows the resulting failure), but
  it obscures intent and would silently mask a genuine cleanup failure on the error path.

The SHA-256 verification at [`:56-59`](MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:56) is
correct and does the heavy lifting for integrity — this is hardening around it, not a hole in it.

**Fix.** Assert `entry.fileURL.scheme == "https"` before the download; move the `defer` to cover
only the failure paths.

**Files.** `MakhtootKit/Sources/MKFonts/MKFontDownloader.swift:37-80`

## 3. UI / UX

### UX-1 · The canvas is entirely invisible to VoiceOver
**Severity: High · Effort: L · ROI: Medium · Approval: Yes** *(scope and interaction-design call)*

**What.** There is not a single `isAccessibilityElement`, `accessibilityElements`, or
`UIAccessibilityElement` anywhere in `MKCanvas` or the app target. All 68 accessibility labels sit
on chrome — toolbars, sheets, zoom controls. The canvas itself, and every node, selection, and
arranged glyph on it, is one opaque unlabeled view.

A VoiceOver user can open a project and reach every button, but cannot perceive or select anything
they have made. The `LayersPanelView` is the only route to node-level structure, and it is not
positioned as an accessibility affordance.

**Fix.** Implement `accessibilityElements` on `contentHostView`: one element per top-level node,
with `accessibilityLabel` derived from node kind plus text content,

FD-04, with the hosted URL deliberately pointed at an RFC 2606 `.invalid` TLD so a misconfigured

Listed because of what it implies for launch: `MKFontDownloader` (81 lines),

about before launch rather than after.

### FC-6 · No UI tests for ~8,000 lines of SwiftUI
**Severity: Medium · Effort: M · ROI: High · Approval: No**

**What.** 1,101 unit tests with zero skips cover MakhtootKit thoroughly. There is **no UI test
target at all** — no `*UITests` directory anywhere in the project.

Every bug the impl-log describes as *"caught on-simulator, not by inspection"* lives in exactly the
layer with no automated coverage. `EditorViewModel.swift:353` documents one such at length: a
committed text overlay that stayed stuck on screen. **FC-1** and **FC-2** are both composition-root
wiring defects — invisible to unit tests by construction, and trivially catchable by one integration
test each.

**Fix.** Add a `MakhtootUITests` target covering the five highest-value flows: onboarding → first
project; insert text → commit; enter and exit Arrange Mode; premium-export paywall gate; and
`.makhtoot` open-in-place import. Add a small set of composition-root integration tests asserting
that `AppContainer`'s dependencies actually reach their consumers.

**Files.** `Makhtoot.xcodeproj` (new target) · `Makhtoot/AppShell/`

### FC-7 · Export gate cannot see premium *assets*
**Severity: Low · Effort: M · ROI: Low · Approval: Yes** *(cross-module scope)*

**What.** `MKExportGate` accepts an optional externally-supplied `Set<MKNodeID>` for premium-asset
detection and defaults it to empty
([`ExportGate.swift:19-35`](MakhtootKit/Sources/MKExport/ExportGate.swift:19)). The header documents
the cause precisely: pattern-background and asset placements are not tagged on `MKNodeCore`
(`sourceAssetID` was proposed and never landed), and `MKPremiumContentLedger` is a caller-maintained
side ledger rather than scene state.

Two of the three gating flags (fonts, photo backgrounds) recover structurally from the scene. The
third does not, and no caller currently supplies the set — so a premium *asset* placed on a canvas
does not gate the export.

**Fix.** Either add `sourceAssetID` to `MKNodeCore` — the clean fix, requiring an `MKModel` schema
touch — or have `EditorViewModel` pass its live `MKPremiumContentLedger`-derived set at the call
site. The former is correct; the latter is cheaper. Founder call on whether a schema bump is
acceptable pre-launch.

**Files.** `MakhtootKit/Sources/MKExport/ExportGate.swift:19-35,72-110` ·
`MakhtootKit/Sources/MKAssets/Provenance/` · `MakhtootKit/Sources/MKModel/MKNode.swift`

### FC-8 · Referral qualifying action is a placeholder
**Severity: Low · Effort: S · ROI: Low · Approval: Yes** *(product decision)*

### FC-9 · Arabic-only is enforced by convention, not by the build
**Severity: Low · Effort: S · ROI: Low · Approval: No**

**What.** `CFBundleDevelopmentRegion` and `CFBundleLocalizations` are both `ar`
([`Info.plist:24-33`](Makhtoot/Config/Info.plist:24)), and `Localizable.xcstrings` declares
`"sourceLanguage": "ar"`. But nothing prevents an English literal reaching a user-facing surface,
and 655 Arabic literals sit outside the catalog (see **UX-7**). The RTL utilities in
`MKRTLUtilities` are applied by hand at each site rather than enforced.

Given that Arabic-only is described in `PROJECT_DESCRIPTION.md` as *the strategic bet* rather than a
temporary limitation, it deserves a guardrail.

**Fix.** Add a build-phase script that fails on user-facing string literals containing Latin
characters outside a small allowlist (font names, format identifiers, URLs).

**Files.** `Makhtoot/Config/Info.plist:24-33` · `Makhtoot/Resources/Localizable.xcstrings` ·
`Scripts/`

## 8. What is working well

Worth stating plainly, because the finding list above is not representative of the whole.

- **Test discipline.** 1,101 tests, zero skips, zero disabled. Rare at this scale.
- **Concurrency.** Actors used correctly and for stated reasons; `nonisolated(unsafe)` appears
  exactly where a lock-guarded snapshot genuinely needs it, with the reasoning written down.
- **Decision documentation.** Nearly every non-obvious choice carries a comment explaining *why*,
  including the ones that turned out wrong. This audit was possible at this depth largely because
  of it.
- **Honest deferrals.** `SUBSETTING_FOLLOWUP.md`, the `.invalid` placeholder URL, and the onboarding
  trial-screen note ("showing that copy today would mean fabricating a trial date… a paywall-
  compliance honesty violation") are all examples of choosing a documented gap over a plausible lie.
  That instinct is worth more than most of the code.
- **The Arabic engine.** `PathLayoutEngine`'s handling of logical-order pen advance, genuinely
  negative Core Text advances, and mark reattachment reflects real understanding of the script
  rather than a Latin algorithm with RTL bolted on. This is the part of the codebase that most
  justifies the product's premise.
- **Error taxonomy.** `MKExportBlockReason`, `MKPersistenceError`, and `FallbackNote` are precise
  and exhaustive — the "never silent" contract is real at the engine level. The gap is that the UI
  discards most of it (**UX-5**, **EU-4**).

The pattern across the serious findings is consistent and worth naming: **the modules are right and
the composition root is under-tested.** `AppContainer` is where correct components get connected —
or, four times in this audit, silently don't. One integration-test file asserting that each declared
dependency actually reaches its consumers would have caught FC-1, FC-2, FC-3, and P-5 before
TestFlight.
