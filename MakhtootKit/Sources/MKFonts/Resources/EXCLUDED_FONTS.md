## Released this session (WS-16, `docs/impl-log/WS-16-cursive.md`)

The 5 fonts below (Amiri, Amiri Quran, Aref Ruqaa, Rakkas, Qahiri) were held
out of `catalog-seed.json` by WS-09 pending resolution of D-222 step 8's
"D-105's mark-capture model needs a cursive-pair structure before that font
ships" condition. WS-16 resolved this and **released all 5 into the default
browsable catalog** this session, with evidence:

1. **Probed empirically** (`docs/impl-log/WS-16-cursive.md` ADR WS16-A1/A2):
   `CTRunGetPositions` already bakes the cursive-adjusted position into
   capture (D-105's own "the shaped positions already encode the answer"
   principle, previously established for mark anchoring, extends unchanged
   to cursive attachment), and MKArrange's D-220 affine chain
   (`MKArrangedGeometry.localAffine`/`worldTransform`) composes
   `layout.position` as an opaque translation regardless of what produced
   it. Display, translate, rotate, and scale of cursive-attached glyphs all
   already worked correctly — verified, not assumed — with **zero geometry
   changes needed**.
2. **Added the minimal structure D-222 actually needs**: a per-glyph
   provenance flag, `MKShapedRun.cursiveAttached` (`MKTextEngine`, a native
   GPOS 'curs'-coverage-table reader, never anchor values) and
   `MKProvenance.cursiveAttached` (`MKModel`, additive/defaulted field, no
   schema-version bump) — NOT the heavier "cursive-pair anchor-delta"
   structure D-222's text raised as a possibility, per the probe evidence
   (a full anchor-delta structure cannot, on its own, fix the one real gap
   below either — see the ADR).
3. **T-AR-31's automated FUNCTIONAL TWIN passes for all 5 fonts**
   (`MakhtootKit/Tests/WS16CursiveTests/AllFiveHeldFontsEvidenceTests.swift`):
   live-vs-arranged derivation is pixel-identical within the 0.5% D-222 bar,
   including for GPOS-cursive-attachment-affected text specifically (Amiri
   «سجا»/«سجد», `CursiveDerivationFidelityTests.swift`).
4. **One real, bounded, DOCUMENTED limitation found and regression-tested**:
   `JoinController`'s D-107 ZWJ-synthetic-context reshape (join-break/
   restore) does not always reproduce the exact natural glyph id — for
   GPOS-cursive-attachment-affected pairs specifically because ZWJ cannot
   trigger the contextual GSUB substitution feeding a font's `curs` feature,
   and more broadly (found empirically on Amiri) for some non-cursive pairs
   too, a general per-font D-107 variance WS03-A6 already flagged as
   font-dependent. This is accepted-by-design per D-222's own established
   precedent for the analogous single-glyph-scale-inside-a-joined-word case
   (T-AR-60/TEST_MATRIX.md §7.9) — a visual-only, non-crashing,
   non-corrupting limitation in a manual arrange-mode edit path, not a
   capture defect.
5. **What remains NOT done this session** (named, not glossed over): the
   full MANUAL-ARABIC human-visual sign-off for T-AR-31/32/33/36-38
   (no human-in-the-loop pass requested, same disposition every other
   workstream's own gate 4 in this repo records); T-AR-36-38
   (ligature decompose/recompose) were not specifically exercised against
   these 5 fonts this session; `MKArrange.ArrangeDeriver` does not yet
   thread `cursiveAttached` from `MKShapedRun` into `MKProvenance` — the
   exact required change is published in `MakhtootKit/CONTRACTS.md`'s
   WS-16 follow-up section for whoever next touches `MKArrange`.
