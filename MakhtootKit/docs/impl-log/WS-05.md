## ADRs (packet §10 duty)

### WS05-A1: DF-6a resolved via `MKClusterMap.clusters`' own array order — no `flowDirection` option

**Decision.** The packet's own task 4a/4b describe the pen order as
"visual order (RTL-aware)" with an elaborate `flowDirection`
(`rtlNatural`/`pathForward`) option computing arc position from
`startOffset + (lineWidth − glyphVisualRightEdge(i))`. Per this run's
explicit instruction ("note DF-6a: the pen order is LOGICAL reading
order, the 'visual-order' name was a corrected misnomer") and
`ARCHITECTURE.md` §9.4 / `TEST_MATRIX.md` T-PTH-2 (both authoritative,
post-dating the packet's own prose), `PathLayoutEngine` implements
**logical reading order** as the ONE pen order — the `flowDirection`
option is dropped entirely, not implemented as a second mode.

**Implementation finding (simplifies HOW, not a deviation from WHAT
DF-6a asks for).** `MKTextEngine.MKClusterMap.clusters`
(`ClusterMap.swift`, WS03-A2) is already built by sorting every raw
cluster — from every run, across the whole line — by UTF-16
`utf16Range.lowerBound` ascending. UTF-16 offset IS logical (typed)
position, independent of script direction, by definition. So a single
walk over `line.clusterMap.clusters` in its own array order already
realizes DF-6a's "logical reading order, chained run-by-run" directly —
no separate per-run-reversal-and-rechain pass is needed. Verified by
`PathLayoutEngineTests.multiSwitchFixtureArcOffsetsMonotonic` and
`.noSpaceDigitAdjacencyHasNoGapOrOverlap` (the packet's two new T-PTH-2
fixtures).

### WS05-A2: rotate-about-advance-center + curvature clamp join mitigation, no glyph warping in v1

**Decision.** Task 4c's anchor-at-advance-midpoint (not leading edge) is
the primary join-continuity mitigation. Task 8's curvature clamp is
implemented as: if the tangent swings more than `maxJoinAngleDegrees`
(default 25°) across ONE base glyph's OWN span (between
`frame(atLength: spanStart).tangent` and `frame(atLength: spanEnd).tangent`
— the glyph's own two span-edge tangents), that glyph's ROTATION source
switches from the midpoint tangent to the normalized average of those two
edge tangents. Position never moves — only the rotation source changes
(moving position off the arc-length midpoint would reintroduce the
cracking task 4c's anchor choice fixes). `curvatureWarning` (task 8.3) is
a SEPARATE measurement: it fires when two ADJACENT base glyphs' final
(post-clamp) rotations differ by more than `curvatureWarningThresholdDegrees`
(default 40°). No glyph outline is ever distorted (v1 scope, per the
packet's own "NO glyph distortion/warping in v1" instruction) — the LUT/
layout API is kept clean of any per-glyph outline transform so the v2
warping seam (`ARCHITECTURE.md` §24) can be added later without touching
this module's placement math.

**Documented limit.** The clamp reduces worst-case rotation mismatch at a
join; it does not GUARANTEE zero visible seam on an arbitrarily sharp
curve. Verified: `PathLayoutEngineTests.gentleArcNoCurvatureWarning`
(radius ≥ 4× font size, tatweel-stretch stress fixture, task 8's own
accept bar) and `.sharpCornerSetsCurvatureWarning` (task 8's "sharp-corner
star path" fixture — flag set, no crash, no NaN). Manual visual
confirmation of "joined Arabic stays visually connected on gentle curves"
needs the DEBUG harness (app dir, out of this packet's fence — see
"Deferred items" below), so it is NOT independently confirmed by eye this
session; the numeric proxy (no curvature warning on the gentle fixture,
warning set on the sharp one) is what ships as evidence.

### WS05-A3: user-offset carry-over keyed by codepoints+ordinal (`PathClusterProvenanceKey`), not `MKClusterID`

**Decision.** `MKCluster.id` (`MKClusterID`) is a fresh UUID minted on
EVERY shaping capture (`MKTextEngine`'s own WS03-A7 note #4) — it cannot
be the stable cross-relayout key task 9 asks for ("carry over userOffsets
by matching clusterID provenance (same codepoints + ordinal)"). This
module defines `PathClusterProvenanceKey { codepoints: [UInt32],
occurrenceOrdinal: Int }` — stable across a full reshape as long as the
relevant substring and its ordinal position among identical clusters
don't change — as the literal realization of "same codepoints + ordinal."
`PathLayoutEngine.layout` accepts `[PathClusterProvenanceKey:
PathGlyphUserOffset]` and folds each entry into the matching glyph(s).
Verified: `PathLayoutEngineTests.userOffsetAppliesAndSurvivesRelayout`
(appending a letter to "علي" → "عليك" keeps the earlier glyph's offset,
task 9's literal accept criterion).

**Known schema gap (flagged, not silently dropped — see "Deviations"
below): this is engine-level support only.** `MKModel.MKPathTextNode` has
no field to PERSIST a user-offset map, so `PathTextCommands
.setGlyphOffset` cannot ship as a real `MKCommand`/Codable-round-tripping
builder within this packet's fence (`MKModel` sources are out of fence).
`PathTextOffsetStore` is the session-scoped stand-in.
