## 4. New findings the plan misses

- **Undo/redo fix needs two classes, not one.** `CanvasSession.canUndo`/`canRedo` pass through `document.undoStack.canUndo` — a *second* non-`@Observable` hop (`MKUndoStack`, `Undo/UndoStack.swift:20-21,105-106`). `@Observable` on `MakhtootDocument` alone fixes scene-dependent fields but not the undo/redo toolbar buttons.
- **`MKDegradationController` is a fourth type in the same observability-gap family.** It's a plain non-`@Observable` `@MainActor` class (`MKRender/DegradationController.swift:95`) — exactly what the 1s memory-poll loop works around. Worth including if a broader observability fix is planned.
- **`ArrangeToolbarView`/`PathEditToolbarView`/`ToolRailView`'s pill chrome is copy-pasted across at least 5 files**, not 3: `PathOptionsPopoverView.swift:101-102` and `FormSelectorPopoverView.swift:46-47` hand-roll the identical `theme.radius.sheet`/`theme.elevation.floatingBar` pair too. No `MKFloatingBar` (or equivalent) component exists anywhere (0 hits) — a fix wanting one shared surface must introduce a new component, not reuse one.
- **Dependency-graph fact for asset rendering**: `MKAssets` depends only on `MKFoundation`/`MKModel`; adding it to `MKRender` would *not* create a cycle — but it's moot, because the shipped WS-14 pattern lowers geometry before the node crosses the module boundary. If a *future* `.asset(MKAssetRef)` vector-program feature is built, the codebase's own precedent (`MKAssetProviding`/`MKEmptyAssetProvider` in `AssetProviding.swift`, built explicitly so `MKRender` never depends on `MKPersistence`) points to a resolver-protocol-in-`MKRender` approach, not a new `MKRender → MKAssets` package edge.
- **Real entitlement/capability case names** (two separate enums, easy to conflate): `MKPremiumCapability` (MKFoundation, gating): `premiumFonts, fontImport, photoBackgrounds, premiumExportFormats, hiResExport, cloudSync, premiumAssets`. `PremiumFeature` (app-layer `MKRoute.swift`, paywall context): `customCanvas, premiumFont, photoBackground, cloudSync, exportFormat, premiumAsset`.
- **`MKColorSpec` has no HSB conversion helpers at all** — only RGBA storage + CGColor/CMYK conversions. A rebuilt color picker must write its own RGB↔HSB math; nothing in `MKColor` provides it.
- **The color picker's `onSelect` callback silently discards alpha.** `hsbColor.resolvedRGBA` comes from `Color(hue:saturation:brightness:)` with no opacity parameter (defaults to 1) — any color chosen through the picker, including a highlight that started at 30% alpha, returns fully opaque. Previously unflagged; worth including in any color-picker rebuild plan.
- **`BackgroundDrawer.swift`'s own comment says `.image` background is "premium content the renderer does not gate"** — i.e., no entitlement check exists at render time despite the doc comment calling it premium. Separate latent gap if entitlement gating matters.
- **`ShapeDrawer.localPath` is duplicated, not shared, in `MKExport`.** `SVGShapeGeometry.localPath` (`SVGProvenance.swift:108-123`) is an independently-maintained second copy of the same geometry switch, because `ShapeDrawer.localPath` is package-internal. Any `.asset`-handling fix must be applied in both places.
- **`MKArrangeInteractionModel.granularity` is plain local `@MainActor` state**, not scene-derived (unlike `activeOwnerNode`/`canBreakOrRestoreJoinForSelection`/`canDecomposeSelection`, which all transitively depend on `session.scene`). A scene-desync fix targeting "all four gates" would over-engineer this one.
- **`MKPathTextInteractionModel` has its own separate `lastErrorMessage` property**, identically named to `MKArrangeInteractionModel`'s — a real trap for anyone grepping `lastErrorMessage` expecting one class.
- **Path-text's schema migration is nontrivial**: fixing the absolute-coordinate/zero-transform convention changes how *already-saved* `.makhtoot` documents render. `MKSceneSchema.currentVersion` has never been bumped past 1; no real (non-identity) migrator has ever shipped. Any BUG15 geometry fix must ship a genuine v1→v2 migrator alongside it.
- **`MemoryStressDriveTests.swift:68`** (MKRenderTests) builds 5000 `MKShapeNode` fixtures relying on the implicit (1,1) default scale — not rendering-sensitive today, but a shape-sizing default change should account for its existence.
- **Two distinct "thumbnail path" storage mechanisms exist and neither is wired**: `MKManifest.thumbnail` (in-package relative filename in manifest.json) and `MKProjectRecord.thumbnailPath` (derived Library/Caches copy, SwiftData store) — the browser UI reads only the latter. A correct fix must populate both, and must trigger from `EditorScene.finish(_:)` (the sole "editor close" choke point). `MKSync/Serialization/MKProjectRecordCoder.swift:79-81` already assumes `thumbnail.png` may exist and copies it during sync — a second production consumer beyond the currently-dead browser path.
- **`MKSnapshotRenderer(fonts:).render(scene, region:, scale:, quality:)` → `UIImage(cgImage:)` → `.pngData()`** is the exact, already-proven pipeline (`EditorViewModel.exportPNGForSharing()`, lines 446-451) a thumbnail feature should reuse.

## 5. Sequencing impact

**The phase order (P0–P8) mostly stands, with one confirmed exception:**

- **P3.1 should be removed from the critical path (or rescoped to a no-op verification task) and no longer gates P3.2.** The plan's Part 5 programme diagram and Part 7 risk table both treat P3.1 ("make `.asset` geometry render in `MKRender`") as an unsized blocker for "the entire asset browser." - **P1.3's remedy should be re-scoped from an automated gate to the existing manual (Q59) checklist path** — this changes *what* P1.3 delivers, not its position in the phase order.
- **No other reordering is supported by the evidence.** RC1/RC2/RC3/RC4/BUG3/BUG10/BUG13/BUG15/BUG16/PHASE6 findings are all within-phase corrections (scope or location fixes) that do not shift phase boundaries. G5's resolution (form selector is substitution-only) constrains P3.4's *scope* (it cannot be lifted out of Arrange Mode without building substantial new machinery) but the audit gives no basis to reorder it relative to other phases.
