## Contract gaps found (reported, not silently invented)

Checked `MakhtootKit/CONTRACTS.md` at the start of this run and again
mid-session — WS-07 published a **contract** ("WS-07 (`MKRender`) —
renderer bring-up contract (P4)") very early, including `RenderTreeProviding`
and `HitTester`. As of this run's session end, the ACTUAL `MKRender`
source tree still does not build those two types (`Sources/MKRender/`
has `AssetProviding.swift`, `SceneRenderer.swift`, `DegradationController
.swift`, `MemoryPressureMonitor.swift`, the `Drawers/` group, `Geometry/
ArrangedGeometry.swift`, `BitmapCache.swift` — no `HitTester.swift` or a
`RenderTreeProviding` conformer). This is WS-07 mid-flight on its own
committed contract, not a missing commitment — re-checked at session end,
still not landed.

Two gaps, precise:

1. **No per-node world-bounds query exists anywhere in the published
   contract.** `HitTester.node(at:in:)` is a single-point, single-best-hit
   query with no bounds/OBB accessor; `RenderTreeProviding` only WRITES
   transforms (`applyTransientTransform`), it has no read accessor either.
   Every task in this packet that needs a node's world bounding box for
   something OTHER than "is this exact point inside this exact node"
   (marquee selection, snapping candidates, selection-chrome placement,
   handle math, `InspectorModel`'s W/H fields) has no real geometry source
   to consume yet. **Not invented around** — `MKCanvasGeometrySource`
   (`Geometry/MKCanvasGeometrySource.swift`) is `MKCanvas`'s own declared
   consumption seam (a protocol `MKCanvas` needs FROM a geometry provider,
   which is squarely task 3's "you own priority/policy" framing), with a
   synthetic test conformer (`Tests/MKCanvasTests/CanvasTestSupport.swift`
   `FakeGeometrySource`) standing in. Recommendation for WS-07/the
   orchestrator: add something like `func worldBounds(for nodeID:
   MKNodeID, in scene: MKScene) -> CGRect?` (or an OBB-returning
   equivalent) to `RenderTreeProviding` or a sibling protocol.

2. **`HitTester.node(at:in:)` returns only ONE result**, so ARCHITECTURE
   §10.3's tap-cycling ("repeated taps within 1.5 s at ≤8 pt distance walk
   the `hits` array so occluded objects are reachable") cannot be built on
   top of it as published — cycling needs the full ordered candidate list,
   not just the top hit. `HitTestPolicy.swift`'s `MKHitCandidate`/`hits(at
   :in:tolerance:)` implements the full policy (ordering, tolerance,
   locked/hidden exclusion, tap-cycling) against a candidate LIST it
   expects a caller to supply — today that's `MKCanvasGeometrySource`
   (gap 1 again); once a real `HitTester` exists, the cleanest integration
   is `HitTester` gaining a multi-hit query, or `MKCanvas` building its own
   candidate list from `MKCanvasGeometrySource.worldOBB` once that seam is
   filled. Recorded, not resolved, this session.

`MKCanvasRenderBridge` (`applyTransientTransform(nodeID:transform:
CGAffineTransform)`, `commitTransients()`) has method names/signatures
copied EXACTLY from the published `RenderTreeProviding` so that once it
actually builds, wiring the real render tree in (in `AppEnvironment.swift`,
WS-13's territory) needs no call-site changes in `MKCanvas` — only a
one-line "pass the real render tree instance instead of a test double."

## Locked-decision conflict — reported, RESOLVED by coordinator gate ruling

Packet §5 task 3's own prose/accept criterion ("`isLocked`/`isHidden`
skip... locked node taps fall through to node below") directly disagreed
with ARCHITECTURE.md §10.3 step 5's original text ("locked nodes hit...
selectable to unlock via inspector... but their handles are disabled").
This implementation followed the packet's literal task-3 wording (locked
nodes excluded from canvas tap hit-testing entirely) and flagged the
conflict rather than silently picking a side.

**Resolution (coordinator gate ruling, this run):** the implementation is
CORRECT and stands. PRD R-4.6 (P0, PRD.md:253 + 267-268) explicitly
specifies "tap selects topmost unlocked visible node... locked nodes are
skipped by tap selection but selectable from the layers panel (with lock
badge)" — the packet matched the PRD; ARCHITECTURE.md's §10.3 step 5 was
the stale text. ARCHITECTURE.md line 1630 has been corrected (the one
sanctioned out-of-fence edit, per the same ruling) to state: locked nodes
are skipped by canvas tap hit-testing, selectable from the layers panel
with a lock badge, annotated "(corrected in Run 3 to match PRD R-4.6; see
docs/impl-log/WS-06.md)". Auditing the code against the FULL R-4.6 text
during this update surfaced one real gap the original conflict note had
missed: `LayersModel.select` routed through `CanvasSession.setSelection`,
whose sanitizer filters locked nodes out — so the "selectable from the
layers panel" HALF of R-4.6 was not actually satisfied. Fixed in the same
pass: `CanvasSession.setSelectionFromLayersPanel(_:)` (a dedicated panel
path that admits locked/hidden nodes, dropping only nonexistent ids) and
`LayersModel.select` now routes through it; canvas tap/marquee behavior
unchanged. Covered by the new
`LayersModelTests.lockedNodeIsSelectableFromTheLayersPanelButNotFromCanvasTap`
(asserts BOTH halves of R-4.6: tap skips, panel selects, row carries the
lock badge). The same ruling routes the
`MKUngroupCommand` fix and the `MKCommandCoder` journal-serialization
gaps to WS-02 upstream; `MKCanvas`'s local conformers
(`Commands/MKCanvasCompositeCommands.swift`) stay as-is until WS-02's fix
lands. See `HitTestPolicy.swift`'s header comment and
`SelectionState.swift`'s `selectable(from:...)` doc comment for the
in-code pointers to this note.

## ADRs

### WS06-A1: transient-transform fast path contract with MKRender

See "Contract gaps" above. `MKCanvasRenderBridge` (`Geometry/
MKCanvasGeometrySource.swift`) mirrors `RenderTreeProviding`'s
`applyTransientTransform`/`commitTransients()` signatures exactly.
`MoveGesture`/`HandleGestures` call `applyTransientTransform` once per
gesture FRAME (visual preview) and `commitTransients()` once at gesture
END — never per-node-per-frame content redraw, honoring D-114/D-115's
"CALayer position updates only" contract on the calling side; WS-07's real
conformer is what has to honor it on the receiving side.

### WS06-A2: selection granularity model (object/glyph/letter)

`MKSelectionState` (`SelectionState.swift`) carries `granularity: .object/
.glyph/.letter` and `compositionScope: MKNodeID?` per task 4's literal
shape, but only `.object` has any interaction code driving it in this P4
slice — `.glyph`/`.letter` selection inside `arranged` nodes is Arrange
Mode canvas UX (task 15, P5), which needs `MKArrange`'s not-yet-built
`LevelMapping`. The data shape is P4 spine work (so P5 doesn't need a
breaking model change); the interaction is not.

### WS06-A3: snapping sources & radii

`SnapEngine.swift` implements ARCHITECTURE §10.5 exactly: canvas
edges/center, other-node edges/centers (via
`MKCanvasGeometrySource.worldOBB` once wired), equal-spacing candidate
detection, 6 view-pt radius (zoom-normalized), and rotation-angle snapping
(delegated to `MKAnchoredResize.snappedAngle` — 5° grid + magnetic pull to
the 45°-family). Hysteresis (task 9/§10.5's "2 pt to prevent flicker") is
declared as a constant (`MKSnapEngine.hysteresisPoints`) but not yet wired
into `snap(...)`'s engage/disengage decision — the current implementation
re-evaluates fresh every call rather than tracking "already engaged"
state across frames. Flagged as a small follow-up, not a correctness bug
(worst case: snap re-evaluates cleanly every frame instead of having
engage/disengage stickiness) — the unit-testable MATH the packet's own
gate asks for is all present and green.

### WS06-A4: overlay commit semantics (D-104) incl. cancel path

`TextEditingOverlayController` (`TextEditingOverlay.swift`) is the pure
state machine: `begin` opens one `MKUndoStack` gesture bracket for the
WHOLE editing session (not per burst — this is what makes burst-boundary
coalescing actually work; see the bug this uncovered, below), `textDidChange`
mirrors into the node via a locally-declared `MKCanvasTextEditCommand`
(§14.3, 700 ms burst window), `commit` ends the bracket, `cancel` unwinds
every undo entry the session pushed (tracked via a plain counter) and
force-restores the original node as a defensive fallback. D-201's "overlay
normalizes to axis-aligned during editing, restores rotation on commit" is
implemented as: the overlay never applies the node's rotation to its own
view transform, and the engine-rendered layer is simply hidden (never
mutated) while editing — so "restoring" the rotation on commit is
automatic (nothing was ever changed) rather than a scene write. This is a
closer reading of §4.8's actual wording than a literal "mutate then
restore" implementation would be, and avoids an unnecessary write/undo
entry pair.

**Real bug this session's own tests caught before it shipped**:
`TextEditingOverlayController.begin()` originally never called
`session.beginGesture()` — `MKUndoStack.perform`'s coalescing is
INERT (`gestureActive == false`) unless a bracket is open, so every
keystroke was silently getting its OWN undo entry regardless of burst
timing. `TextEditingOverlayTests.keystrokesWithinTheBurstWindowCoalesceToOneUndoEntry`
failed immediately on first test run (3 keystrokes → 4 total undo entries
instead of 1 more), which is exactly what led to finding and fixing it.
Left in this log because it's a real "test-first caught a real bug"
example, not a hypothetical.

## Other real bugs caught by this session's own tests (worth recording)

1. **`weak var geometrySource`/`renderBridge` + inline temporary test
   doubles.** `session.geometrySource = FakeGeometrySource()` deallocates
   the instance immediately (no strong reference survives the statement) —
   `CanvasSession.geometrySource`/`.renderBridge` are intentionally `weak`
   (the view controller, not the session, owns the render tree's
   lifetime), which is correct production design but a real test-authoring
   footgun. Caught by 3 initially-failing tests
   (`snappingPullsTheDraggedNodeOntoACanvasEdge`,
   `aMultiFrameResizeProducesExactlyOneUndoEntry`,
   `aMultiFrameRotateProducesExactlyOneUndoEntry`) whose numbers were
   silently wrong (snap never engaged, resize/rotate never previewed)
   rather than crashing — fixed by holding a local `let` reference for the
   test's lifetime in every call site, and documented in
   `CanvasTestSupport.swift`'s `FakeGeometrySource`/`RecordingRenderBridge`
   doc comments so it isn't reintroduced.
2. **`UITextView.baseWritingDirection = .rightToLeft` does not compile.**
   `baseWritingDirection(for:in:)` is a `UITextInput` protocol METHOD, not
   a settable property — only caught by the iOS-simulator `xcodebuild
   test` gate (macOS `swift test` never compiles the `#if
   canImport(UIKit)` block at all, since UIKit isn't available there).
   Fixed via `semanticContentAttribute = .forceRightToLeft` +
   `NSParagraphStyle.baseWritingDirection` in `typingAttributes` (the
   actual supported mechanism). This is exactly why the packet's own gate
   requires BOTH `swift test` and `xcodebuild test` against a real iOS
   destination — recorded here as a concrete instance of that gate finding
   something the faster loop cannot.
3. **`MKUngroupCommand` (WS-02, `MKPersistence/Undo/Commands.swift`) does
   not compose the group's own transform into children before splicing
   them back to top level** — verified by reading the shipped source, not
   assumed: `apply(to:)` does `copy.nodes.replaceSubrange(index...index,
   with: g.children)` with children's `core.transform` untouched. A group
   moved/rotated/scaled AFTER grouping would silently snap its children
   back to their PRE-MOVE positions on ungroup. `MKPersistence` is out of
   this packet's fence, so the fix lives entirely inside `MKCanvas`:
   `MKCanvasUngroupCommand` (`Commands/MKCanvasCompositeCommands.swift`)
   performs the correct composition
   (`MKGroupTransform.worldTransform(childLocal:groupTransform:)`) before
   splicing, in one atomic `apply()`, with `MKRestoreTopLevelNodesCommand`
   (a public WS-02 primitive) reused as the exact inverse. Covered by
   `CanvasSessionTests.ungroupAfterMovingTheGroupPreservesChildWorldPositions`
   and the pure-math cross-check in `GeometryMathTests
   .groupThenTransformThenUngroupPreservesWorldPosition`. Recommendation:
   WS-02 (or whichever workstream next owns `MKPersistence/Undo/
   Commands.swift`) should apply the same fix to `MKUngroupCommand`
   itself, since any OTHER caller of that command (not routed through
   `MKCanvas`) would still hit the bug.

## Cross-packet gaps flagged (not invented around)

`MKCommandCoder` (`MKPersistence/Undo/MKCommandCoder.swift`) is a CLOSED
switch over WS-02's own command catalog — `MKCanvasMultiTransformCommand`,
`MKCanvasMultiCoreCommand`, `MKCanvasTextEditCommand`, and
`MKCanvasUngroupCommand` (all declared in `Commands/
MKCanvasCompositeCommands.swift`, all legitimate conformers of the public,
open `MKCommand` protocol) are NOT known to it. `CommandJournal.append`
throws `unknownCommandType` for them, which `MakhtootDocument.apply(_:)`
swallows via `try?` by design (journaling failures never block the
in-memory apply). Practical, scoped consequence: a crash mid-drag/
mid-typing-burst/mid-ungroup loses only that ONE pending journal entry on
crash-recovery replay — the normal ≤2 s debounced full-scene autosave
still captures the end state on its regular cadence regardless. Also: two
of these four command types (`MKCanvasMultiTransformCommand`,
`MKCanvasTextEditCommand`) exist specifically because the SHIPPED
`Commands.swift` doesn't have the `MKBatchCommand`/`MKTextEditCommand`
types ARCHITECTURE §14.1's own illustrative closed catalog names — verified
by reading `Commands.swift` in full, not assumed. Recommendation: WS-02 (or
whoever next touches `MKPersistence/Undo/`) adds "batch"/"textEdit"/
"ungroupComposed" cases to `MKCommandCoder`, or exposes an extensible
registration hook, so a future workstream doesn't have to re-discover this.
