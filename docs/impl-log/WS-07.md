### WS07-A1: scaleBucket quantization + re-raster hysteresis

**Decision.** `MKScaleBucket.quantize(_:)` (`ContentHash.swift`) maps an
arbitrary zoom scale to the nearest bucket AT OR BELOW it, on the sequence
`bucket_n = 0.025 × (√2)^n` for integer `n`, clamped to `[0.025, 64]`.
"Nearest at or below" (floor, not round) means content never renders
blurrier than the actual zoom — it can only be marginally higher-res than
strictly needed. `MKLayerTreeController.setVisibleRect` only forces a
re-rasterization pass when the quantized bucket actually CHANGES (an
early-return on same-bucket), which is the "hysteresis" the packet's task
1 accept criterion asks for ("scroll/zoom produces no content redraw until
zoom settles into a new bucket") — realized as bucket-crossing detection
rather than a separate timer/threshold-with-margin mechanism (unlike the
memory ladder's hysteresis, §12.4, which explicitly needs a time-based
margin because its input is noisy; zoom-bucket crossings are already
discrete and don't need one).

**Verified pitfall (caught by test, not by inspection):** the bucket
sequence does **not** pass through exactly `1.0×` (since
`log(1/0.025)/log(√2)` isn't an integer) — an early test assumed
`quantize(1.3) == 1.0` and failed with `1.131`. Fixed the TEST, not the
implementation, once the math was checked by hand — documented here so a
future reader doesn't "fix" `quantize` to force round numbers, which would
contradict §11.3's literal "powers of √2 from 0.025×" spec.

### WS07-A2: direct-draw choice for huge nodes over CATiledLayer (v1)

**Decision.** `TileRenderer.swift` implements task 9's "huge-node tiling
support" as bounds math only (`tileRects(covering:scale:maxBytes:)`,
splitting a region into ≤64 MB strips) over the EXISTING
`MKSnapshotRenderer.render(_:region:scale:quality:)` region-rendering
path — no `CATiledLayer`-style manual mosaic-sublayer machinery, no new
rendering code path. The packet's task 9 explicitly frames this as a
choice ("choose direct-draw for v1 simplicity, document tradeoff") and
that framing is followed literally.

**Tradeoff.** Direct-draw means a huge node's FULL bitmap is never
materialized at once (good — the whole point), but panning across it at a
fixed zoom re-renders whichever tiles just became visible from scratch
each time, with no tile-level caching/reuse across pan gestures in this
implementation (`BitmapCache` is keyed `(nodeContentHash, scaleBucket)`,
not `(nodeContentHash, scaleBucket, tileOrigin)` — extending the key
shape to cache individual tiles is the natural P14/WS-08 follow-up if
profiling shows repeated-tile re-render cost matters in practice).
`MKLayerTreeController` itself does not yet ROUTE large nodes through
`TileRenderer` automatically (task 9's "manual tiles" wiring into the
live canvas layer tree is not built) — `TileRenderer` is exercised today
by `MKExport`-shaped callers (region rendering) and is ready for
`MKLayerTreeController` to call once a size threshold policy is added;
this is the one task-9 sub-piece intentionally left at "primitive
exists, auto-wiring doesn't" for this P4 slice.

### WS07-A3: ladder thresholds/hysteresis implementation of D-116 (P4 hooks/seams, not full hardening)

**Decision.** `MKMemoryStage`/`MKDegradationController`/
`MKMemoryPressureMonitor` implement the FULL D-116/D-223 state machine
(threshold mapping, `.warning`-forces-stage1, `.critical`-never-downgrades,
10 s-below-threshold-minus-5pts hysteresis, save-before-degrade ordering
with stage-1/2 full-flush vs. critical journal-only routing) exactly per
ARCHITECTURE §12.3/§12.4's pseudocode — all of it is real, tested logic,
not stubs. What is explicitly NOT built (P14, per this run's scoping
instruction "D-223 ladder hooks/seams... not the full hardening pass"):

1. Real `os_proc_available_memory()` sampling — `MKMemorySampling
   .currentUsedFraction()` returns a hardcoded `0` (documented

   exercised via the injectable `sampler` closure `MKMemoryPressureMonitor`
   accepts — `DegradationLadderTests.swift`'s 9 tests walk the full
   0→1→2→3→(back) cycle, hysteresis timing included, without needing the
   real symbol.
2. No cross-module `MKMemoryGovernor` (ARCHITECTURE §12.3 declares this
   type `// MKFoundation`, a target outside this packet's fence) —
   `BitmapCache` accounts its own bytes and exposes `purgeOffscreen()`/
   `purgeAll()` matching the shape a future governor would call, but
   nothing outside `MKRender` is registered with anything today.
3. `MKLayerTreeController` does not yet READ `MKDegradationController
   .fidelity` to actually halve `contentsScale`/simplify shadows on a live

   (`MKRenderQuality.editorPreview(stage:).fidelity`,
   `MKStylePainting.paintReducedShadowIfNeeded`,
   `SceneRendererTests.reducedFidelityShadowNeverDoubleDarkensOverlappingMarks`),
   but the LIVE WIRING from a running `MKMemoryPressureMonitor` into the
   canvas's actual render quality is a P14/WS-13 integration task (needs

**Rationale for building the full state machine anyway** (rather than a
thinner stub): the packet's own task 10 accept criteria are unit-testable
independent of real memory pressure ("unit tests with injected readings
walk 0→1→2→3 and back"), and INV-17/D-223's save-before-degrade ordering
is exactly the kind of subtle sequencing bug that's cheap to get right
now and expensive to retrofit later. Building the full, real, tested
state machine — while being explicit about the ONE genuinely
unverifiable piece (the Darwin symbol) — is more honest than a
"P14 will build this" placeholder that would need the same design work
redone later.

### WS07-A4: content-hash cache keying (transform excluded)

**Decision.** `MKContentHash.hash(of:scaleBucket:)` hashes exactly the
fields that affect PIXELS at a given zoom bucket — style
(fill/stroke/shadow), and per-kind content (text string + `MKTextStyle`,
shape geometry, image asset ref + kind, background content, and for
arranged nodes the FULL `ArrangedComposition` including every child's
`layout`/`transform`/`outline`/`style`) — and explicitly EXCLUDES
`MKNodeCore.transform`, `.opacity`, `.isHidden`, `.isLocked` (transform/
opacity are layer properties applied around a cached bitmap, §11.2;
hidden/locked are presence/policy, not content). One documented wrinkle:
for ARRANGED nodes specifically, each CHILD's own `transform` field IS
included in the composition hash (not excluded) — because D-220's chain
bakes a child's `transform` directly into the world geometry the stored
outline is painted at (unlike a top-level node, where transform is a
separate, cheap layer-property update); only the composition's OWN
`core.transform`/`core.opacity` follow the normal top-level-node exclusion
rule. Verified by `ContentHashTests` (7 cases: transform-only no-op,
opacity-only no-op, fill-color change, text-string change,
scale-bucket change, hash stability, plus the two `MKScaleBucket`
correctness tests WS07-A1 describes).

### Fix A (WS-13 Bug 2): committed transform-only changes never reached the layer

**Root cause** (`MKRender/LayerTreeBuilder.swift`): `syncNode` updated
layer geometry only inside `rasterize(_:into:)`, which is (correctly,
WS07-A4) gated on `MKContentHash` — and `MKContentHash` (correctly)
excludes `transform`. The transform-application path existed only for
TRANSIENT gestures; on a committed sync, `syncNode` actively RESET the
layer transform to `.identity` and nothing re-applied the committed
transform. Model right, layer stale — exactly WS-13's reproduction
(chrome correct, pixels stuck until an unrelated zoom-bucket crossing).

**Fix**: the controller now tracks `bakedTransform`/`bakedAnchor` per
node — the world transform baked into the layer's current bitmap and the
layer's world anchor at bake time. EVERY pure transform change, committed
or transient, is applied as the delta `baked⁻¹ ∘ current` converted to a
layer transform via the new `layerTransform(worldDelta:anchor:)` helper.
Content-hash changes still (and only they) re-rasterize, re-baking the
transform and resetting the delta to identity.

**Second latent bug found while fixing**: the pre-existing
`applyTransientTransform` set the raw world-space delta directly as the
layer transform. CALayer applies its transform about the layer's ANCHOR
(`rendered(p) = anchor + M(p − anchor)`), so a raw world delta is only
correct when it is a pure translation (translation is anchor-independent)
— live ROTATE/SCALE gestures would have rendered displaced. WS-06's
drag-focused tests never caught it because drags are translations. The
anchor-adjusted helper (`M = translate(anchor) ∘ D ∘ translate(−anchor)`,
derivation in its doc comment) now serves both paths.

**Evidence**: `MKRenderTests/CommittedTransformSyncTests` (4 tests) —
committed move: `consumeRasterizationCount() == 0` AND flattened layer
tree pixel-identical (≤0.1%) to a fresh export-path render of the moved
scene, plus direct old-position/new-position pixel probes (the literal
WS-13 symptom); committed 90° rotation of an asymmetric 40×10 bar:
correct-anchor pixel probes, zero re-raster; transient 90° rotation: same
probes (locks the latent anchor bug); move-then-recolor sequence: exactly
one re-raster, at the new transform, still export-identical.

### Fix B (WS-13 Bug 1): `SystemFontStubProvider` garbled Arabic

**Root cause** (`MKFoundation/Stubs/MKFontProviding.swift`, confirmed by
probe script before editing): the stub ignored `handle.postScriptName`
and always returned `CTFontCreateUIFontForLanguage(.system, size, "ar")`
(= `.SFNS-Regular`). Shaping through that font makes Core Text cascade
Arabic runs to `.SFArabic-Regular`, whose PostScript name + glyph IDs
`MKTextEngine` captures into the run (probe: glyphs `[9, 1244, 44, 206,
286, 640]` for «مرحبا»). At draw time `LiveTextDrawer` resolves the run's
captured name back through the stub — which returned `.SFNS-Regular`
again, so SF-Arabic glyph IDs were drawn through SF-UI's glyph table:
garbled Arabic, correct Latin (Latin glyph IDs were captured from the UI
font itself). A shaping↔drawing font-consistency violation, not a
rendering-pipeline defect — matching WS-13's isolation experiment.

**Fix trap, verified empirically**: the naive fix
(`CTFontCreateWithName(runPSName)`) is runtime-fragile — on the macOS 26
host, CoreText REFUSES dot-prefixed system-font name requests
(".SFArabic"/".SFArabic-Regular" both) and silently substitutes
TimesNewRomanPSMT with only a console note. WS-13's app-side workaround
uses exactly this call and happens to work on the iOS 26.5 simulator
runtime only. The fixed stub therefore resolves in three
round-trip-verified steps: (1) by-name, accepted only if the returned
font's PostScript name matches the request (catches the silent Times
substitution); (2) the language-tagged UI font itself when IT was
requested (Latin runs); (3) the SF Arabic cascade member obtained via the
proper API for this job, `CTFontCreateForStringWithLanguage(seed, "م",
"ar")` — probe-verified to return the same font/glyph table Core Text
picks during shaping (identical glyph bounding boxes for the captured
IDs). Unknown names land on (3), an Arabic-capable default appropriate
for an Arabic-first app's pre-WS-09 stub.

**Evidence**: `MKRenderTests/FontStubProviderTests` (5 tests) — the
coordinator-requested «مرحبا» shaping smoke test (glyph sanity — noting
SF Arabic legitimately shapes 5 letters to 6 glyphs via base+dot
component decomposition, so the "garbled" marker is `.notdef`/glyph 0 and
PS-name mismatch, not glyph count; cluster-map coverage of the full
source string; and THE invariant: draw-time resolution of every run's
captured font name returns a font with that exact PostScript name);
Arabic coverage of the default handle's resolved font; real installed
fonts still resolve by name; bogus names fall back Arabic-capable; and a
default-stub vs. explicit-provider whole-pipeline render-identity check
that also asserts non-blank output. Suite green on BOTH the macOS host
(where by-name resolution is refused — exercising fallback steps 2/3)
and the iOS 26.5 simulator (the runtime where WS-13 observed the
garbling). The pre-existing `MKFoundationTests` stub tests (size-only
