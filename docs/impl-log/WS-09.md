## Run-3 fix — `CoverageAnalysisTests.amiriSupportsQuranicMarksAndTashkeel` test-order dependency (2026-07-18)

**Symptom**: `swift test --filter CoverageAnalysisTests` failed deterministically
(both standalone and inside `--filter MKFontsTests`) with `arabicRange.percentage
→ 0.0`, `supportsQuranicMarks`/`supportsTashkeel` both false — despite the Amiri
binary being intact (`Resources/Fonts/Amiri/Amiri-Regular.ttf`, 431KB, valid
TTF, unchanged). Passed in WS-09's original session; the only change since was
an unrelated test-suite rewrite in a sibling workstream that reshuffled global
`swift test` ordering across the whole package.

**Root cause (confirmed)**: the test resolved its `CTFont` by PostScript name
— `CTFontCreateWithName(face.postScriptName as CFString, 24, nil)` — after
only calling `BundledFontIndex().loadAll()`, which reads `records.json`/font
files off disk but never calls `CTFontManagerRegisterFontURLs`. `CTFontCreateWithName`
never errors on an unregistered name; it silently substitutes a fallback
system font. The test only ever passed because *some other test* in the same
process (e.g. `MKFontRegistryTests`, which does call `registry.loadBundled()`
→ `CTFontManagerRegisterFontURLs(.process)`) happened to run first and
register Amiri into the process before this test's name lookup — a hidden
dependency on cross-suite execution order, which Swift Testing does not
guarantee. Once a sibling workstream's test-suite rewrite changed global
ordering, this test could run before any font got registered, so
`CTFontCreateWithName("AmiriRegular", ...)` silently returned a Latin
substitute (e.g. Times/Helvetica) → 0% Arabic coverage across the board.

**Fix**: `MakhtootKit/Tests/MKFontsTests/CoverageAnalysisTests.swift` —
`amiriSupportsQuranicMarksAndTashkeel` now resolves its `CTFont` directly from
`face.fileURL` via `CTFontManagerCreateFontDescriptorsFromURL` +
`CTFontCreateWithFontDescriptor` (new private helper
`Self.ctFont(fromFileURL:size:)`), instead of by process-wide name lookup.
This reads the real on-disk Amiri binary's own sfnt tables regardless of
whether anything has registered it into the process yet — hermetic, order-
independent, no dependency on any other test having run first.

**Source audit (MKFonts + MKFontsTests)**: `MKCoverageAnalyzer.swift` itself
takes a `CTFont` parameter and does no name resolution — no source change
needed there. Grepped every test file in `MKFontsTests` for
`CTFontCreateWithName`/`ctFont(for:` /`MKRegistryFontProvider` usage: every
other call site (`MKFontRegistryTests`, `MKFontLockControllerTests`,
`MKFontStorageManagerTests`, `MKLicensingDataSourceTests`,
`MKPerFontEngineReRunTests`) calls `registry.loadBundled()` itself, within
the same test, before resolving any font by name — each is self-contained
and does not rely on any other test's registration. `MKFontRegistry.ctFont(for:)`
also round-trip-verifies (`CTFontCopyPostScriptName(font) == face.postScriptName`)
and throws `MKFontError.registrationFailed` on a mismatch, so even a future
ordering regression on those paths would fail loudly rather than silently
report wrong data. `CoverageAnalysisTests.latinOnlySystemFontReportsZeroArabicCoverage`
resolves `"Helvetica"` by name, which is a real always-present system font
unrelated to Amiri registration — no change needed. No other registration-
order dependency found.
