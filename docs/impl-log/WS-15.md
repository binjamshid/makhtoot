## Root cause and what actually blocks upload

The App Store Connect API key already in use (`KEY_ID`, issuer
`ISSUER_ID`, team `54T3MDUR7H`) is valid for archiving (it
authenticated fine for the archive step above) but **its assigned role in App Store
Connect does not include cloud-managed distribution-certificate access.** Apple's roles
that can manage certificates/profiles via the Xcode Cloud-managed-signing API are
`Admin`/`Account Holder`-tier; a `Developer`/`App Manager`-tier key can build but not
mint or fetch distribution certificates through this path.

This is a real gap, not a bug in tonight's work: `signingStyle=automatic` forces Xcode
to go through exactly this cloud API to find-or-create an "App Store" (distribution)
provisioning profile for `net.binjamshid.makhtoot`, and none exists locally for this
specific bundle id yet (checked directly tonight — every `.mobileprovision` already on
this machine under `~/Library/MobileDevice/Provisioning Profiles/` is a distribution
profile for a **different** app in the same team's portfolio: "Ghawazi AppStore CLI",
"Ghawazi Widgets AppStore CLI", "Mahdhar AppStore" ×2, "Mahdhar Dev AJR" ×2 (dev-only),
and "Masoon AppStore CLI" — the last one is the file named
`C2T9K5NMZC-masoon-appstore.mobileprovision`; direct inspection tonight shows its actual
embedded `TeamIdentifier` **is** `54T3MDUR7H`, the same team as this project — the
`C2T9K5NMZC`-looking filename prefix is not the team id, correcting
`docs/impl-log/WS-07-p14-run3.md`'s observation (a), which read that prefix as a
"foreign team" without inspecting the profile's actual contents. It is still retired-app
residue worth deleting eventually, just not a foreign-team file.). None of these seven
local profiles has `net.binjamshid.makhtoot` as its application identifier, so none is
usable even under manual signing without first obtaining the right profile — and the
valid local keychain certificate, "Apple Distribution: Abdulrahman Al-Rashdi
(54T3MDUR7H)", has no matching profile to pair with for this specific app yet.

The fact that distribution profiles already exist for sibling apps under this same team
shows distribution-capable signing has worked for this account before — almost
certainly via an interactive Xcode session under the founder's own logged-in Apple ID
(which typically carries full account privileges), not this CI-style API key.
