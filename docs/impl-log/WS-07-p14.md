## Tasks completed

### T-A: MKDegradationController wiring (LayerTreeBuilder.swift)

Added `private weak var degradationController: MKDegradationController?` to
`MKLayerTreeController`. Weak reference avoids a retain cycle — WS-13's
`AppEnvironment` holds the strong ref. Added an optional `degradationController`
parameter (default `nil`) to `init()` for backward-compatible callers.

Added `effectiveContentsScale` computed property that halves the contents scale
when `degradationController?.fidelity == .reduced` (ARCHITECTURE §12.4:
"half-res bitmaps: scaleBucket −1"). Replaced the hardcoded
`let contentsScale = screenScale * CGFloat(scaleBucket)` in both `syncBackground`
and `rasterize` with `effectiveContentsScale`.

Replaced the two hardcoded `.editorPreview(stage: .normal)` calls with
`.editorPreview(stage: degradationController?.stage ?? .normal)` so the live
ladder stage flows through to the drawers.

Both `MKLayerTreeController` and `MKDegradationController` are `@MainActor`,
so direct property access across the two types is safe without `await`.

### T-B: Real os_proc_available_memory() sampling (MemoryPressureMonitor.swift)

Added `#if os(iOS) / import Darwin.os.proc / #endif` conditional import at the
top of the file (before the enum declarations).

Replaced the placeholder `return 0` stub with a real implementation:
on iOS it calls `os_proc_available_memory()` (available via Darwin since iOS 13)
and computes `1 - available / total` against `ProcessInfo.processInfo.physicalMemory`.
On macOS it continues to return `0` so `swift test` on the host toolchain compiles
and passes without the iOS-only symbol.

The VERIFY-AT-IMPLEMENTATION note from the original P4 pass is now satisfied for
the iOS build path.

### Not captured this session: MKPathTextTests and MKTextEngineTests

Five bounded `swift test --filter <Target>` attempts (3× MKPathTextTests, 2×
MKTextEngineTests), each preceded by the standard `pkill -9 -f
"swift-test|swift-build|swiftpm-testing-helper"; sleep 1` hygiene and run
strictly sequentially, never completed a full green run in this session —
every attempt started correctly (build succeeded, the suite began, a handful
to a few dozen non-perf tests passed), then stalled indefinitely before
reaching `relayoutBudget`/`fullReshapeAndRelayoutBudget` (MKPathTextTests) or
before completing any test at all (MKTextEngineTests, 0/N both attempts).

Diagnosed with `sample <pid>` against the stalled `swiftpm-testing-helper`
process (per `docs/HANDOFF-ORCHESTRATOR.md`'s own "Ops lessons" playbook):
every worker thread, including the main thread, was parked in
`mach_msg2_trap` — a live IPC wait, not a spin — for the full sampling
window, with zero CPU consumed. This matches the handoff doc's documented
"Full-package `swift test` can wedge the host's fontd" phenomenon, observed
here per-target rather than only full-package, on both of this package's
heaviest CoreText/Arabic-shaping-consuming test targets specifically. `ps`/
`top` during the stalls repeatedly showed a concurrent, unrelated sibling
session's iOS Simulator process (`BADAN.app` and its `xctest` driver) at
80–97% CPU — consistent with this being contention from another concurrent
agent session on the same shared host (per this session's own briefing:
"this machine is running multiple other agent sessions concurrently right
now"), not a regression introduced by this pass. Retrying after the ambient
load average dropped (from ~50 down to single digits over the session) still
reproduced the same stall pattern at least once for each target, so this is
not purely a function of instantaneous load average either — the exact
trigger (this host's `fontd`/CoreText state vs. `swift-testing`'s
default concurrent test execution for these two font-heavy targets) was not
pinned down further, as doing so would mean building new diagnostic
infrastructure, which is explicitly out of scope for this pass.

**Why this doesn't block the pass.** The edits to both files
(`MakhtootKit/Tests/MKPathTextTests/PerfTests.swift` and
`MakhtootKit/Tests/MKTextEngineTests/ShapingServiceTests.swift`) are
comment-only — confirmed with `git diff`, which shows exclusively added `//`
lines in both files, zero `#expect`, budget-constant, or algorithm lines
touched. A doc-comment-only change cannot alter runtime behavior, so the
inability to capture a fresh PASS/FAIL this session carries no regression
risk; the previously-established budgets and behavior in these two files are
unchanged from before this pass. Re-running `swift test --filter
MKPathTextTests` and `swift test --filter MKTextEngineTests` once the host
is quieter (or once no sibling session is mid-build) is the natural
follow-up, but is an ops/environment task, not a code task.
