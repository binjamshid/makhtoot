## ADRs

### WS02-A1: `scene.json` envelope + migration policy

**Decision.** `scene.json` is `{"schemaVersion": Int, "scene": MKScene}`
(`MKSceneEnvelope`, `Schema/SceneCodec.swift`). `MKSceneCodec.decode` reads
`schemaVersion` from the raw JSON object BEFORE attempting any typed
decode: `schemaVersion > MKSceneSchema.currentVersion` throws
`MKModelError.schemaTooNew` immediately (Arabic message "هذا المشروع
أُنشئ بإصدار أحدث من مخطوط", exact string from packet task 6);
`schemaVersion < currentVersion` runs the `MKSceneMigratorRegistry` chain
(`v(n) → v(n+1)` pure JSON-object transforms) before typed decode;
`schemaVersion == currentVersion` decodes directly. v1 ships one migrator,
`MKIdentityMigrator` (v1→v1, no-op), registered in
`MKSceneMigratorRegistry.standard` — proves the dispatch path is real and
tested (`SceneSchemaTests.migratorRegistryDispatchesIdentityMigrationForCurrentVersion`,
`migrationPathMissingThrowsForAnUnregisteredOlderVersion`) before any real
migration is ever needed.

**`MKNode` Codable shape — a deliberate deviation from ARCHITECTURE.md
§13.4's illustrative schema.** The architecture doc's JSON Schema flattens
each node's payload keys alongside `"kind"` at the top level (e.g.
`{"kind":"group","base":{...},"children":[...]}`). This implementation
nests the payload under its own key instead: `{"kind":"group","payload":{...}}`
(`MKNode.swift`'s `Codable` extension). Reasons, in order of weight: (1)
Swift's `Codable` has no supported way to splice one `Encodable`'s keys
into an enclosing keyed container without a hand-written `CodingKeys` +
manual field-by-field encode/decode PER node payload type (~7× the surface
area of the nested form, for zero behavioral difference); (2) the SAME
§13.4 schema already uses the nested `{"kind":…, "<kind>":{…}}` shape for
`arrangedChild` and `ligatureGroup.state` — so nesting is consistent with
half of the schema's own two conventions, not a third novel approach; (3)
no downstream packet's stated accept criteria depend on the literal
flattened key layout — every consumer (WS-04..WS-08) reads `scene.json`
through `MKSceneCodec`/typed `MKScene`, never hand-parsed JSON. Flagged
here explicitly since it is a schema-shape choice a future workstream might
reasonably expect to match the architecture doc verbatim.

**Path-data encodings — two distinct types, not one.** Packet task 4's
prose only names `MKBezierPathData` for `MKGlyphNode.outline`, but
ARCHITECTURE §3.6 and the §13.4 schema define two non-interchangeable
encodings: a flat op-code command stream (`MKPathData`, schema's `pathData`
def — used for glyph/ligature outlines and `MKShapeGeometry.path`) and an
anchor+control-point curve (`MKBezierPathData`, schema's `bezierPath` def —
used for `MKPathTextNode.path` and `MKSourceTextBackup.pathData`). Both are
implemented, in `MKBezierPathData.swift` (no separate `MKPathData.swift`
file was added — consolidated into the one file the packet's deliverable
list already names, since the two types are the same "path encoding"
concern and share no other natural home).

### WS02-A2: journal format & recovery semantics

**Decision.** `journal.mkj` lives at the `.makhtoot` package root (never
under `backups/`, per D-223) as JSON Lines, one command per line. Each
command's **forward** form is journaled (never inverses, §14.4). Line
schema deviates from ARCHITECTURE §14.4's illustrative example in one
respect: the command is stored as a JSON **string** field (`cmdJSON`)
rather than a nested JSON object (`cmd`). Reason: `crc32` must be
verifiable by re-hashing the EXACT bytes originally hashed. Hashing a
nested JSON object requires re-serializing it after `JSONSerialization`
round-trips it through an untyped `[String: Any]`, which has no ordering
guarantee — a spurious CRC mismatch on every single line was the actual
first-draft behavior before this fix was applied (caught immediately by
`CommandJournalCrashRecoveryTests`, before it ever reached a fixture). A
JSON *string* field's bytes are unambiguous to re-hash. `MKCommandCoder`
(`Undo/MKCommandCoder.swift`) is the closed-catalog `{"kind","payload"}`
(de)serializer for `any MKCommand`, mirroring `MKNode`'s pattern.

**`AutosaveController`/`CommandJournal` split.** `AutosaveController`
(actor) owns the ≤2 s debounce (`MKDebouncer`, cancel-and-restart on every
mutation) and orchestrates the INV-7 save order (assets → `scene.json` →
`manifest.json` → journal-truncate, `flushNow`). D-223's stage-3/critical
path is a SEPARATE entry point, `criticalJournalFlush(command:baseRev:)`,
which calls only `CommandJournal.append` — no scene re-encode, no manifest
write, verified directly by
`AutosaveControllerTests.criticalFlushWritesOnlyTheJournalNeverSceneOrManifest`
(byte-identical `scene.json`/`manifest.json` `mtime` before/after) and by
`MakhtootDocumentTests.saveNowCriticalRoutesToJournalOnlyNeverFullScene`.
**Routing D-223 correctly is the CALLER's responsibility**
(`MakhtootDocument.saveNow(reason:)` branches on `MKSaveReason
.memoryPressureCritical` before ever calling into `AutosaveController`) —
`AutosaveController.flushNow` itself has no special-case for
`.memoryPressureCritical` and would happily do a full re-encode if a
caller mis-routed it there. This is called out because WS-07 (the actual
memory-pressure-ladder driver) MUST route stage-3 events through
`MakhtootDocument.saveNow(reason: .memoryPressureCritical)`, not directly
into `AutosaveController.flushNow`.

**Crash recovery** (`CrashRecovery.swift`) replays the valid journal
prefix onto the last-saved scene, verifying BOTH per-line CRC32
(`CommandJournal.readValidRecords`) AND the §14.5 `baseRev` chain (each
record's `baseRev` must equal `MKSceneRevision.hash` of the scene *after*
replaying every prior record) — stops at the first mismatch either way,
writes a `backups/rescue-<ts>.scene.json` snapshot of whatever was
recovered, and preserves any structurally-damaged tail as
`journal.mkj.damaged-<ts>` (never silently discarded). Durability gate
evidence: `crashRecoveryReplaysAllTenMutations20Of20Iterations` runs the
full "apply 10 commands → crash before flush → reopen → replay" cycle 20
times, asserting exactly 10 replayed commands and the correct final state
every iteration.

### WS02-A3: content-addressed asset store with orphan grace cycle

**Decision.** `MKAssetStore` (actor, `AssetStore.swift`) stores
`assets/sha256-<hex>.<ext>`, deduping on digest (`storeAsset` is a no-op
write if the digest's file already exists). `sweepOrphans(referencedBy:)`
implements the "one save cycle of grace" (task 8): on every sweep, files
already in `backups/orphans/` from the PRIOR sweep are deleted first
(their one grace cycle is over), THEN currently-unreferenced `assets/`
files are moved into `backups/orphans/`. This gives an asset exactly one
full save cycle of survival after its last referencing node is removed —
long enough for an in-flight undo to still resolve it via `assetData(for:)`
(the file only truly leaves `assets/` after the FIRST sweep, and only
truly leaves disk after the SECOND).

**Locally-implemented support utilities, not `MKFoundation` additions.**
FILE_MAP.md §5 sketches `FileLocations.swift`/`ContentHash.swift`/
`Debouncer.swift` as living in `MKFoundation` with an "owner: WS-02" tag.
This run's scope fence is explicit: "you own the MKModel and MKPersistence
targets... ONLY... Do NOT touch... other module targets" — `MKFoundation`
is WS-01's target. Per FOUNDATION.md's own supremacy rule and the same
precedent WS-01 logged for its own FILE_MAP granularity conflicts, this
packet's scope fence governs over FILE_MAP's file-placement sketch:
`MKAtomicIO`, `MKContentHash` (SHA-256 via `CryptoKit`, a system framework
— zero third-party deps preserved), `MKSceneRevision` (FNV-1a scene-hash,
NOT `Hasher` — `Hasher` is randomly reseeded per process, unusable for a
hash compared across a save and a later crash-recovery replay in a
DIFFERENT process), `MKCRC32`, `MKDebouncer`, and `MKFileLocations` are all
implemented privately inside `MKPersistence/Internal/PersistenceSupport.swift`
instead, `internal` (not `public`) since `MKPersistence` is their only
consumer.

### WS02-A5: SwiftData `@Model` classes are not `Sendable` — DTO layer added

**Finding, not a pre-existing decision.** `MetadataStore` is declared
`@ModelActor` (SwiftData's actor-isolation macro for a private
`ModelContext`). The first draft had every public method return the raw
`@Model` classes (`MKProjectRecord`, etc.) directly. `swift build` under
Swift 6 strict concurrency REJECTED this immediately: `PersistentModel`
classes are context-bound mutable reference types and do not conform to
`Sendable`, so returning one across the actor boundary is a real
concurrency-safety violation the compiler caught, not a false positive.
Fixed by adding `Metadata/MetadataSummaries.swift`: plain `Sendable`
struct snapshots (`MKProjectSummary`, `MKFolderSummary`, `MKExportSummary`)
that every PUBLIC `MetadataStore` method returns instead; only code running
INSIDE the actor (private helpers like `fetchProjectRecord`) ever touches a
live `@Model` instance. Task 20's "builds under Swift 6 strict concurrency
with no warnings" gate would have been unreachable without this — logged
because any future workstream adding a new `MetadataStore` method should
follow the same pattern (fetch `@Model`, map to a summary struct before
returning) rather than reintroducing the violation.

## Fix 1 — `MKUngroupCommand` transform-composition bug (BUG, fixed)

**Root cause (confirmed by reading the shipped source, matching WS-06's
report exactly):** `MKUngroupCommand.apply` spliced `g.children` back to
top level with each child's `core.transform` untouched. A child's stored
transform is LOCAL to the group's frame; `MKScene.reparenting` creates
groups with an identity transform, so local == world only until the group
itself is moved/rotated/scaled — after which ungroup silently snapped
children back to their pre-group-transform positions.

**Fix (`MKPersistence/Undo/Commands.swift`):** before splicing, each
child's transform is composed with the group's own:
`core.transform = core.transform.concatenating(groupTransform)` — the same
math as `MKCanvas`'s `MKGroupTransform.worldTransform(childLocal:groupTransform:)`,
inlined rather than imported because the dependency edge runs
`MKCanvas → MKPersistence`, never the reverse. Inverse semantics unchanged
(`MKRestoreTopLevelNodesCommand` snapshot — still exact). Carries the
documented `MKTransform2D` shear-free limitation (exact whenever the
group's scale is uniform or rotation is zero — every transform v1
produces).

**Regression test:** `CommandPropertyTests
.ungroupAfterMovingAndRotatingTheGroupPreservesChildWorldTransforms` —
group two nodes (one with a non-trivial pre-existing transform, so real
composition is exercised, not translation passthrough) → move AND rotate
the group (translation + π/4) → ungroup → assert each child's resulting
affine matrix equals `local ∘ groupTransform` to 1e-9 per component, AND
the recorded inverse still restores the exact pre-ungroup tree.

## Fix 2 — journal-invisible canvas commands (GAP, fixed via option (a))

**Root cause:** `MKCommandCoder` is a closed switch over the WS-02
catalog; WS-06's four local `MKCommand` conformers threw
`unknownCommandType` on `CommandJournal.append` (swallowed by
`MakhtootDocument.apply`'s `try?`), so multi-select drags, inspector
multi-edits, typing bursts, and canvas ungroups were silently exempt from
crash-recovery replay — a D-223/no-loss violation within the sub-2 s
journal durability window.

**Fix — option (a) as the coordinator preferred (canonical primitives, no
registration API):** three new commands in `Commands.swift`, semantics
(including coalescing-key formats) copied from the canvas conformers so
adoption is drop-in:

- `MKBatchTransformCommand(gestureID:newTransforms:)` — multi-node
  transform set, one undo entry per gesture (`"move-\(gestureID)"` key).
- `MKBatchCoreCommand(gestureID:newCores:label:)` — multi-node whole-core
  replace (`"core-\(gestureID)"` key, Arabic label passthrough).
- `MKTextEditCommand(nodeID:newNode:burstKey:)` — §14.1's previously-
  missing text-edit command; opaque node replace with a caller-supplied

All three are `Codable` and registered in `MKCommandCoder`
(`"batchTransform"`/`"batchCore"`/`"textEdit"` cases both directions).
The fixed `MKUngroupCommand` already had its `"ungroup"` coder case — its
replay now carries the corrected composition semantics automatically.

**Why (a) over (b) (registration API):** matches the coordinator's stated
preference; also `MKCommandCoder`'s closed switch is itself a deliberate
design (journal decode must be total over a KNOWN catalog to keep replay
deterministic — an open registration surface would make journal

**New tests (`Tests/MKPersistenceTests/CommandCoderTests.swift` + 2 in

- `everyCatalogCommandTypeHasACoderCase` — sweeps ALL 16 concrete command

- `journalReplayRecoversABatchTransformGesture` — end-to-end: baseline

# Session 3 — M4 wave-gate items: deterministic autosave test + WS-04 journal gap

Date: 2026-07-18. Trigger: coordinator message from the M4 wave gate.
Fences honored: `MKPersistence` sources/tests + `MakhtootKit/CONTRACTS.md`

## Item 1 — flaky mutation-storm test: fixed at the source (scheduler injection)

**Root cause, confirmed from the reproduction description:** the session-2
version of `mutationStormProducesAtMostTwoWritesIncludingTheEventualSettleFlush`
raced a fixed 300 ms post-storm `Task.sleep` against a 50 ms debounce
timer. Under full-package parallel load, the CPU-starved debounce task
could fail to run within the window → `settledCount == 0` → false failure.
Wall-clock windows are unfixable by widening (any width loses under enough
load); the fix removes the wall clock entirely.

**Production changes (behavior identical):**
- `Internal/PersistenceSupport.swift`: new INTERNAL seam
  `MKDelayScheduling { func delay(for: Duration) async throws }` +
  `MKTaskSleepScheduler` (a plain `Task.sleep` — byte-for-byte the
  behavior the debouncer had before). `MKDebouncer` now takes the
  scheduler at init (default: real sleep).
- `AutosaveController`: the PUBLIC init is unchanged and delegates to a
  new INTERNAL init that accepts a scheduler (reached only via
  `@testable` — no public API growth). Added
  `completedFlushCount` (counts every completed flush attempt — including
  hash-unchanged no-write passes and journal-only flushes; distinct from
  `fullSaveCount`, which still counts only real `scene.json` writes) and
  `public func awaitFlushes(atLeast:)` — suspends until the count reaches
  the target. Registration-race-free by construction: the counter is
  checked on the actor BEFORE suspending, so a flush that already
  completed satisfies the wait immediately. `recordFlushCompleted()` runs
  in a `defer` in both `flushNow` and `criticalJournalFlush` so a
  throwing flush can never leave a waiter hung.

**Test changes:**
- The storm test now injects `ManualDelayScheduler` (test-file actor
  conforming to the internal seam): `delay` suspends unconditionally
  until the test calls `advanceAll()`. Flow: 100 schedules →
  `waitForRegistrations(atLeast: 100)` (suspension-based, no wall clock)
  → assert `fullSaveCount == 0` (now a GUARANTEE — nothing can fire while
  every delay is held) → `advanceAll()` (99 cancelled tasks exit via
  their cancellation check; the one live task flushes) →
  `awaitFlushes(atLeast: 1)` → assert `fullSaveCount == 1` (strengthened
  from the old `>= 1 && <= 2` — exactly one settle write is now provably
  the only possible outcome). Zero timing dependency in either direction;
  runs in ~30 ms.
- New `awaitFlushesReturnsImmediatelyWhenTargetAlreadyReached` guards the
  registration-race property itself.

# Session 4 — Run-3: fixing the long-deferred D-115 host-load-flaky perf
gates at the source

Date: 2026-07-21. Trigger: Run-3 task, "the D-115 perf-budget tests ...
pass comfortably in isolation ... but intermittently blow their
wall-clock budgets under full-package parallel CPU contention." Fences
honored: `MakhtootKit/Tests/**` only, no `Sources` changes, this log only.

## Background

`MakhtootDocumentTests.open100NodeFixtureCompletesUnderOneSecond` /
`.open5000NodeFixtureCompletesUnderThreeSeconds` have been a recurring
false-red since Session 2 of this log (the "D-115 perf gates" evidence
block above) — every one of WS-06, WS-07, WS-08, WS-09, WS-10, and
WS-16-cursive's impl logs independently hit the exact same failure under
full-package `swift test`/`xcodebuild test` (many suites' tests scheduled
in parallel), confirmed it passed in isolation, and deferred it as
out-of-fence rather than fix it (it belongs to `MKPersistence`, this
workstream). WS-10's log has the clearest repro numbers:
`open100NodeFixtureCompletesUnderOneSecond` measured 0.088 s in isolation
against its 1 s budget — an ~11× margin — yet still failed under the
960-test/157-suite full-package run.

## Approach chosen

Widening the budgets was rejected outright — the numbers ARE the D-115
gate; loosening them would hide a genuinely slow implementation instead of
catching one. Instead, fixed the two failure modes separately, keeping
the budget numbers byte-for-byte unchanged:

1. **Self-inflicted contention.** Moved the two perf tests out of the
   general `MakhtootDocumentTests` suite into a new, dedicated
   `MakhtootDocumentPerfGateTests` suite marked `@Suite(..., .serialized)`
   — its own two heavy-I/O tests can no longer race each other for CPU.
2. **Contention from the rest of the package.** `.serialized` cannot stop
   sibling suites elsewhere in the package from consuming CPU at the same
   wall-clock moment, so added a small `measureUnderD115Budget` helper:
   measures with `ContinuousClock` exactly as before; if the first attempt
   misses budget, sleeps 200 ms (letting whatever transient contention
   caused the miss settle) and tries exactly once more; only a second miss
   fails the test. A momentary scheduler stall is exonerated by a clean
   retry; a truly slow implementation fails both attempts and still
   reports red, deterministically — the accept criterion the coordinator
   set (loosen the gate = no; make it not flake = yes).

**Live-discovered second instance.** While verifying the fix with
`swift test --filter MKPersistenceTests`, a previously-undocumented sibling
D-115 test flaked in the same run:
`AutosaveControllerTests.incrementalFlushOf100NodeSceneCompletesUnder100Milliseconds`
recorded `elapsed → 0.184713416 seconds` against its `.milliseconds(100)`
budget — same root cause (parallel contention starving a tight wall-clock
assertion), never previously flagged in any impl log, caught only because
this session was actively re-running the target suite under contention.
Per the task's instruction to search for and treat other tests sharing
the pattern, applied the identical fix: extracted the test into a new
`.serialized` `AutosaveControllerPerfGateTests` suite with the same
retry-once-after-settle helper (duplicated locally — no shared test-only
helper target exists in this package to put it in once). Each retry
attempt builds a brand-new `DocumentPackage`/`AutosaveController` via
`makeAutosaveTestEnvironment()` rather than reusing the first attempt's,
because a second `flushNow` on the SAME controller with an unchanged
scene hits `AutosaveController`'s hash-unchanged skip fast path
(`unchangedSceneSkipsARedundantWrite` covers that behavior) — reusing the
environment across attempts would have quietly timed the wrong code path
on retry. This is a different fix shape from Session 3's mutation-storm
fix (scheduler injection, wall clock removed entirely) because that test
had an unfixable-by-widening RACE (fixed sleep vs. debounce timer); this
test has no race — it is a single direct timing of real synchronous work,
so retry-on-miss is the correct fit, not scheduler injection.
