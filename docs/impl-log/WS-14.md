## ADRs

### WS-14-A1: self-contained serialization (inline paths + assetID) vs referenced assets

**Decision.** `MKAssetInstantiator.place(asset:)` returns a plain
`.shape(MKShapeNode(geometry: .path(MKPathData)))` node with the ENTIRE
asset geometry inlined via `MKAssetGeometry.toPathData()` — the same
`MKPathData` type and rendering path (`MKRender.ShapeDrawer`'s `.path`
case) every other shape node already uses. This makes self-containment
literal and total: a placed asset's node carries ZERO reference back to
`MKAssets` — no `assetID` string anywhere in `scene.json` for that node —
so "a `.makhtoot` file must render on a device/app-version lacking that
asset id" (packet task 3) is true by construction, not by a fallback path
that has to be separately tested.

**The packet's "assetID provenance attribute for future dedup/re-link"
half of task 3 is NOT applied to the node itself — documented gap, not a
silent omission.** The shipped `MKModel` schema (verified by reading
`Sources/MKModel/MKNode.swift`) has no generic metadata slot suitable for
this: `MKNodeCore.name` is already spoken for (`= nameAr`, the SAME task's
own requirement), and `MKShapeGeometry.asset(MKAssetRef)` is a different,
unsuitable case — `MKAssetRef` is a content-addressed digest+ext into
`MKPersistence`'s persisted `assets/` store, and `MKRender.ShapeDrawer`'s
`.asset` case is a documented no-op today (records a `.missingAsset`
substitution, draws nothing, pending a future `MKAssetVectorProgram`) — so
using it would make every placed asset invisible until that lands, the
opposite of self-containment. This run's fence is `MKAssets` sources only
(no `MKModel` edit permitted), so the clean fix — one additive field — is
out of scope this session. Proposed, ready-to-apply addition for whoever
next has `MKModel` in their fence (mirrors the WS02-A7/WS-06↔WS-07
precedent of a documented, ready-to-apply out-of-fence diff):

```swift
// MKModel/MKNode.swift, MKNodeCore:
public var sourceAssetID: String?   // Codable, defaults nil, additive
```

Until that lands, `MKPlacementRecord` (returned alongside every placed
node by `MKAssetInstantiator`/`MKPatternInstantiator`) and
`MKPremiumContentLedger` (WS-14-A2/T13) carry assetID bookkeeping at the
call site — real, tested, and exactly the seam a future document-session
integration (WS-02/WS-13) would drive.

**Pattern backgrounds hit an analogous, separately-documented gap**: the
packet's task 3/8 asks for pattern backgrounds to become "a `.background`
node with pattern fill," but `MKBackgroundContent` (verified in
`MKNode.swift`) has exactly two cases — `.solid`/`.image` — no pattern
case. `MKPatternInstantiator.placeBackground` realizes a pattern as a
`.group` of tiled, individually-inlined `.shape(.path(...))` nodes instead
— vector, fully self-contained, drawn by the already-shipped renderer with
zero new `MKRender` work, at the documented cost of a flatter SVG-export
shape later (no `<pattern>`/`<use>` semantics needed — every tile
serializes as its own ordinary `<path>`, simpler than the packet's own
framing, not a defect).

### WS-14-A2: pattern backgrounds premium per Q34 derivation

**Decision.** Every `.patternBackgrounds` asset (8 shipped) has
`isPremium == true`, unconditionally — cites **D-215** (`DECISIONS_LOG.md`,
Run-1 self-review amendment, dated 2026-07-17): "Pattern
backgrounds (and all non-solid background fills) are premium content. Free
tier backgrounds = solid colors only, exactly per Q34." Enforced
structurally (every `MKPatternTileGenerator` descriptor is constructed with
`isPremium: true`, no per-asset override point exists) and verified by
`MKPatternBackgroundTests.everyLibraryPatternBackgroundIsPremium`/
`AssetProvenanceAudit`. Gating integration: `MKAssetBrowserModel.select(_:)`
returns `.premiumRequired(capability: .premiumAssets, ...)` for a free
entitlement attempting to place any pattern —
`MKPatternBackgroundTests.freeEntitlementBlocksPatternPlacementWithPremiumRequiredOutcome`.

### WS-14-A3: original-authorship sourcing posture + forbidden sources

**Decision.** Every v1 asset's provenance record is `MKAssetOrigin
.originalWork` — no `derivedVerified` asset ships. `Resources/
ASSET_SOURCING_RULES.md` (this module's resource, checked in) is the full
written policy: default posture (original authorship; regular/star-polygon
CONSTRUCTIONS aren't copyrightable, the specific authored path data is),
derivation conditions (never used in v1, written down for when it might
be), the forbidden-source list (clip-art aggregators, stock marketplaces,
competitor asset dumps, AI-traced images, font-glyph decorations, Uthmani/
KFGQPC assets), the font-glyph-avoidance rule (T7), the no-Qur'anic-content
rule (§2 OUT), and the provenance-completeness rule that
`AssetProvenanceAudit` mechanically enforces.
`MKAssetProvenanceLibrary.standard(for:)` DERIVES one provenance record per
descriptor directly from `MKAssetLibrary.standard.all` (never a
hand-maintained parallel list that could drift or silently miss an asset)
— this is what makes "every manifest asset has provenance" true by
construction.

### WS-14-A4: runtime thumbnails vs checked-in art

**Decision.** `MKAssetThumbnailRenderer` is a small internal CG rasterizer
(actor-owned LRU cache, no disk-checked-in PNGs) — per the packet's own
framing of this as the preferred choice ("to avoid stale checked-in art").
No `MKRender` dependency (packet §3: "no direct dependency... prefer
reuse" is the alternative, not the default) — `MKAssets`'s only declared
edge beyond `MKFoundation`/`MKModel` stays exactly what FOUNDATION §2
locks it to. Fill rule is plain CG nonzero winding, matching
`MKRender.StylePainting.paint` exactly, so a thumbnail and the real canvas
render of the same asset always agree — verified directly (crescent hole
pixel-sampling, frame hollow-center pixel-sampling).

## Deviations / judgment calls (each also documented at its own call site)

1. **Fill rule realized via winding-direction discipline, not a stored
   even-odd flag consulted at render time** — `MKModel`/`MKRender` have no
   fill-rule field anywhere; `MKRender.StylePainting.paint` always calls
   plain `ctx.fillPath()` (nonzero). Every "hole" asset (crescent, rosette
   rings, frame borders, mandorla) is authored with the outer subpath and
   inner/hole subpath wound in OPPOSITE directions so nonzero fill alone
   produces the correct subtraction. `MKAssetFillRule`/
   `MKAssetStyleableRegion.fillRule` are still recorded (Codable, matching
   task 1's literal field list) as documentation/intent for a future
   consumer, not consulted by `toPathData()` — see `MKAssetGeometry.swift`.
2. **`AssetProvenanceAudit` implemented as a `@Suite` inside `MKAssetsTests`,
   not a separate SPM test target** — this codebase's established grain is
   one test target per module (`Package.swift`'s own precedent, every
   other module). The literal audit LOGIC (`AssetProvenanceAudit.run`) is
   a standalone, public, callable-from-anywhere type — the "target" the
   packet names is realized as a suite + a reusable audit function, not a
   separate product.
3. **`MKAssetSearchNormalizer` duplicates `MKPersistence.SearchNormalizer`'s
   logic** rather than importing it — FOUNDATION §2 locks `MKAssets` to
   `MKModel` only (no `MKPersistence` edge), and this run's fence forbids
   adding one. Same "duplicate a small shared utility across fenced
   modules" pattern this codebase already established for
   `MKFixtureLocator` (WS-02).
4. **`MKAssets` depends on `MKFoundation` in addition to `MKModel`** —
   `MKModel` does not `@_exported import MKFoundation` (verified
   empirically, same finding WS-06/WS-07 logged for their own targets), and
   this module's public API spells `MKNodeID` (`MKPlacementRecord`) and
   `MKEntitlementProviding`/`MKPremiumCapability`
   (`MKAssetBrowserModel`) directly. Logged in `Package.swift`'s own
   comment at the edit site.

## Real bugs found and fixed during this session

1. **`#expect(_:_:)` (Swift Testing) rejects a bare `String` variable as
   its second (comment) argument** — several tests passed
   `descriptor.assetID` directly; fixed by wrapping in a string
   interpolation literal (`"\(descriptor.assetID)"`). `Comment` conforms to
   `ExpressibleByStringLiteral`, not to a generic `String`-accepting
   overload.
2. **`collection.allSatisfy(\.keyPath)` inside `#expect(...)` fails to
   compile** ("call is to 'rethrows' function, but argument function can
   throw") under the `#expect` macro's expansion — fixed by using an
   explicit closure (`.allSatisfy { $0.keyPath }`) instead of a bare key
   path at every call site.
3. **`#filePath` as a DEFAULT PARAMETER VALUE resolves at the CALL SITE,
   not the declaration** — `MKAssetManifestGenerator.resourcesDirectory
   (sourceFile: String = #filePath)`'s first draft silently resolved to
   whichever TEST FILE called it, pointing at a nonexistent `Tests/
   Resources/` directory instead of `Sources/MKAssets/Resources/` for every
   caller outside the declaring file — caught by
   `MKAssetProvenanceTests.sourcingRulesDocumentExistsAndIsComplete`
   failing with exactly that wrong path in its error message. Fixed by
   using `#filePath` directly in the function BODY (no parameter
   indirection), which always captures the file it is lexically written in
   regardless of caller.
4. **SPM resource bundling is a build-time snapshot, not live** — the
   `regenerateManifestResources` test writes real files to `Sources/
   MKAssets/Resources/*.json` at TEST-RUN time, but `Bundle.module` (built
   from whatever was on disk at the LAST `swift build`) cannot see that
   write within the SAME test invocation. First full-suite run showed
   `bundled.count == 0` against `generated.count == 57`. Not a bug in the
   shipped code — an inherent property of the "test-time tool writes a
   real checked-in file" pattern this codebase already uses
   (`MKFixtureLocator`) — documented in `MKAssetManifestGenerator`'s own
   doc comment (regenerate, THEN rebuild, THEN the sync test passes) and
   resolved for this session by running the two-pass sequence once and
   committing the regenerated resource files.
5. **Test over-asserted "no substring 'font' anywhere in provenance
   notes"** — the auto-generated calligraphic-element notes correctly and
   deliberately AFFIRM "no font file... consulted" (exactly what §4 of
   `ASSET_SOURCING_RULES.md` asks records to state), which trivially
   contains the substring "font." Fixed the TEST (check for the specific
   FORBIDDEN phrasing — "derived from font"/"font glyph" — and require the
   affirmative "no font file" phrase to be present), not the production
   notes, which were correct as generated.
6. **REAL geometry bug, caught by the T11 visual QA pass itself**: the
   first-draft "pointed arch" construction (`ornament.mihrab-arch-outline`,
   `frame.arch`) used two cubic Bézier curves sharing an endpoint at the
   apex, with control points that did not deliberately diverge in tangent
   direction there — the two curves blended SMOOTHLY at the shared point,
   rendering a rounded dome/tombstone silhouette instead of a genuinely
   pointed Islamic arch. Fixed by replacing the ad hoc bezier blend with
   `MKAssetPathBuilder.pointedArchSegments` — a proper two-centered
   ("equilateral") arch construction: two circular arcs, each centered at
   the OPPOSITE spring point with radius equal to the full span, meeting at
   a point where their tangent directions genuinely differ (60° apart) —
   an unambiguous, unsmoothable corner. Verified visually in the
   regenerated contact sheets (both the ornament and frame versions now
   show a real point).
7. **REAL bug in the QA tooling itself, caught while reviewing the fix
   above**: `MKAssetContactSheetGenerator.generate` applied an UNNECESSARY
   manual "counter-flip" (`translateBy`+`scaleBy(1,-1)`) before drawing
   each already-correctly-oriented thumbnail `CGImage` into a cell,
   assuming `CGContext.draw(_:in:)` always renders a `CGImage` upside-down
   into a non-flipped context. Verified empirically (three standalone
   repro scripts, not assumed) that this assumption was FALSE:
   `draw(_:in:)` orients the image correctly with NO extra transform
   needed at these coordinates; the manual counter-flip was itself
   flipping an already-correct image, so every vertically-asymmetric asset
   (the arch, teardrop, semicircle, arrow's vertical component, …) rendered
   upside down IN THE CONTACT SHEET ONLY — never in the real rendering
   path (`MKAssetThumbnailRenderer.render` on its own was independently
   verified correct via the same repro-script method). This is what
   initially made the arch fix above LOOK like it hadn't worked during
   review; fixing the sheet generator (removing the manual flip entirely)
   resolved both the sheet's own row-order bug (item 8 below) and this
   per-cell orientation bug together. Also confirmed via this same review
   that `shape.triangle`/star points/`shape.teardrop` etc. were ALWAYS
   correctly oriented in the real pipeline — only this QA tool's own
   rendering was ever wrong.
8. **Contact-sheet row order was vertically flipped** (a second, related
   bug in the same file, caught first): `MKAssetContactSheetGenerator
   .generate`'s sheet `CGContext` has no base top-left flip (unlike
   `MKAssetThumbnailRenderer.makeContext`), so placing cell `row` at
   `y = row * cellSize` in that plain bottom-left-origin/y-up context put
   `descriptors[0]` at the BOTTOM of the displayed image and the LAST
   asset at the TOP — exactly backwards for a reviewer reading
   `descriptors` order top-to-bottom. Caught by inspecting an actual
   generated sheet (the single-item last row appeared at the top). Fixed
   by computing `cellOrigin.y = sheetHeight - (row + 1) * cellSize`.
9. **Simulator-vs-host timing budget**: `MKAssetThumbnailTests
   .firstRenderIsBelowBudgetAndSubsequentRendersAreCached`'s strict 16 ms
   packet budget passes comfortably on the macOS-host `swift test` loop but
   failed on the iOS Simulator (~25 ms observed even for the PURE,
   non-actor-mediated render call) — the Simulator's CG rasterization has
   no GPU acceleration and is not a representative device-class
   measurement (mirrors WS-07's own posture: real device-verified perf
   numbers are a P14 job, not asserted here as a hard device gate). Fixed
   by keeping the strict 16 ms budget on the host loop and using a
   documented, looser Simulator-only ceiling (`#if targetEnvironment
   (simulator)`) rather than silently deleting or globally loosening the
   check.
