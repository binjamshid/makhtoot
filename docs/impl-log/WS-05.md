## 4. Gaps and deferred items (detected by inspection)

1. **DEBUG harness not delivered (task 14).** No
   `PathTextHarnessView.swift` exists anywhere in the repo (`find` over
   the whole tree for `*PathTextHarness*` returned nothing). This means
   the packet's §7 "Manual Arabic checklist" gate
   (`T-ARABIC-M-PATH-*`) and the corresponding `TEST_MATRIX.md`
   `T-AR-46`…`T-AR-50` (MANUAL-ARABIC, `manual-visual`) entries have no
   screenshot evidence anywhere under `docs/impl-log/evidence/` (checked —
   only `docs/impl-log/evidence/WS-09/` exists, nothing for WS-05). The
   circle/arc/wave/star, inside/outside, and join-continuity-on-gentle-
   curves fixtures are all covered by automated numeric assertions instead
   (§3 above), which is a real but different evidence bar — it does not
   substitute for an actual visual walkthrough once a canvas exists,
   consistent with how WS-04's own log flagged the identical gap for its
   own harness.

2. **Per-glyph user-offset persistence gap (tasks 3/9/11).** Confirmed by
   reading `MKModel`'s shipped `MKPathTextNode` (via `PathTextCommands.swift`'s
   own doc comment and `README.md`'s "Known schema gap" section): it has
   no field to hold a per-cluster user-offset map. `PathLayoutEngine`
   fully supports user offsets at the engine level (tested,
   `userOffsetAppliesAndSurvivesRelayout`); `PathTextOffsetStore` is an
   explicitly session-scoped, non-Codable, non-`MKCommand`-integrated
   stand-in. The real fix (an additive `MKModel.MKPathTextNode` field) is
   outside this packet's fence (`MKPathText` sources/tests + `Package.swift`
   only) and is not done. Same status for `PathLayoutOptions`' engine-only
   fields (`alignment`, `baselineOffsetMagnitude`, `overflow`, `insideOut`,
   `closedPathGap`, `letterSpacingExtra`, join-continuity thresholds) —
   only the three-field `MKModel.MKPathLayoutOptions`
   (`startOffset`/`side`/`spacingMode`) persists.

3. **`PathPlacementProviding` conformer for `MKArrange` — this IS real,
   not a gap.** `MKPathTextPlacementProvider` (`PathPlacementProvider.swift`)
   is a genuine conformer, verified in this reconstruction by reading both
   the conformer and its test: `PathPlacementProviderTests` calls the real
   `MKArrange.ArrangeDeriver`/`RevertService`, not a fake. Flagging this
   explicitly since the task briefing for this reconstruction asked to
   check for exactly this — the answer is yes, it exists and is
   integration-tested against the real dependency.

4. **`MKRender`'s sampler-replacement seam is documented but NOT adopted.**
   `README.md`'s "Seam WS-07 should adopt" section is explicit that
   `MKRender/Drawers/PathTextDrawer.swift` still uses its own
   `MKPolylineArcLength` stand-in (fixed subdivision, no adaptive
   tolerance, no join mitigation, and — the README states — walks glyphs
   in raw per-run visual order rather than logical reading order, so it is
   only correct-looking for single-direction text). This packet did not
   touch `MKRender` (correctly out of fence) and no evidence was found
   that a later WS-07 session adopted the seam — `CONTRACTS.md`'s own
   WS-05 section repeats the same "not edited by this packet" caveat with
   no follow-up note attached. **This is why no `os_signpost`
   `pathRelayout` instrumentation fires from real `MKPathText` code in
   production today**: the `pathRelayout` signpost category already exists
   in `MKRender/RenderSignposts.swift` (WS-07's own module), but nothing
   currently calls `PathLayoutEngine.layout` from inside a signposted
   interval — `PerfTests`' wall-clock measurements are the only perf
   evidence that exists for this packet's own work.

5. **Marks and arrange-on-path — a documented, inherited gap, not
   introduced here.** `README.md`'s "Marks and arrange-on-path" section:
   a FREE/detached mark (no preceding base) on arranged path text keeps
   its flat straight-baseline position rather than following the path,
   because `ArrangeDeriver` never queries `PathPlacementProviding` for a
   mark's own glyph address. This is `ArrangeDeriver`-level (WS-04's
   module), outside this packet's fence.

6. **Two `PathLayoutEngineTests` §6 fixtures without a dedicated,
   individually-named test** (see §3 above): `Fixtures.shaddaStack`
   ("شَدَّةٌ" on a wave, stacked-mark-order-at-crest-and-trough) and the
   numerals-stay-sequential pair (`numeralsArabic`/`numeralsLatin`) are
   defined in `Fixtures.swift` but this reconstruction found no test
   asserting either by name. They may be exercised incidentally by other
   assertions but that was not verified.

7. **Codebase-memory MCP duties (packet §10: `manage_adr` for
   WS05-A1/A2/A3, implementation-log entries after tasks 4/8/12) —
   status unknown.** This reconstruction did not query the codebase-memory
   MCP graph (out of the stated fence for this task, and the tool's prior
   session state isn't recoverable by static file inspection). If those
   ADRs were never recorded due to the same termination that lost this
   log, they are also missing — flagged here so a future session knows to
   check/recreate them rather than assume they exist.
