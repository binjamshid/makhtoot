## §5 Deviations

**D1 — MKSyncPendingQueue is in-memory, not SwiftData-backed.**
The task packet requested a persisted pending queue. On the first engine start (T12), `enqueueAllPendingFromStore` rebuilds the queue from `listProjects()` (projects with `syncState == 0` or no `lastSyncedChangeTag`), so the queue is reconstructed on relaunch. Full SwiftData persistence for the queue would add no correctness benefit vs. the rebuild approach, and avoids a second SwiftData context on a hot code path.

**D2 — state serialization persisted via `.stateUpdate` events, not on `stopEngine`.**
The prior version of the controller tried to read `engine.state.serialization` directly in `stopEngine`. The actual CKSyncEngine API does not expose a `serialization` property on `CKSyncEngine.State`; instead it delivers `.stateUpdate` events with `stateSerialization` payloads. Fixed to persist on each `.stateUpdate` event.

**D3 — `CKContainer.fetchUserRecordID` bridged via `withCheckedContinuation`.**
The async variant `container.fetchUserRecordID()` does not exist in the current CloudKit SDK; only the completion-handler form is available. Bridged using `withCheckedContinuation`.

**D4 — Zone filter removed from `nextBatch`.**
The original code tried to check `context.options.zoneIDs` but this member does not exist on `CKSyncEngine.SendChangesOptions` in the current SDK. Since MKSync uses a single zone (`MakhtootProjects`), the filter is unnecessary and was removed.

**D5 — MKSyncTests target does NOT live-test CKSyncEngine.**
`CKSyncEngine` is a concrete class with no mockable protocol interface in the current SDK. All unit tests exercise pure functions and actors (decision engine, naming, error mapper, account state, pending queue, status publisher) directly. Two-device integration tests are documented as environment-deferred (T-sync-01..06 in `Docs/SyncManualTests.md`).

## §7 MKPersistence additions (cross-module seam)

### `MKTombstoneRecord` (new SwiftData model)

Added to `MetadataModels.swift`. Fields: `projectID: UUID` (unique), `deletedAt: Date`.
Added to `MKMetadataSchema.models` array so SwiftData includes the table in the unified schema.

### `MKProjectChange` (new public enum)

New file `Sources/MKPersistence/MKProjectChange.swift`:
- `.created(MKProjectSummary)` — yielded from `addProject`
- `.modified(MKProjectSummary)` — yielded from `move`, `markModified`
- `.renamed(UUID, newTitle: String)` — yielded from `rename`
- `.deleted(UUID)` — yielded from `deleteProject`

### `MetadataStore` additions

- `changesContinuation: AsyncStream<MKProjectChange>.Continuation?` — actor-stored; set when `changes` is first accessed
- `changes: AsyncStream<MKProjectChange>` — computed property using `AsyncStream.makeStream()`; single-consumer model
- `markModified(projectID:modifiedAt:contentHash:)` — stamps `modifiedAt`/`contentHash` fields on an `MKProjectRecord`, yields `.modified`
- `updateSyncState(projectID:syncState:lastSyncedChangeTag:)` — stamps `syncState`/`lastSyncedChangeTag`; does NOT yield (prevents upload loop)
- `tombstones() throws -> [UUID]` — lists all tombstone record IDs
- `recordTombstone(id:) throws` — upserts a tombstone; called by `deleteProject`
- `clearTombstone(id:) throws` — removes a tombstone; called after server confirms deletion

### Tombstone lifecycle

`deleteProject` → `recordTombstone` (creates tombstone) → MKSync uploads the DELETE → `sentRecordZoneChanges` → `clearTombstone` (removes tombstone). Net result when the server confirms: no orphan tombstone.

When MKSync applies a remote deletion: `deleteProject` (creates tombstone) then immediately `clearTombstone` (removes it) — the deletion came from the server, not from the device, so no upstream delete record is needed.
