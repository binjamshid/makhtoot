## ADRs

### WS-13-A1: Navigation architecture (Stack vs SplitView per size class) + route model

**Decision.** `MKRoute` (`Makhtoot/AppShell/Navigation/MKRoute.swift`) is a
five-case `Identifiable` enum exactly matching the packet's T3 spec:
`browser, editor(MKProjectID), settings, paywall(PaywallContext),
onboarding`. `AppNavigationModel` (`@Observable @MainActor`) owns a
`path: [MKRoute]` push stack, a `presentedSheet: MKRoute?`, a
`presentedFullScreenCover: MKRoute?`, and a `sidebarSelection` for the
regular-width idiom. `RootShellView` is the single owner of one
`AppNavigationModel` per window and switches container by
`horizontalSizeClass`:

- **Compact (iPhone / iPad narrow):** `NavigationStack(path:)` rooted at
  `ProjectBrowserView`; `.editor`/`.paywall`/`.settings`/`.onboarding`
  handled by `.navigationDestination(for: MKRoute.self)` when pushed, or
  by `.sheet(item:)` for settings/paywall specifically (matching the
  packet's "settings/paywall = sheets" rule).
- **Regular (iPad):** `NavigationSplitView` — sidebar lists "المشاريع" /
  "الإعدادات", detail switches on `sidebarSelection`; the editor still
  presents as a `.fullScreenCover(item:)` on both idioms when opened from
  a regular-width context (`AppNavigationModel.openEditor(_:isRegularWidth:)`
  branches push-vs-cover), matching the packet's per-idiom editor
  presentation rule.

**Verified manually** (see Verification evidence below): iPhone push
navigation to the editor with a working back/"تم" pair; iPad
`NavigationSplitView` with the sidebar correctly on the trailing-in-RTL
(visual right) side; iPad editor opens as a true full-screen cover (sidebar
disappears entirely, unlike the iPhone push).

**Alternative considered:** a single `NavigationStack` everywhere with a
manually-drawn sidebar-like leading panel for iPad. Rejected — packet T3
explicitly names `NavigationSplitView` as the iPad browser strategy, and
using the real system component gets correct RTL mirroring, resizing, and
collapse behavior for free instead of reimplementing it.

### WS-13-A2: Bootstrap ordering and what may block first paint

**Decision.** `AppContainer` (composition root, D-231) is constructed
synchronously in `MakhtootApp.init` via `@State private var container =
AppContainer()`. The packet's T2 full bootstrap sequence (font
registration kickoff, trial record ensure, entitlement resolver start,
sync controller, analytics init, all via `TaskGroup` with explicit
ordering) is **not implemented in this slice** — there is nothing real
behind any of those seams yet (no `MKFonts`, `MKStore`, `MKSync`,
`MKAnalytics` implementations exist; they're all Run-3-sibling work in
progress or not yet started). Writing a `TaskGroup` bootstrap scaffold
with only stub calls behind it would be dead ceremony with no way to
honestly verify T2's AC (a real trial record surviving a kill-mid-onboarding
test needs a real Keychain-backed trial controller, which doesn't exist).
`AppContainer.init` is `<1 ms` (in-memory struct/actor construction only),
so it trivially satisfies "must not block first paint" without needing
async structure yet. **Flagged for whichever slice lands WS-10's
`MKTrialController`: that is when T2's real bootstrap ordering (and its
kill-mid-onboarding AC) becomes buildable and testable.**

## ADRs

### WS-13-A5: real `ProjectLibraryProviding` conformer — lazy-bootstrap actor over `MetadataStore`/`DocumentPackage`, not `MakhtootDocument`

**Decision.** `Makhtoot/AppShell/Persistence/MKPersistenceProjectLibrary.swift`
(new file, new `Persistence` group under `AppShell`) is the real conformer
wired into `AppContainer.init`'s default parameter, replacing
`InMemoryProjectLibrary`. It is a plain `actor` (not `@MainActor`) wrapping
WS-02's `MetadataStore` (SwiftData index) plus direct `DocumentPackage`/
`LaunchReconciler` calls for on-disk `.makhtoot` package I/O.

Two sub-decisions:

1. **Lazy, memoized bootstrap instead of async `init`.** `init()` only
   resolves `Documents/Projects` and `Application Support/Makhtoot` URLs
   (cheap `FileManager` calls, no directory creation, no SwiftData
   `ModelContainer` open) — real I/O (`MetadataStore.makeContainer` +
   `LaunchReconciler.reconcile`, a full directory scan) happens on first
   protocol-method call, behind a memoized `Task<MetadataStore, Error>?`
   so concurrent early callers share one bootstrap. This extends WS-13-A2's
   "first frame must not await real subsystem startup" principle to the
   first REAL subsystem this shell has had to sequence — `AppContainer.init`
   stays synchronous and `<1 ms`; the actual store-open cost is paid
   inside the browser's own `.task`, which was already async.
2. **`DocumentPackage.create`/`.duplicateProject`, never `MakhtootDocument`,
   for project creation/duplication.** `MakhtootDocument` (`@MainActor`,
   owns undo stack + journal + `AutosaveController`) is the right API for
   a LIVE editing session, but nothing in this slice opens one — the
   editor is still `EditorPlaceholderView` (WS-06/07 haven't landed).
   Standing up a full `MakhtootDocument` for a document nothing will ever
   mutate this session would be dead weight and would force
   `MKPersistenceProjectLibrary` onto `@MainActor` for no reason. Browser
   CRUD talks to `DocumentPackage`/`MetadataStore` directly, exactly as
   T4's own locked rule already requires ("browser reads ONLY the metadata
   index, never scene.json") — this session extends that rule to writes
   as well, for the same reason. **Flagged for whichever slice lands the
   real editor: opening a project for editing must switch to
   `MakhtootDocument.open`, not keep reading/writing through this actor.**

**Verified:** 501 real `.makhtoot` packages (`manifest.json`/`scene.json`/
`assets/`/`backups/`) created via the running app on the iPhone 17
simulator, confirmed on disk via `xcrun simctl get_app_container` (see
Verification evidence below); a real `MKMetadata.store`
(+ `-wal`/`-shm`) SwiftData file at `Library/Application Support/Makhtoot/`.

### WS-13-A6: `ProjectLibraryProviding` extended, not replaced — folders/search/duplicate/export-history/refresh all additive

**Decision.** `Makhtoot/Stubs/ProjectLibraryProviding.swift` (the
EARLY-SLICE seam) is extended in place rather than superseded by a new
protocol: `fetchAll(folderID:)` (with a `fetchAll()` convenience overload
for source compatibility), `search(_:)`, `listFolders()`/`createFolder`/
`renameFolder`/`deleteFolder`, `move(_:toFolder:)`, `create(name:canvas:)`
(now canvas-size-aware for T8), `duplicate(_:)`, `exportHistory(_:)`, and
`refreshFromDisk()` (T14). `ProjectSummary` gained `folderID`, `canvasSize`,
`premiumContentPresent`, `isOrphaned`. `InMemoryProjectLibrary` is kept
(now implementing the full extended protocol) purely for `#Preview` bodies

### WS-13-A8: app-local `MKAppSignpost` vocabulary, not an addition to `MKFoundation.MKSignpost`

**Decision.** `Makhtoot/AppShell/Support/MKAppSignpost.swift` declares
`launch`/`browserScroll`/`editorOpen` as a NEW, app-local `OSSignposter`
enum rather than adding cases to `MKFoundation.MKSignpost` (WS-01's closed,
cross-module D-115 engine-budget vocabulary —
`manipulationFrame`/`typingEcho`/`documentOpen`/`autosave`/`export`).
Reason: this session's fence is `Makhtoot/` + `Makhtoot.xcodeproj` only;
`MKFoundation` sources are out of scope regardless of which packet is
running. `MKPersistence.MakhtootDocument.open` already emits its own
`MKSignpost.documentOpen` interval (WS-02) — `editorOpen` here measures a
DIFFERENT thing (shell routing latency: tap → route pushed/covered → first
frame), not document I/O, so there is no overlap/duplication even once a
real editor lands. `MKLaunchTimer` (same file) is a one-shot cold-launch
timer: `shared`'s lazy-static construction begins the interval; the

`MakhtootApp.body` (first evaluation), not `init()` — documented inline
since a naive read of "as early as possible" would reach for `init()` and
hit a compiler error.

## Real bugs found this session (the headline result)

Four are load-bearing; two are UI-reachability regressions this session's
own new toolbar chrome introduced and then caught+fixed within the same
session. All are backed by on-simulator, screenshot-level evidence — see
"Verification evidence" below for the specific reproduction transcripts.

### Bug 1 (CRITICAL, WS-01/WS-09 territory) — `SystemFontStubProvider` renders Arabic as garbled glyphs

`MKFoundation.SystemFontStubProvider.resolve(_:)` resolves via
`CTFontCreateUIFontForLanguage(.system, size, "ar")`. In this session's
iOS 26.5 simulator runtime, every Arabic `MKLiveTextNode` rendered through
this provider (`MKRender`'s default `fonts:` parameter, used by both
`MKShapingEngine` at shape time and `LiveTextDrawer` at draw time) came
out as non-Arabic-looking garbled glyphs — confirmed with a synthetic,
canvas-independent `MKSnapshotRenderer.render` call (bypassing
`MKCanvas`/`MKLayerTreeController`/CALayer entirely) that rendered "Hello"
correctly and "مرحبا" as garbage through the identical code path,
isolating the bug to Arabic-specific font resolution, not a rendering
pipeline defect. Requesting the SAME nominal font (`.SFArabic`) directly
by PostScript name via `CTFontCreateWithName` instead of the language-
tagged UI-font lookup renders correctly (verified with the same synthetic
scene).

**Workaround (this session, in-fence):** `Makhtoot/AppShell/Scenes/Editor/MKAppFontProvider.swift`
— a new `MKFontProviding` conformer using `CTFontCreateWithName(".SFArabic",
size, nil)`, passed to `MKLayerTreeController`/`HitTester` via their
already-injectable `fonts:` parameter (exactly the extensibility seam
`MakhtootKit/CONTRACTS.md` documents this protocol for). Not a package
edit — `MKFontProviding` is a public protocol precisely so a caller can
substitute a better conformer.

**Flagged for WS-01/WS-09:** fix `SystemFontStubProvider` itself, or
confirm this is simulator-only (no physical device was attached this
session to check — G-PERF/device-specific font behavior is explicitly
deferred per this run's own instructions). Every OTHER pre-WS-09 consumer
of the default `SystemFontStubProvider()` (WS-03/06/07's own test suites)
apparently never exercised real Arabic glyph rendering end-to-end, so this
bug was latent, not previously caught.

### Bug 2 (CRITICAL, WS-07 territory) — `MKLayerTreeController` never visually moves a committed transform-only change

`MKLayerTreeController.syncNode` (`MKRender/LayerTreeBuilder.swift`) only
updates a node's `CALayer.bounds`/`.position` from inside
`rasterize(_:into:)`, itself only invoked when `MKContentHash` differs
from the last-committed hash. `MKContentHash` deliberately EXCLUDES
`MKNodeCore.transform` (WS07-A4, `docs/impl-log/WS-07.md`: "transform/
opacity are layer properties applied around a cached bitmap" — correct
intent for the LIVE-GESTURE fast path). The bug: there is no OTHER code
path keeping `layer.position`/`.bounds` in sync with a COMMITTED
transform-only change (a real move/resize/rotate with no text/style
edit) — `sync(to:)` resets the transient delta to `.identity` and leaves
the layer at its stale pre-move position. Reproduced with zero ambiguity:
applying a real `MKBatchTransformCommand` through the exact same
`session.perform` funnel a drag gesture's `endGesture()` uses left the
rendered text visually stuck at its old position, while the selection
chrome (reading live `geometrySource`/`worldOBB` off the current scene,
not the stale layer) correctly showed the new position/rotation
immediately — proving the MODEL was right and only the LAYER was stale.
Forcing an unrelated `MKLayerTreeController.setVisibleRect` zoom-bucket
crossing (which explicitly calls `committedContentHash.removeAll()`
before a full re-`sync`) immediately snapped the text to the correct
position, confirming the exact mechanism.

**Practical impact if unfixed:** this would affect every REAL drag/
resize/rotate gesture too, not just this session's DEBUG-hook substitute
— a user would see a node visually "snap back" to its pre-drag position
the instant they lift their finger, even though the underlying document
correctly holds the new transform (confirmed via `scene.json` inspection
and via chrome). This is silent data-vs-render disagreement, exactly the
class of bug D-118's "canvas and export must never disagree" principle
exists to prevent, and would have been extremely visible/embarrassing in
any real interactive session.

**Workaround (this session, in-fence):** `EditorViewModel
.workAroundStaleLayerPositionBug()` — after every committed scene
mutation (inside the existing `sceneObservationTask` loop that already
drives chrome refresh), force a zoom-bucket crossing via the PUBLIC
`setVisibleRect` API and immediately revert to the real current zoom,
both synchronously inside the same MainActor turn (before Core Animation's
next commit/display cycle) so the cache busts and every node re-
rasterizes with no visible flicker. Costs one extra full-scene
rasterization pass per mutation — acceptable P4 correctness-over-
performance tradeoff, flagged for WS-07 to fix at the source (the real
fix: `syncNode` should update `layer.position`/`.bounds` from the current
`node.core.transform` unconditionally, independent of the content-hash-
gated `rasterize` call), which would let this workaround be deleted.

### Bug 3 (HIGH, this session's own code) — undo/redo toolbar buttons silently stale

The undo/redo buttons originally read `viewModel.session.canUndo`/
`.canRedo` directly — computed properties on `CanvasSession` (`@Observable`)
that forward to `document.undoStack.canUndo`/`.canRedo`, where
`MakhtootDocument`/`MKUndoStack` (`MKPersistence`) are plain, NON-
`@Observable` classes. The `@Observable` macro only instruments a type's
OWN stored properties — a computed property reading THROUGH a non-tracked
nested object establishes no Observation dependency edge, so SwiftUI never
reliably re-evaluates `.disabled(!canUndo)` after a mutation. Confirmed
on-simulator: after a real committed transform, the undo button's tap
produced no effect — not a rendering issue, `scene.json` on disk still
held the PRE-undo transform after the tap, proving the button's action
never fired (SwiftUI does not dispatch a disabled button's action).

**Fix (this session, own code, not a package bug):** genuinely tracked
STORED properties `EditorViewModel.canUndo`/`.canRedo`, refreshed by the
same `sceneObservationTask` loop plus immediately after `undo()`/`redo()`
calls themselves. The toolbar now reads these instead of
`session.canUndo`/`canRedo` directly.

### Bug 4 (MEDIUM, this session's own code, NOT fully resolved) — iPad persistent-column layers list only shows the last row

On iPad's persistent-column layout, `LayersPanelView`'s row list showed
only the background row — the Live Text node's row was missing — while
the IDENTICAL `LayersModel`/`LayersPanelView` through the iPhone sheet
presentation (a `NavigationStack`-bounded context) correctly showed both
rows. This isolates the bug to the iPad persistent-column `VStack`/
`ScrollView` height-propagation, not the underlying data/view logic
(confirmed by the sheet's correct rendering with the SAME `viewModel
.layers` instance). Attempted fix: unconditional
`.frame(maxHeight: .infinity)` on both panel columns and their containing
`VStack` (previously conditional on the SIBLING panel also being shown,
`nil` otherwise) — this did **not** resolve it on re-test. **Left as a
confirmed, documented open bug** rather than continuing indefinitely;
flagged for a follow-up session. Does not block core editing (iPhone's
sheet-based layers panel is fully correct; the iPad INSPECTOR column
toggle was not independently re-verified after this fix attempt either —
see Deferred remainder).

### Bug 5/6 (reachability, this session's own code, FIXED) — toolbar/tool-rail overflow silently drops buttons on iPhone

Two related UI-reachability bugs, both caught by on-simulator interaction,
both fixed this session:

- **Tool rail (bottom floating bar):** a plain `HStack` of 12 buttons + a
  divider does not fit iPhone portrait width; SwiftUI does not wrap or
  scroll a plain `HStack` automatically — the leading-most buttons
  (including "add text") were pushed off-screen and unreachable, with no
  visual indication anything was missing. **Fix:** wrapped in
  `ScrollView(.horizontal)` (and `.vertical` for the unused-but-available
  vertical axis), with an explicit `.frame(maxWidth:)`/`.frame(maxHeight:)`
  cap so the scroll container doesn't just hug its content and recreate
  the same overflow.
- **Top toolbar (`ToolbarItemGroup(placement: .primaryAction)`):** six
  buttons (layers, inspector, undo, redo, export, DEBUG menu) competed for
  the same compact-width toolbar area. Unlike the tool rail, a
  `ToolbarItemGroup` has NO scroll/overflow affordance for plain
  `Button`s at all (only a `Menu` collapses itself into a "…" glyph) — with
  all six present, "تراجع" (undo) became genuinely unreachable. **Fix:**
  moved the layers/inspector toggle buttons OUT of the top toolbar
  entirely (into the already-scrollable tool rail on compact width; iPad
  already had an equivalent `MKChip` pair for the persistent-column
  toggle), leaving 4 items (undo/redo/export/DEBUG) which fit and are
  individually tappable.

## ADRs

### WS13-A9: `MKCanvasRenderAdapter` — bridging WS-07's real render tree into WS-06's consumption seam

`Makhtoot/AppShell/Scenes/Editor/MKCanvasRenderAdapter.swift`. `MakhtootKit
/CONTRACTS.md`'s "WS-06 — consumption seam over WS-07's contract" note
promised wiring the real `MKLayerTreeController`/`HitTester` in would be
"a one-line substitution, not a redesign" once they landed; this adapter
is that substitution, implemented at the app-target composition-root level
(D-231) since neither package may import the other across this session's
fence. `worldOBB(for:in:)` deliberately does NOT reuse `HitTester
.worldGeometry(of:in:)` verbatim (a raw `CGAffineTransform` built by matrix
concatenation, which can accumulate shear once a non-uniform-scale child
is nested inside a rotated group) — it composes the same way
`InspectorModel.worldTransform(for:in:)` already does, via
`MKGroupTransform.worldTransform` on decomposed `MKTransform2D` values
(shear-free by construction, matching `MKOrientedRect`'s single-rotation-
angle shape), then builds the OBB from that transform +
`MKNodeLocalBounds.localBounds(of:)`. This keeps every consumer of
`session.geometrySource` self-consistent with the position/rotation math
`InspectorModel` already uses for the same node.

### WS13-A10: `EditorViewModel` owns the D-104 overlay lifecycle directly, not the `UIViewControllerRepresentable`'s Coordinator

Originally the overlay's presence was synced only from `CanvasHostView
.updateUIViewController`, on the assumption that SwiftUI re-invokes a
representable's update method whenever an `@Observable` property read
inside it changes (the same Observation integration `body` gets). This
assumption held for the NORMAL path (canvas double-tap → mode change →
SwiftUI-driven re-render) but broke for the DEBUG-hook path (a `Menu`
button action that doesn't touch any `@Observable` property a currently-
displayed `View.body` happens to be tracking) — the just-committed overlay
`UIView` was left stuck on screen, visibly overlapping the newly-correct
engine-rendered text. **Decision:** `session.mode` gets the same explicit
poll every other cross-boundary signal in this file uses (zoom scale,
memory stage) — a 100 ms cadence `startModePolling()` task, PLUS an
immediate synchronous call from `debugCommitActiveOverlay()` itself (since
the state change is already synchronous by the time that call returns).
Belt-and-suspenders: `CanvasHostView.updateUIViewController` still also
calls `syncOverlay()` (harmless, idempotent), for lower latency in the
common case.

### WS13-A11: DEBUG hooks substitute for pointer-drag gestures, the same way text-entry substitution was anticipated

This run's own gate instructions anticipated computer-use text-entry being
blocked (a documented limitation from WS-13 Session 1/2) and specified a
DEBUG-hook substitution with the substitution documented. This session
found the SAME tooling-limitation class extends to pointer DRAG gestures:
`left_click_drag` and manual `left_mouse_down`/`mouse_move`/`left_mouse_up`
sequences against the Simulator window both produced no visible move —
confirmed by direct A/B comparison (identical crops before/after several
drag attempts) and by `scene.json` inspection (position genuinely
unchanged on disk). Move/resize/rotate is therefore verified via
`EditorViewModel.debugApplyTestTransform()` — a DEBUG-only hook that
applies a real `MKBatchTransformCommand` (translate + 15° rotate + 1.4×
scale) through the SAME `session.perform` funnel `MoveGesture
.end()`/`HandleGestures.endResize()`/`.endRotate()` use at a real drag's
end, landing in the real undo stack/journal/autosave — not a bypass of the
gesture SYSTEM, a substitute for the POINTER INPUT that would normally
drive it. Documented here per the same "document the substitution" rule
the packet's own gate note anticipated for text entry.

### WS13-A12: DEBUG shaping harness + perf HUD land in `Makhtoot/App/Debug/`

`ShapingHarnessView.swift` (WS-03's own deferred deliverable — its impl
log explicitly names this path and defers it to "WS-13 territory") and
`PerfHUDView.swift` (WS-07's own deferred deliverable, same reasoning) are
both DEBUG-only screens this session builds. The harness drives
`MKShapingService` (the cached, `typingEcho`-signposted actor facade)
directly against free-typed input, showing line/glyph/run/cluster counts,
base direction, mark/ligature/joining-analysis counts, last-shape
duration, and cache hit/miss counters — reachable from Settings' `#if
DEBUG` section. The perf HUD polls a small `EditorPerfHUDDataSource`
adapter (`MKRenderPerfHUDDataSource` conformer) every 500 ms, showing last
manipulation-frame duration (from `debugMeasureManipulationFrames()`),
memory stage, and rasterization count — `bitmapCacheBytes` is honestly
reported as `0` since `MKLayerTreeController` does its own per-node
`layer.contents` dictionary caching rather than using WS-07's `BitmapCache`
actor (confirmed by inspection — no `BitmapCache` reference anywhere in
`LayerTreeBuilder.swift`), so there is no real byte-accounted cache to
report a number from.

## Bug 4 (iPad persistent-column layers list) — root-caused and closed

### Root cause (confirmed, same diagnosis Session 3 reached)

`Makhtoot/AppShell/Scenes/Editor/EditorScene.swift`'s `regularLayout`
originally gave each persistent-column panel (`LayersPanelView`/
`InspectorPanelView`) a conditional `.frame(maxHeight: showsOther ?
.infinity : nil)`. When only ONE column was visible, `maxHeight: nil` left
the panel's internal `ScrollView` unconstrained inside the containing
`VStack`, collapsing the `LazyVStack`'s available height to something too
small to lay out more than one row — reproducing exactly as Session 3
described it: the iPad persistent column showed only the background row,
while the IDENTICAL `LayersModel`/`LayersPanelView` instance, presented
through the iPhone sheet's `NavigationStack`-bounded context, correctly
showed every row.

### The fix (already present in the codebase — Session 3's own attempt)

Session 3 already changed both panels to an UNCONDITIONAL
`.frame(maxHeight: .infinity)` (always, not just when a sibling panel is
also showing) and documented this as the correct fix in
`EditorScene.swift`'s own inline comment — but that same session's "Bug 4"
writeup and "Deferred remainder" section called the bug CONFIRMED
UNRESOLVED after re-testing the fix.

### This session's finding: the fix IS effective — re-verified, not re-applied

A fresh `xcodebuild ... build` + `xcrun simctl install` + `launch` cycle
against the SAME iPad (A16) simulator instance Session 3 used, followed by
an extensive interactive reproduction attempt via computer-use, could
**not** reproduce Bug 4 in any of the following configurations:

- Layers column alone, 2 rows (text + background) — both rows rendered.
- Layers + Inspector columns simultaneously, 2–3 rows — layers rendered
  correctly, split-height with the inspector, both fully visible.
- Cold app launch (fresh `terminate`+`launch`), layers opened as the FIRST
  post-launch action — all rows rendered immediately, no stale/empty first
  paint.
- Incrementally growing the same project from 2 rows up to **28 rows**
  (each row added live while the panel was open, via repeated "add text"
  taps) — every row rendered at every count tested (2, 3, 4, 5, 7, 13, 18,
  23, 28), no row ever silently dropped, matching the iPhone sheet's
  behavior exactly.
- Toggling the layers column closed and reopened fresh at 28 rows —
  correct on every reopen.

Given the fix code is unchanged from what Session 3 itself shipped and
tested, and this session's re-test of the SAME code on the SAME simulator
instance consistently succeeds across a much wider matrix than Session 3
attempted, the most likely explanation is that Session 3's own re-test ran
against a stale build or an incompletely-reinstalled app binary — that
session's own log documents exactly this class of environment friction
elsewhere (Session 2's log: "the iPad's `uninstall` call appears to have
been the step that caused an earlier combined-command 2-minute timeout and

## Real bug found this session — `BezierPathModel.init(_:)` mints a fresh random anchor id on every call

Found via the E2E drive's own `debugDumpSceneJSON` data-level checkpoints
(not a screenshot): `path-after-anchor-drag.json`'s path segments were
byte-identical to `path-after-text-commit.json`'s — the anchor drag had
silently no-op'd. Root cause, confirmed by reading
`Sources/MKPathText/BezierPathModel.swift`'s `init(_ data: MKBezierPathData)`
directly: `MKBezierPathData`/`MKBezierSegment` carry no persisted anchor-id
field at all, so every `PathAnchor` this initializer builds gets a fresh,
random `MKPathAnchorID` (a UUID-backed id whose default init mints a new
UUID) — there is nothing for the initializer to preserve. Because
`MKPathTextInteractionAdapter`'s hit-test path (`hitTargets`/
`nearestHitTarget`) and its later mutation path (`moveAnchorCommand`, etc.)
each built their OWN separate `BezierPathModel(node.path)` from the current
scene, the two calls minted two completely different random ids for the
same physical anchor — `PathEditModel.moveAnchor`'s own "return the path
unchanged if the id isn't found" contract then made every mutation attempt
across two calls a silent, undetectable no-op.

**Fix (this session, adapter-level, not a `MKPathText` source edit — out of
this session's fence):** a per-`MKNodeID` stable-anchor-ID cache
(`anchorIDCache: [MKNodeID: [UUID]]`) inside
`MKPathTextInteractionAdapter`, resolved through a `stableModel(for:
nodeID:)` helper that overwrites `BezierPathModel(_:)`'s freshly-minted ids
with the cached array whenever the anchor count is unchanged, and
regenerates/clears the cache when `insertAnchorCommand`/
`deleteAnchorCommand` change the anchor count. Documented in full in the
