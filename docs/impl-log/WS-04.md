## ADRs

### WS04-A1: fidelity-fit algorithm for ligature decomposition (affine fit + stored offsets)

**Decision.** D-221's algorithm fits against OUTLINE bounds (ink), not
advance-box bounds, per ARCHITECTURE §7.5's literal text ("union bounds U
of provisional outlines; original ligature outline bounds L"). Implemented
as: natural pen walk via advances (spacing only) → per-constituent OWN
outline bounding box → two edge-alignment anchors (`anchorFirst` puts
constituent 0's own outline left edge exactly at `L.minX`; `anchorLast`
puts the last constituent's own outline right edge exactly at `L.maxX`) →
every constituent's fitted x is a LINEAR INTERPOLATION between those two
anchors, proportional to its natural (unfitted) pen position. This is
"a single affine fit" in the sense the packet requires (one degree of
freedom — the interpolation parameter — maps natural pen space to fitted
pen space, pinned exactly at both ends) without requiring a literal
uniform-scale-then-shift derivation to hit the edges exactly.

**Why the first version was wrong (caught by the fidelity test).** The
first implementation fit against `composed.layout.advance.width` (the
ligature's ADVANCE box), not its outline bounding box — this made the
"union bounds within 2%" accept criterion fail by ~3.2pt on a real لا
fixture (advance boxes and ink bounds routinely differ by several points
due to side bearings). Switching to outline-bbox-based fitting (this ADR)
fixed it — `LigatureDecomposerTests.fidelityFitAlignsWithinTwoPercentWhenWithinClamp`
now passes with the assembled outline width within 0.02% of the original
(essentially exact, since the edge-alignment is algebraic, not
approximated).

**Real-font finding, logged per packet §10's "store the actual
ligature-fidelity percentage achieved."** On **Geeza Pro at 36pt**, لا's
own fused-ligature outline (`boundingBoxOfPath.width ≈ 15.74pt`) is
substantially NARROWER than the two standalone lam+alef glyphs placed
side by side (`≈21.84pt`), giving `naturalScaleFactor ≈ 0.72` —
**outside** the `[0.85, 1.15]` clamp. This is the D-221 pre-flight
clamp-refusal path firing CORRECTLY (not a defect): decomposing لا on
Geeza Pro at this size automatically falls back to default-forms mode,
with `fidelityAutoRefused = true` on the result.
`LigatureDecomposerTests.decomposeLaaConstituentsAndClampBehaviorOnRealFont`
locks this exact measured finding in (so a future font/size/toolchain
change that shifts the ratio gets caught, not silently masked); a
SEPARATE synthetic fixture
(`fidelityFitAlignsWithinTwoPercentWhenWithinClamp`) directly exercises
the successful within-clamp fit path since the real لا/Geeza-Pro
combination doesn't happen to. The WS-09 fixture re-run (Amiri/Noto Naskh)
is the natural place to re-measure whether a "real" font's لا lands inside
the clamp — flagged as a follow-up for whoever runs that re-run.

### WS04-A3: follow-base implemented as command expansion over flat value tree

**Decision.** No per-move "sync marks" command exists. Because
`MKMarkNode.relativeOffset` is base-local and both `MKArrangedGeometry`
(`MKRender`, already shipped) and this module's own
`MarkAttachmentController.worldPosition(ofMark:in:)` compose `base.affine`
automatically at read time, an attached mark follows its base FOR FREE the
instant the base's `transform` changes via the ordinary
`ArrangeStyleEditor.setTransform` path — no additional command is
synthesized, dispatched, or discarded. Verified directly by
`MarkAttachmentControllerTests.movingBaseMovesTheMark`.

### WS04-A4: recompose blocked after constituent edits unless forced (no new MKModel storage)

**Decision.** D-221's widened dirty check ("compare FULL current node
state — transform AND style — against the state captured immediately
after decomposition") needs a baseline with no dedicated storage field
available in `MKModel` (outside this packet's fence). Resolved by
CONSTRUCTION rather than storage: every freshly-decomposed constituent is
initialized with `transform == .identity` (new placement lives entirely in
`layout.position`/`fidelityOffsets`) and `style == group.style` (the
ligature group's own top-level style field, a SIBLING of the `state` enum,
left untouched by decompose/recompose) — so the baseline for ANY
constituent, at ANY later moment, is simply `(.identity, group.style)`, a
direct comparison rather than a stored snapshot. Full reasoning in
`LigatureDecomposer.swift`'s file header. Verified by
`LigatureDecomposerTests.styleOnlyEditBlocksRecomposeUnlessForced_TARR_LIG_STYLE`
(the T-ARR-LIG-STYLE regression fixture, style-only edit with NO transform
change still trips the block) and
`.transformOnlyEditAlsoBlocksRecomposeUnlessForced`.

### WS04-A5 (new, not in the packet's original §10 list — added because it was a real bug the fidelity test caught): `ArrangeDeriver` needs a paint-style input

**Decision.** The packet's task-2 signature literally lists only
`(sourceText, MKTextStyle, ShapingCaptureResult, PathPlacementProviding)`
— no fill/stroke/shadow input. But `ArrangedDrawer` (`MKRender`, already
shipped) paints each arranged CHILD by its OWN independent `MKStyle`
(unlike `LiveTextDrawer`, which reads the single outer `MKNodeCore.style`)
— so without a paint-style input, every derived glyph/mark/ligature would
default to `MKStyle.default` (`fill: .none`), i.e. INVISIBLE, even for a
fully-painted source Live Text node. `ArrangeDeriver.derive` gained a
`paintStyle: MKStyle` parameter (defaulted, so existing call shapes still
compile), applied to every freshly-created child — same pattern
`LigatureDecomposer` already used for its own constituents. Caught
immediately by `DerivationFidelityTests` (100%-diff renders before the
fix); fixed same session.

Date: 2026-07-18. Trigger: coordinator convergence task following
`docs/impl-log/WS-02.md` session 3 (Item 2), which added the canonical

— arrange-engine contract" section specifically so this session could
close the gap flagged above (deviation 5, "Known gap"). Fences honored:
`MakhtootKit/Sources/MKArrange` + `MakhtootKit/Tests/MKArrangeTests` only
— no `MKPersistence`, `MKModel`, `Package.swift`, or app-dir edits (a
sibling agent was concurrently working `MKTextEngine`/`MKModel`; verified

## Root cause (confirmed, matches WS-02 session 3's diagnosis exactly)

`MKArrangedCompositionCommand` (this module's own `MKCommand` conformer,
`ArrangeCommands.swift`) could never be named by
`MKPersistence/Undo/MKCommandCoder.swift`'s closed switch — the dependency
edge runs `MKArrange → MKPersistence`, never the reverse. Every
composition-internal mutation this module's controllers build
(`JoinController.command`, `FormSelectorModel.command`,
`LigatureDecomposer.decomposeCommand`/`recomposeCommand`,
`MarkAttachmentController.detachCommand`/`reattachCommand`/`moveCommand`,
`ArrangeStyleEditor`'s four helpers) constructed this type, so
`CommandJournal.append` threw `unknownCommandType` for all of them —
silently swallowed by `MakhtootDocument.apply`'s `try?` per WS-02's own
report. In-memory undo/redo (`MKUndoStack`) was always correct; only a
crash before the next autosave flush could lose one of these edits — a
D-223/no-loss violation, same class of bug as WS-06's canvas commands
(WS-02 session 2) before those were canonicalized.

## Fix: adopt `MKReplaceNodesCommand`, retire `MKArrangedCompositionCommand`

Per `CONTRACTS.md`'s adoption row, option (a) (canonical primitives, no
registration API) — `MKArrangedCompositionCommand` is deleted outright
(not deprecated-in-place; nothing outside this module referenced it, and
keeping a dead duplicate type around would just be a second footgun for
the next controller author). Every former call site now goes through one
new, centralized helper:

```swift
// ArrangeCommands.swift
public enum ArrangeCommands {
    public static func replaceComposition(
        of ownerNode: MKArrangedTextNode, with newComposition: ArrangedComposition,
        label: String, coalescingKeySuffix: String? = nil
    ) -> any MKCommand {
        let updatedNode = MKArrangedTextNode(core: ownerNode.core, composition: newComposition, derivedFrom: ownerNode.derivedFrom)
        return MKReplaceNodesCommand(
            nodeID: ownerNode.core.id, newNode: .arranged(updatedNode), label: label, coalescingKeySuffix: coalescingKeySuffix)
    }
}
```

**The one real design decision this migration forced (not just a
mechanical rename).** `MKReplaceNodesCommand.apply` is an absolute-value
replace — it needs the FULL new `MKArrangedTextNode` (`core` +
`composition` + `derivedFrom`) computed at command-CONSTRUCTION time. The
retired type instead re-read the live owner node off the SCENE at
apply-time and only overwrote `composition`, so none of this module's
controller signatures previously carried the owner's `core`/`derivedFrom`
at all — only a bare `ownerNodeID: MKNodeID` plus the `composition` being
mutated. Every composition-command-builder's signature therefore changed
from `(..., ownerNodeID: MKNodeID, composition: ArrangedComposition, ...)`
to `(..., ownerNode: MKArrangedTextNode, ...)` (internally
`ownerNode.composition` replaces the old bare `composition` parameter,
which — every call site already confirmed — was always exactly
`ownerNode.composition` anyway, so this is a strict simplification, not an
added constraint on callers):

- `JoinController.command(applying:ownerNode:isBreak:)`
- `FormSelectorModel.command(selecting:ownerNode:)`
- `LigatureDecomposer.decomposeCommand(groupID:ownerNode:options:)` /
  `.recomposeCommand(groupID:ownerNode:force:)`
- `MarkAttachmentController.detachCommand(markID:ownerNode:)` /
  `.reattachCommand(markID:toBase:ownerNode:)` /
  `.moveCommand(markID:byDelta:ownerNode:gestureID:)`
- `ArrangeStyleEditor.setStyle`/`.setOpacity`/`.setTransform`/
  `.nudgeBaseline`/`.nudgePosition` (all five, same `ownerNode:` swap)

**Two semantic differences from the retired type, both already documented
in `CONTRACTS.md`'s adoption row and re-confirmed here against the actual
implementation:** (1) the replacement node is snapshotted at
command-construction time rather than re-read from the scene at apply
time — safe under journal replay because `CommandJournal`'s `baseRev`
chain pins the replay base to the exact scene the command was built
against (verified directly by this session's own journal round-trip
tests, not just asserted); (2) a missing target now throws
`MKPersistenceError.nodeNotFound` (from `MKReplaceNodesCommand.apply`)
rather than `MKArrangeError.sourceNodeNotArranged` — that error case is
kept in `ArrangeInvariants.swift`'s taxonomy (dormant, documented inline)
for any future explicit pre-check call site, but nothing in this module
throws it anymore; no test asserted on it before this session (confirmed
by grep), so nothing regressed.

`Undo/redo semantics are unchanged` — every `ArrangeCommandTests`/
`ArrangeStyleEditorTests`/`FormSelectorModelTests` assertion about
apply/inverse behavior passes with the same expected outcomes; only two
test files needed edits beyond a type name (`ArrangeStyleEditorTests.swift`,
`FormSelectorModelTests.swift` — both needed to construct an
`MKArrangedTextNode` up front and pass `ownerNode:` instead of
`ownerNodeID:`/`composition:`, since that's the exact information the new
canonical command needs at construction time that the old one didn't).
`JoinControllerTests`/`LigatureDecomposerTests`/`MarkAttachmentControllerTests`
needed ZERO edits — they only exercise the pure `breakJoin`/`restoreJoin`/
`decompose`/`recompose`/`detach`/`reattach`/`move` functions directly, not
the `...Command` builders this session's signatures touched.

## New test: journal round-trip (`Tests/MKArrangeTests/JournalRoundTripTests.swift`)

(`MKCommandCoder.encode`/`.decode`), without needing `CommandJournal`/

   the replayed revert step, AND the final replayed scene are all
   byte-identical (`MKScene: Equatable`) to their in-memory-only
   counterparts, and that derive→revert round-trips back to the original
   scene exactly.
2. `compositionInternalEditRoundTripsThroughMKCommandCoderReplay` —
   regression coverage for the ACTUAL bug fixed this session: builds an
   already-`.arranged` scene, applies `ArrangeStyleEditor.setStyle` (one
   representative composition-internal mutation — every other controller
   in this module funnels through the same `ArrangeCommands
   .replaceComposition` primitive, so this exercises the shared code path
