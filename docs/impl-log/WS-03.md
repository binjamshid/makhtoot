### WS03-A1: MKTextEngine early-spike request-type seam (local `MKTE`-prefixed stand-ins)

**Decision.** ARCHITECTURE.md §3/§4 specifies the eventual shaping-request
shape using `MKModel` types (`MKSourceText`, `MKTypography`,
`MKTextFrameSpec`, `MKFontRef`) that do not exist yet (P2 was in flight
concurrently). Rather than guess `MKModel`'s final schema or create a fake
dependency on a target that isn't ready, `MKTextEngine` ships **local**
stand-in types prefixed `MKTE` (`MKTESourceText`, `MKTETypography`,
`MKTEFrameSpec`, `MKTEShapingRequest` — `Sources/MKTextEngine/
ShapingRequestTypes.swift`). The one exception is `MKFontHandle`, reused
as-is from the real WS-01 `MKFontProviding` seam
(`MKFoundation/Stubs/MKFontProviding.swift`) — that **is** the production
seam per DEPENDENCY_GRAPH.md edge E-F1, not a placeholder, so reusing it
is correct rather than local-only.

**Rationale.** Distinct names make the eventual `MKModel` integration a
mechanical rename + field-mapping pass the compiler can drive (every call
site that needs updating fails to compile the moment the real types
replace the local ones), instead of a silent name collision (if I had
reused the final `MK` names) or a permanent, undocumented dependency on
throwaway types.

**Alternatives considered and rejected:**
- *Fork/guess `MKModel`'s schema now* — rejected: risks divergence from
  whatever P2 actually ships, and this packet's own text explicitly warns
  against "guessing the final shape" (see packet's SLICE SCOPE
  instruction: "define internal equivalents you will later adapt to
  MKModel types, and record that seam as an ADR").
- *Block P3 entirely on P2* — rejected: contradicts the explicit
  early-spike instruction and DEPENDENCY_GRAPH's soft P2→P3 edge ("P3 can
  begin against MKFoundation alone... finish P3 after P2 exits").

### WS03-A2: Cluster-map algorithm & non-monotonic run handling

**Decision.** `MKTEClusterMapBuilder` (`Sources/MKTextEngine/
ClusterMap.swift`) implements ARCHITECTURE §4.5 exactly: group glyphs by
`CTRunGetStringIndices` value *within each run*, sort distinct indices
ascending per run (this is what restores logical order under RTL
glyph-array reversal — the packet's own warning: "for an RTL run, glyph
order is visually LTR but string indices *descend*; sorting by string
index restores logical order"), then sort **all** raw clusters across runs
by UTF-16 start (handles cross-run bidi reordering, e.g. a Latin/digit run
appearing visually first) to produce the final `clusters` array in logical
order. Classification precedence: `.control` (all codepoints are
ZWJ/ZWNJ/bidi-control) → `.ligature` (>1 non-mark codepoint, 1 glyph) →
`.markOnly` (0 non-mark, ≥1 mark) → `.baseWithMarks` (≥1 non-mark, ≥1
mark) → `.simple`.

The "1 codepoint → N glyphs" rare case (packet task 6d) is **not** a
separate `Kind` — observed for real ("به" → base ب realizes as **2**
glyphs), it stays `.simple` with `glyphs.count > 1`, matching ARCHITECTURE
§4.5's own correctness caveat ("the table never assumes 1:1 anywhere").
`CTRunGetStatus(.nonMonotonic)` is captured verbatim on
`MKTEShapedRun.isNonMonotonic` but not asserted on in tests (font/OS
dependent — WS03-A4 tolerance policy).

**Verification method.** Before writing the algorithm, a standalone
CoreText probe program (`swiftc` command-line, not part of the package)
was compiled and run against every §6 fixture string using system SF
Arabic, dumping raw `CTRunGetGlyphs`/`CTRunGetStringIndices`/
`CTRunGetPositions`/`CTRunGetStatus`/`CTRunGetStringRange` per run. The
algorithm and its tests are grounded in that captured, real data — not
assumption. Full transcript below ("Session log" → step 3).

**Alternatives considered and rejected:**
- *Sort by glyph-array position instead of string-index value* — rejected:
  produces wrong cluster boundaries for every RTL run (confirmed by the
  probe: RTL run glyph arrays are visually-ordered, string indices are
  not monotonic in that order).
- *Add a distinct `.multiGlyph` Kind* — rejected in favor of matching
  ARCHITECTURE §4.5's locked `Kind` enum shape exactly (5 cases); the rare
  multi-glyph case is representable within `.simple` without a new case,
  and downstream consumers (WS-04+) will be coded against the ARCHITECTURE
  shape.

### WS03-A3: Mark classification table & Qur'anic subranges + real base-resolution behavior

**Decision.** `MKTEMarkClassifier` (`Sources/MKTextEngine/
MarkClassifier.swift`) implements D-105's explicit ranges (honorifics
0x0610–061A, harakat 0x064B–065F, superscript alef 0x0670, Qur'anic
annotations 0x06D6–06ED) checked **before** falling back to
`generalCategory ∈ {nonspacingMark, enclosingMark}`, with an explicit
exclusion set `{0x06DD, 0x06DE, 0x06E9}` for the three scalars inside the
Qur'anic annotation range that are **not** marks — verified via
`Unicode.Scalar.Properties.generalCategory` (0x06DD → `.format`; 0x06DE,
0x06E9 → `.otherSymbol`; see transcript below).

**Empirical finding (important — differs from a literal reading of the
packet's illustrative fixture text).** Against system SF Arabic, combining
marks (fatha/kasra/damma/tanwin) consistently get their **own**
`.markOnly` cluster distinct from their base's cluster — not fused into a
`.baseWithMarks` cluster with the base. The one observed exception is
**shadda**, which SF Arabic fuses into the same glyph as its base letter.
The packet's task 8 fixture prose ("شَدَّةٌ: shadda+damma-tanwin stack on
the dal — two marks, distinct offsets, both based on same glyph") reads
naturally as "same cluster"; real captured data shows the *base
resolution outcome* (both marks resolve to the dal) is correct, but the
*cluster structure* getting there is: `[ش][fatha][د+shadda-fused][fatha][ة][tanwin]`
— six clusters, not a single "base+two-marks" cluster. `MKTEMarkAttacher`
(`Sources/MKTextEngine/MarkAttachment.swift`) is written to resolve a
mark's base by walking **backward across cluster boundaries** (nearest
preceding cluster classified `.simple`/`.ligature`/`.baseWithMarks`), which
handles both the "own cluster" case (harakat) and the "fused" case
(shadda) correctly, rather than assuming same-cluster membership.

**Alternatives considered and rejected:**
- *Assume marks always share their base's cluster* (a literal reading of
  the packet fixture prose) — rejected after the probe showed this is
  false for the common case (harakat) against SF Arabic; would have
  produced a base-resolution algorithm that silently failed to attach the
  majority of marks in every realistic Arabic sentence.
- *Hardcode "شَدَّةٌ" to a specific glyph/cluster count* — rejected per the
  packet's own task 9 instruction ("document per-font expectations rather
  than hardcoding one glyph count"); the test asserts mark **count** (4)
  and **universal base resolution**, not cluster topology.

### WS03-A4: Golden-capture tolerance policy (zero hardcoded glyph ids)

**Decision.** Glyph ids and exact metrics vary per OS/font version
(WS-01-A5 already demonstrated a real macOS-vs-iOS-Simulator platform gap
in a *different* module — `Color` equality — establishing this is not a
hypothetical concern in this environment). `MKTextEngineTests` contains
**zero** hardcoded glyph ids. Every assertion is structural: codepoint/
glyph counts, cluster `kind`, totality/invertibility of the cluster map,
base-resolution *success* (not *which* base by id), relative-offset
**sign** (not magnitude), bidi level *consistency* (not a specific run
count where the fixture's own structure could vary).

**Perf-test finding.** The D-115 pre-gate single-line capture test
initially measured ~85 ms on the iOS Simulator destination (with
code-coverage instrumentation enabled) for the *first* call in a fresh
test process — this is one-time CoreText font-loading/cache cost, not
steady-state typing-echo latency (the thing D-115 actually budgets).
Adding a warm-up call before the timed measurement brought every
subsequent call under 2 ms, comfortably inside the 50 ms test threshold
(and the packet's own tighter "<5 ms" target). Documented on the test
itself (`ShapingEngineSmokeTests.swift`) so a future reader doesn't
"fix" the warm-up back out and reintroduce flakiness.

### WS03-A5: MKModel integration resolves the WS03-A1 seam; MKTextEngine gains an MKModel dependency edge (PROPOSED DEVIATION)

**Decision.** The `MKTE*` stand-ins are deleted. The engine consumes
MKModel types directly:
- `MKShapingRequest` = `{MKSourceText, MKTextStyle, MKTextFrameSpec}`
  (`ShapingRequest.swift`) — the packet task-1 signature realized with
  WS-02's real types, including per-range `MKStyleRun` overrides and the
  `.rightToLeftOverride` forced-direction attribute.
- Mark classification returns `MKModel.MKMarkClass`; mark offsets are
  `CGSize` (matching `MKMarkNode.relativeOffset`); joining analysis emits
  `MKModel.MKJoiningState` (the exact `MKGlyphNode.joining` type); glyph
  outlines are `MKModel.MKPathData` (1000/em, INV-13); `MKCluster.id` is
  `MKFoundation.MKClusterID` (durable UUID → `MKProvenance.clusterID`).
- Capture types renamed to the final ARCHITECTURE §4.2 names
  (`MKShapedRun`/`MKShapedLine`/`MKShapedParagraph`/`MKClusterMap`/
  `MKBidiMap`/`MKGlyphAddress`).

**Proposed deviation (flagged, not silent):** `Package.swift`'s
`MKTextEngine` target now depends on `MKModel`, whereas FOUNDATION §2's
table row lists only "MKFoundation, MKFonts (font handles)". Justification:
the WS-03 packet's own §3 upstream list ("WS-02 (`MKTextStyle`,
`MKFontRef`, `JoiningForm`, `MKBezierPathData`)"), PLAN P3's entry criteria
("P2 `MKModel` types available for provenance structs"), DEPENDENCY_GRAPH's
P2→P3 soft-edge rationale ("provenance structs finalize against MKModel
types late in P3"), and this session's explicit orchestrator instruction
("adapt ... to the real MKModel types") all require the import. No cycle
results (MKModel depends only on MKFoundation). If a future FOUNDATION
revision wants the table row amended, this is the evidence trail.

### WS03-A6: D-107 ZWJ harvest — the system SF font ignores a LEADING ZWJ; real Arabic fonts honor D-107 fully (per-font finding)

**Finding (probed empirically BEFORE implementing `FormResolver`).** In the
system SF font (`.SFNS` via `CTFontCreateUIFontForLanguage`), a *trailing*
ZWJ correctly forces initial form, but a *leading* U+200D does **not**
trigger final/medial joining — medial-context harvests return the initial
form, final-context the isolated form. In **Geeza Pro** and **Damascus**
(both bundled on macOS and iOS), D-107 works exactly as the decision
specifies: all four forms yield distinct glyph ids, and harvested-medial
equals natural-medial (Geeza Pro ح: g260/g261/g262/g912 for
iso/ini/med/fin; natural medial ح in «محمد» = g262 — exact match; same for
م g346). Probe transcripts in the session log below.

**Decision.** `MKFormResolver` implements D-107 verbatim and
font-agnostically (this is not a D-107 conflict — the technique is sound;
one specific font underimplements leading-ZWJ joining).
`FormResolverTests` run against Geeza Pro via a test-local
`NamedFontProvider: MKFontProviding` (production wiring untouched — the
protocol is the seam; a test conformer is exactly what it exists for).
**Consequences flagged:** (a) WS-04's form picker cannot deliver real
medial/final harvests for text set in the system-font stub — resolved when
WS-09 registers Amiri/Noto and re-runs this suite per font (stub S2 flip);
(b) T-TXT-5's full 11-letter form sweep belongs to that re-run.

**Related finding:** Core Text silently **drops** a
`kCTFontFeatureSettingsAttribute` setting the font doesn't support
(`dlig` on SF Arabic → `CTFontCopyAttribute` returns nil; `liga=0`
round-trips). Harmless behavior, but it means T-TXT-7's dlig
glyph-count-difference test also joins the WS-09 Amiri re-run; what ships
now: the feature-dictionary dump tests, the rlig-never-emitted guarantee,
and lam-alif-survives-`.off` (the load-bearing D-108 invariant).

### WS03-A7: service/cache/joining/kerning design decisions

1. **`MKShapingService`** is the ARCHITECTURE §4.4/§4.7 actor facade: LRU
   keyed on the full `MKShapingRequest` hash, cost = glyphCount × 64 B,
   32 MB default limit, `typingEcho` signpost (the reserved `MKSignpost`
   vocabulary) around single-line shaping, `invalidateCache()` as the
   WS-09/WS-07 hook. The pure struct `MKShapingEngine` remains for batch
   callers. (Packet task 13 names the facade "MKShapingEngine";
   ARCHITECTURE names the actor "MKShapingService" — both exist, the actor
   carries the ARCHITECTURE name, logged as a naming reconciliation.)
2. **Joining is analyzed once over the full paragraph text**, then
   partitioned per line by `sourceRange` — letters at a wrap boundary must
   not see an artificial text edge, and all indices stay absolute (the
   same space the cluster/bidi maps use).
3. **Kerning overrides** (`MKTextStyle.kerningOverrides`,
   clusterPairIndex-based) are realized by two-pass shaping: shape once
   without overrides to learn cluster boundaries, map pair index k to the
   k-th non-control cluster's UTF-16 range, re-shape with `.kern` range
   attributes. Dangling pair indices are ignored, not crashed on.
4. **Whole-line `==` across two captures of the same text is intentionally
   false** (`MKCluster.id` mints fresh UUIDs per capture — provenance keys
   are unique per derivation). Geometry equality is asserted on
   `runs` + `typographicBounds`. Test-design note for downstream suites.
