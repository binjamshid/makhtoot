## ADRs

### WS-01-A1: Project/package layout per D-100/D-101

**Decision.** One `Makhtoot.xcodeproj` app target (`Makhtoot`) + one local
SPM package `MakhtootKit` at `MakhtootKit/`, referenced from the app
project via `XCLocalSwiftPackageReference` (relativePath `MakhtootKit`).
`MakhtootKit/Package.swift` declares all 16 FOUNDATION §2 module targets
as library products with the exact dependency edges from FOUNDATION §2 /
FILE_MAP §4.2–4.3; the app target links all 16 products (via
`XCSwiftPackageProductDependency` entries in the Frameworks build phase),
even though only `MKDesignSystem` has real call sites in this packet — so
WS-02..WS-15 agents can `import` any module immediately without touching
`project.pbxproj`.

**`project.pbxproj` was hand-authored** (objectVersion 56, classic
`PBXGroup`/`PBXFileReference`/`PBXBuildFile` structure, not the newer
`PBXFileSystemSynchronizedRootGroup` folder-sync format) via a small
Python generator script (not committed — scratch tooling only) that
assigns UUIDs and emits the plist-format text directly, satisfying "the
Xcode project file must be authored directly (no xcodegen/tuist)."
Chosen over the newer synchronized-group format because the classic
format's failure modes are well-documented and `plutil -lint` catches
plist syntax errors immediately, which mattered a great deal for
iterating on a hand-written project file with no interactive Xcode
session to fall back on.

**Alternatives considered and rejected:**
- *Single mega-target* (all engine code + UI in the app target, no local
  package) — rejected: D-101 explicitly mandates the package split, and a
  mega-target defeats the whole point of §2's dependency-edge enforcement
  (illegal cross-module imports would compile silently instead of failing
  the build).
- *Per-feature `.xcodeproj`* (e.g. a separate project per workstream,
  combined via a workspace) — rejected: D-101 says one app target + one
  local package; per-feature projects would multiply hand-authored
  `project.pbxproj` files (16×) instead of one, hugely increasing the
  surface for exactly the kind of hand-authoring error this packet is
  already fighting, with no corresponding benefit (SPM target-dependency
  edges already give the enforcement a multi-project split would exist to
  provide).
- *XcodeGen/Tuist-generated project* — rejected outright per D-101 (no
  such tooling in this repo) and the packet's own instruction.

### WS-01-A2: Cross-workstream stub contracts (entitlement/font/document)

**Decision.** Three protocol seams live in `MKFoundation` so WS-03..WS-08
can build and test without waiting on WS-02/WS-09/WS-10:
`MKEntitlementProviding` (+ `StubEntitlementResolver`, always
`.lifetime`), `MKFontProviding` (+ `SystemFontStubProvider`, system SF
Arabic via `CTFontCreateUIFontForLanguage`), `MKDocumentStoring` (+
`InMemoryDocumentStore`, actor-isolated, no persistence). Full mapping —
stub type, consumer, real implementation, owning packet — is in
`MakhtootKit/CONTRACTS.md`.

**Alternatives considered and rejected:**
- *Concrete stub types with no protocol* (e.g. downstream code imports
  `StubEntitlementResolver` directly) — rejected: this is exactly the
  "always-premium stub becomes accidentally the production dependency"
  failure mode; forcing a protocol means WS-10's swap-in in
  `AppEnvironment.swift` (owned by WS-13) requires zero call-site changes
  anywhere else.
- *Stubs owned by each consuming workstream instead of centrally in
  `MKFoundation`* — rejected: would create 3+ divergent ad hoc "fake
  entitlement" implementations across WS-03..WS-08 with no shared
  precedence-ordering guarantee (D-113), instead of one audited
  implementation every consumer shares.

### WS-01-A3: `MKTransform2D` composition bug found and fixed during
this packet (not a pre-existing decision — logged because it changes how
downstream workstreams should trust `concatenating`/`inverted`)

**Finding.** The first implementation of `MKTransform2D.affineTransform`
built the matrix by chaining
`CGAffineTransform.identity.translatedBy(position).rotated(rotation).scaledBy(scale)`.
This chaining composes in the *opposite* order from what
`init(decomposing:)` assumes when reading `a,b,c,d,tx,ty` back out
(translate-then-rotate-then-scale vs. the intended
scale-then-rotate-then-translate), so `concatenating`/`inverted` silently
produced wrong matrices for any transform with a non-identity
position **and** rotation **and** scale together — caught by
`invertedTransformMapsAPointBackToItself`
(`MakhtootKit/Tests/MKFoundationTests/TransformMathTests.swift`), which
failed by ~10–12pt on a 7×7pt test point before the fix. Fixed by building
the `CGAffineTransform` directly from the closed-form
`a = sx·cosθ, b = sx·sinθ, c = -sy·sinθ, d = sy·cosθ` formula, which is
the exact algebraic inverse of `init(decomposing:)`.

**Residual, documented limitation (not a bug):** when a transform's scale
is *non-uniform* (`scale.width != scale.height`) **and** its rotation is
non-zero, the true matrix inverse/composition generally requires shear to
represent exactly, and `MKTransform2D` has no shear term (the packet's
struct shape is fixed to `{position, rotation, scale}`, no more). In that
combination, `concatenating`/`inverted` return the best shear-free
decomposition, not an exact one. This is inherent to any shear-free
decomposed-transform representation, not specific to this implementation.
It's exact whenever scale is uniform or rotation is zero, which is every
transform this scaffold or its immediate consumers produce today (no
per-axis-shear tool exists in v1). **WS-04 (arrange, nested glyph/mark
transforms) and WS-06 (canvas, nested group transforms) should be aware of
this** if a future feature introduces non-uniform-scaled rotated groups —
the escape hatch (documented on `concatenating(_:)`) is to compose
`.affineTransform` values directly instead of going through the decomposed
API when exactness under shear matters.

### WS-01-A4: `MKRTLUtilities.baseDirection` digit handling

**Finding.** The first implementation classified any Arabic-Indic digit
(`٠`–`٩`, U+0660–0669) as "strong RTL" for first-strong-character base
direction detection, because those codepoints fall inside the same
Unicode Arabic block (U+0600–06FF) used for script detection
(`isRTLCharacter`). Per the Unicode Bidirectional Algorithm, digits carry
bidi class AN/EN (a **weak** direction), so a string of digits alone
(`"١٢٣"`) must not decide base direction — caught by
`pureArabicIndicDigitStringHasNoStrongDirection`
(`MakhtootKit/Tests/MKFoundationTests/RTLUtilitiesTests.swift`). Fixed by
excluding the Arabic-Indic (U+0660–0669) and Extended Arabic-Indic
(U+06F0–06F9) digit ranges from the strong-direction scan in
`baseDirection(of:)` specifically; `isRTLCharacter` (general script
detection, used elsewhere e.g. for future search folding) is unchanged.

### WS-01-A5: Dynamic `Color` is not reliably `Equatable` on-device

**Finding.** `InkPaperTheme`'s colors are built via
`Color(uiColor: UIColor { traits in ... })` (a dynamic, light/dark-aware
color) so a single theme instance renders correctly in both color schemes
without the caller branching on `colorScheme`. A test asserting
`theme.selectionStroke == theme.accent` (D-126: "one deep accent" — no
second brand color for selection) passed under `swift test` (macOS host)
but **failed** under `xcodebuild test` on an iOS simulator destination:
two separately-constructed dynamic `Color` values that resolve to
identical RGBA in every trait collection compare unequal via `Color`'s
`Equatable` conformance on a real UIKit-backed platform (the macOS run
never exercised this because `Color(light:dark:)`'s `#if canImport(UIKit)`
branch doesn't compile there, so the assertion degenerated to comparing
the same `light` value with itself). Fixed the test (not the
implementation — the implementation is correct) to resolve both colors to
concrete RGBA via `UIColor.resolvedColor(with:)` under both
`UIUserInterfaceStyle.light`/`.dark` and compare components, rather than
relying on `Color ==`. **Any future test asserting equality of two
`MKTheme` dynamic colors on-device should use this pattern, not `==`.**
This is a real platform gap worth remembering — it is exactly why this
packet ran `xcodebuild test` against an iOS destination in addition to
`swift test`, and why that extra step is worth keeping in every
downstream workstream's habits, not just WS-01's.

   FILE_MAP §1 sketches this as a "package aggregate scheme (build+test

## Known gap: `Makhtoot` app scheme's `TestAction` is empty

`Makhtoot.xcodeproj/xcshareddata/xcschemes/Makhtoot.xcscheme` builds and
launches the app correctly (`BuildAction`/`LaunchAction`/`ProfileAction`
all verified working), but its `TestAction` has an empty `<Testables>`
list rather than wiring in `MKFoundationTests`/`MKDesignSystemTests` as
WS-01 packet §5 task 20 literally asks ("wired into scheme Makhtoot").

**What was tried** (all failed with `xcodebuild: error: ... There are no
test bundles available to test.` even though the app itself builds and
links all 16 package products correctly from the same project):
- `BlueprintIdentifier = "MKFoundationTests"`, `ReferencedContainer =
  "container:MakhtootKit"` — the documented convention per XcodeGen's
  `SchemeGenerator.swift` (`getBuildableTestableReference`), a
  battle-tested reference implementation.
- Same, with the package container lowercased (`container:makhtootkit`).
- Same, with `BuildableName` suffixed `.xctest` (the convention for
  native-target XCTest bundles).
- Same, with `ReferencedContainer = "container:MakhtootKit/Package.swift"`
  (pointing at the manifest file directly).
- Same, with `BlueprintIdentifier` namespaced `"MakhtootKit::MKFoundationTests"`.
- Adding the standard `project.xcworkspace/contents.xcworkspacedata`
  implicit-workspace file (normally auto-generated by Xcode on first
  open) in case scheme resolution depends on workspace-level SwiftPM
  state — no change.
- Listing the test targets in the scheme's `BuildActionEntries` in
  addition to `TestAction`'s `Testables`, and with them removed (minimal
  form) — no change either way.

**What works, verified green:** `xcodebuild -scheme MakhtootKit-Package
-destination 'platform=iOS Simulator,id=<UUID>' test`, run from
`MakhtootKit/` — this is the scheme Xcode/SwiftPM synthesizes
automatically whenever `xcodebuild` targets a `Package.swift` directly
(confirmed via `xcodebuild -list` inside `MakhtootKit/`, which lists
`MakhtootKit-Package` alongside the per-library-product schemes). Both
`MKFoundationTests` (29 tests / 6 suites) and `MKDesignSystemTests` (6
tests / 1 suite) run and pass through it — see verification evidence
below. `docs/BUILD.md` documents this as the canonical test invocation.

**Best hypothesis, unconfirmed:** wiring a *local SPM package's test
target* into a *different project's* scheme (cross-container reference)
may need Xcode's interactive package-graph resolution session (opening
the project once in the IDE, or using its scheme editor UI) to write a
container/blueprint identifier format this environment could not
discover by pattern-matching documented conventions alone — as opposed to
xcodebuild's fully-automatic, self-contained resolution when the package
IS the thing being built directly (no cross-container reference needed).
This environment has no interactive Xcode session available. **Flagged
for whichever future workstream/agent has interactive Xcode access**: open
`Makhtoot.xcodeproj`, select the `Makhtoot` scheme ▸ Edit Scheme ▸ Test,
check `MKFoundationTests`/`MKDesignSystemTests`, save (as a *shared*
scheme), and replace the empty `<TestAction>` in
`Makhtoot.xcscheme` with what Xcode writes. Non-blocking: `swift test`
and `xcodebuild test -scheme MakhtootKit-Package` both already give 100%
equivalent coverage of the same two test targets.
