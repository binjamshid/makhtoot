### Spike A — `CGContext(data:...space:<CMYK>...)` bitmap-context creation on iOS

**VERDICT: supported, but ONLY with `CGImageAlphaInfo.none`.**

`.premultipliedLast` (the RGBA-reflex choice) and `.alphaOnly` both return
`nil` — not a crash, a clean allocation failure. 8-bit and 16-bit-per-
component both work with `.none`. An ICC-based CMYK `CGColorSpace`
(`CGColorSpace(iccData:)`, the FD-03 bundled-profile shape) behaves
identically to the named Generic CMYK space.

**Actionable consequence for P10-completion's raster CMYK path**: a CMYK
bitmap context carries no alpha channel. Node opacity / transparency-layer
compositing (the `beginTransparencyLayer` calls in `MKSceneRenderer
.drawTopLevel`) MUST happen in an RGBA context first; only the FINAL
whole-image conversion into the CMYK context can happen, with no alpha
semantics inside that context. This was not previously specified anywhere
in ARCHITECTURE §15.3/§16.4.

### Spike B — exact `CGPDFContext` OutputIntent aux-key name + value shape

**VERDICT (two parts):**

1. **The KEY SHAPE ARCHITECTURE §16.5 assumed is correct**: the singular
   `kCGPDFContextOutputIntent` key with a single `CFDictionary` value is
   accepted, produces a well-formed `/OutputIntents` array-of-one in the
   output PDF's document catalog, and is `ios(14.0)`-available (confirmed
   in the iOS SDK header — `CGPDFContext.h` — well within the D-100 iOS 18
   floor). The plural `kCGPDFContextOutputIntents` (array-of-dicts) key
   also works and is likewise `ios(14.0)`-available.
2. **ARCHITECTURE §16.5's illustrative code is WRONG about
   `kCGPDFXDestinationOutputProfile`'s value type.** The SDK header
   (`CGPDFContext.h`) documents it must be "an ICC-based `CGColorSpaceRef`"
   — NOT a `CGDataProvider` wrapping raw ICC bytes, which is what
   ARCHITECTURE §16.5's sample code passes. This was verified empirically,
   not just read off the header comment: passing a `CGDataProvider`
   **silently succeeds at context-construction time** but produces a PDF
   whose `/OutputIntents` dictionary is missing `/DestOutputProfile`
   entirely — the ICC profile stream never gets embedded. A PDF/X claim
   built this way would be **provably false** (no embedded profile,
   despite claiming `GTS_PDFX`). Passing an ICC-based `CGColorSpace`
   instead produces a PDF with `/OutputIntents`, `/DestOutputProfile`,
   **and** an embedded `/ICCBased` stream — verified by reading the
   produced PDF's raw bytes back (not just checking `CGContext` didn't
   return `nil`).

Raw probe output + produced-PDF byte inspection (same iOS 26.5 simulator):

## Pattern-background contract recommendation (WS-14 coordination)

`docs/impl-log/WS-14.md` (WS14-A1) documents that pattern backgrounds do
**NOT** land as a `.background` node with pattern fill — `MKBackgroundContent`
has exactly `.solid`/`.image`. `MKPatternInstantiator.placeBackground`
instead realizes a pattern as a `.group` of individually-inlined
`.shape(.path(...))` nodes: ordinary vector shape content, drawn by the
already-shipped renderer with zero `MKRender` special-casing.

**Assessment against this session's export contract**: for the RASTER
formats this session ships (JPEG/PNG opaque/alpha), the impact is **exactly
zero** — a pattern-background group is indistinguishable from any other
group-of-shapes to `MKSceneRenderer`/`MKSnapshotRenderer`/
`MKTiledRasterExporter`, all of which already draw arbitrary node trees
correctly. No test, no code path, no special case was needed to make
pattern-background scenes export correctly this session (verified
implicitly — `TestScenes`' group/shape fixtures exercise the identical
node kinds a pattern-tile group is made of).

**Recommendation: adapt the exporter (i.e., do nothing special — treat
pattern-tile groups as ordinary shape content), do NOT add a `.pattern`
background case to `MKModel`.** Reasoning:

1. **Zero cost today, for every format this session implements.** No
   `MKModel` schema change is needed to ship correct raster export of
   pattern backgrounds — it already works.
2. **The only format this would matter for is the (deferred) SVG writer's
   file-size efficiency.** Per §16.6's element-mapping table, a pattern
   tile group serializes today as N ordinary `<g>`/`<path>` elements
   (the "Shape" row already covers it) rather than one `<pattern>`+`<use>`
   construct — larger SVG files for pattern-heavy exports, NOT a
   correctness or editability defect (the WS-14-A1 ADR's own framing:
   "simpler than the packet's own framing, not a defect").
3. **Adding a `.pattern` case would be a THREE-module coordinated change**
   (`MKModel`'s `MKBackgroundContent`, `MKRender`'s `BackgroundDrawer` —
   which would need genuine NEW pattern-tiling draw code, arguably a
   second drawing path worth scrutinizing against D-118/INV-2's "single
   render path" invariant — and `MKExport`'s SVG writer) for a bounded,
   not-yet-measured file-size win, while every fenced session so far
   (including this one) has deliberately avoided speculative `MKModel`
   edits outside its own packet.
4. This recommendation is NOT a new judgment — it is the SAME conclusion
   WS-14 itself already recorded (`docs/impl-log/WS-14.md`'s cross-packet
   coordination note #2): "worth revisiting once a `MKExport` SVG
   `<pattern>` writer exists and profiling shows the flat-tile SVG file
   size matters for large canvases." This session's independent
   assessment (from the export side rather than the asset side) arrives at
   the identical answer: defer, profile first, don't guess.

## Run 3 fix (2026-07-18) — `TiledRasterExporterTests` cancellation "no temp files" flakiness

**Symptom**: `cancellationBeforeTilingStartsLeavesNoTempFiles` and
`cancellationMidTilingLeavesNoTempFiles` (`TiledRasterExporterTests.swift`)
both failed deterministically with `countAfter` one greater than
`countBefore` (e.g. `66 == 65`) — read at face value as "the tiled exporter
leaked one scratch temp file on cancellation."

**Root cause — NOT an exporter bug**: both tests measured "no leaked temp
files" by listing the whole SHARED system temp directory
(`FileManager.default.temporaryDirectory`) and counting entries matching
`hasPrefix("mk-export-")`. That prefix is not exclusive to
`MKMappedBitmapAssembly`'s scratch file
(`TiledRasterExporter.swift`'s `"mk-export-\(UUID().uuidString).tmp"`,
opened then `unlink()`'d immediately, before any tile work — see the file's
existing ADR comment). `ExportCoordinatorTests.tempDir()` (a sibling helper
in `ExportCoordinatorTests.swift`) creates one `mk-export-coordinator-
<uuid>` scratch DIRECTORY per test and — prior to this fix — never removed
it, so every `swift test` invocation left one more such directory behind in

### CMYK ground-truth verification — two findings while building the corpus

**Method**: littleCMS `transicc` 5.1 (`/opt/homebrew/bin/transicc`,
Homebrew `little-cms2`; confirmed present — `which transicc`). Argyll
`xicclu` checked, NOT found. Profile: Apple Generic CMYK, dumped via
`CGColorSpace(name: .genericCMYK).copyICCData()`. Ground truth: `echo "R
G B" | transicc -t1 -o<profile>.icc -n` (8-bit sRGB in, CMYK % out).
Corpus + exact commands are in `Tests/MKColorTests/CMYKConverterTests.swift`'s
header.

**Finding — pure black CMM divergence**: CoreGraphics' ColorSync CMM and
littleCMS disagree by ~1.21 percentage points on the C channel for sRGB
`(0,0,0)` (M/Y/K agree within ±0.5pp). Both parse the identical profile
bytes under the identical intent — the divergence is each engine's own
interpolation near the profile's black-point extreme. A documented, wider
(±1.3pp) tolerance is asserted for this ONE swatch/channel; every other
swatch/channel in the corpus passes the general ±1pp bound comfortably.

**Finding — Apple Generic CMYK has NO rendering-intent differentiation**:
task 3's out-of-gamut `#00FF00` discriminator (packet: "asserted to differ
... by MORE than tolerance") is UNSATISFIABLE under the only profile
available this session — perceptual and relative-colorimetric conversions
are numerically IDENTICAL, confirmed independently via CoreGraphics
(`CGColor.converted`) AND littleCMS (`transicc -t0` vs `-t1`). Byte-level
inspection of the profile's own tag table (`AppleGenericCMYK.icc`
extracted from `CGColorSpace(name:.genericCMYK).copyICCData()`) explains
why: `A2B0`/`A2B1`/`A2B2` (perceptual/relative-colorimetric/saturation)
all point at the EXACT SAME byte offset (1928) and size (21523 bytes) —
one shared LUT reused via ICC tag-table indirection, not independent
tables that happen to agree numerically. `CMYKConverterTests` asserts the
ACTUAL, verified behavior with a header explaining the finding;
`.relativeColorimetric` is still passed explicitly everywhere (correct
practice for when FD-03 lands a real profile).

```
python3 tag-table dump (AppleGenericCMYK.icc):
A2B0 offset= 1928 size= 21523
B2A0 offset= 23452 size= 21492
A2B1 offset= 1928 size= 21523   ← same offset/size as A2B0
A2B2 offset= 1928 size= 21523   ← same offset/size as A2B0
B2A1 offset= 23452 size= 21492  ← same offset/size as B2A0
B2A2 offset= 23452 size= 21492  ← same offset/size as B2A0
```

### Spike C — true per-element vector CMYK is unreachable within this
### packet's fence

**Probe**: constructed a CMYK-OutputIntent-carrying PDF context, set
`ctx.setRenderingIntent(.relativeColorimetric)` explicitly, then filled a
rect using an ORDINARY sRGB `CGColor` (exactly what `MKRender`'s
`ShapeDrawer`/`LiveTextDrawer`/`ArrangedDrawer`/`PathTextDrawer` all do via
`ctx.setFillColor(color.cgColor)`). Decompressed the produced PDF's
content stream:

```
q Q q /Cs1 cs 0.8 0.1 0.1 sc 10 10 50 50 re f
/Cs2 cs 0.1 0.9 0.9 0.05 sc /Gs1 gs 80 10 50 50 re f Q
```

`/Cs1` is a freshly-embedded sRGB ICCBased colorspace resource (3
components, unconverted) — CoreGraphics did NOT auto-convert the sRGB
`CGColor` into the context's "CMYK" space; it just tagged the fill
operator with the CGColor's OWN colorspace. `ctx.setRenderingIntent` had
zero observable effect on this. (`/Cs2`'s 4-component fill is the CONTROL
— an explicitly-CMYK `CGColor`, set via `setFillColorSpace`+
`setFillColor([4 components])`, which DOES come through correctly — proving
the context itself is fine; only the AUTOMATIC RGB→context-space
conversion doesn't happen.)

**Root cause**: a `CGContext(url:mediaBox:auxiliaryInfo:)` PDF context has
NO fixed "native colorspace" parameter at all (unlike a bitmap context's
`space:` argument) — every PDF paint operator's color is entirely
per-operator, driven by whatever `CGColorSpace` the active `CGColor`/
`setFillColorSpace` call carries at that instant. Achieving real
per-element CMYK requires the DRAWERS THEMSELVES to construct CMYK
`CGColor`s before calling `setFillColor`/`setStrokeColor` — a `MKRender`
source change, outside this packet's fence ("MKExport/MKColor sources...
no one else is editing").

**Decision**: `PDFPrintCMYKExporter` renders the WHOLE PAGE via the
existing tiled-raster pipeline (RGBA, correct opacity compositing per
Spike A), converts it ONCE via `CMYKConverter.convertWholeImage`
(`.relativeColorimetric`, explicit), and embeds that single CMYK image
with a real OutputIntent. Every export carries `FallbackReason
.cmykContentRasterized` — never silent. Full reasoning in
`PDFPrintCMYKExporter.swift`'s header, `CONTRACTS.md`'s new WS-08
P10-COMPLETION section, and the module READMEs.

### Spike D — `kCGPDFXOutputIntentSubtype` must be the literal
### `"GTS_PDFX"` or CoreGraphics silently drops the whole OutputIntent

Following D-226's own WS08-A3 ADR ("no PDF/X claim under fallback"), the
first implementation used a custom subtype string
(`"GTS_PDFX_fallback_not_a_claim"`) for the Apple Generic fallback.

### `NSData.decompressed(using: .zlib)` naming trap (test-infrastructure
### finding, not a production-code finding)

While building `PDFContentStreamProbe` (a test helper), calling
`NSData.decompressed(using: .zlib)` directly on a real PDF `/FlateDecode`
stream's raw bytes threw `NSCocoaErrorDomain Code=5377`. Root cause:
despite its name, `.zlib` in `NSData.CompressionAlgorithm` operates on RAW
DEFLATE (RFC 1951), NOT the zlib-wrapped container (RFC 1950: 2-byte
header + DEFLATE + 4-byte Adler-32) that PDF's `/FlateDecode` actually
uses. Fix: strip the 2-byte header + 4-byte trailer before decompressing.
Documented in `PDFVectorExporterTests.swift`'s `PDFContentStreamProbe` doc
comment so nobody "fixes" it back to the naive call.

### Fixture-authoring pitfall: `MKStroke.width`/`cornerRadius` are
### unit-square-relative, and stroke width isn't CTM-scale-compensated

While building the evidence QA scene, a rect with `cornerRadius: 16` and
`stroke width: 3` (both chosen as if they were absolute document points)
rendered as, respectively, a fully-swallowed stadium/ellipse shape and (far
more surprising) a SOLID BLACK CANVAS. Isolated via a bisection of
standalone probe scenes (background-only → clean; background + plain rect,
no stroke/rounding → clean; + rounding only → clean small rounded rect; +
STROKE only, `cornerRadius: 0` → **entire canvas solid black**). Root
cause: `MKShapeGeometry`'s unit-square convention (`ShapeDrawer.localPath`)
means a shape's geometry — including `cornerRadius` — is expressed in a
**-0.5...0.5 unit square**, with real size carried entirely by the node's
own transform `scale` (concatenated onto the CTM BEFORE the drawer runs).
`MKStylePainting.paint`'s `ctx.setLineWidth(CGFloat(stroke.width))` sets
the width in THAT SAME (heavily-scaled) user space — CoreGraphics scales
stroke width by the CTM like any other geometry, so a literal `width: 3`
under a 320×160 node scale becomes a stroke roughly 320×3=960pt wide,
enough to swallow the entire visible canvas in black. This is a real
`MKModel`/`MKRender` ergonomics/documentation gap (not something this
fence can fix) — `ShapeDrawer.swift`'s/`MKShapeGeometry`'s doc comments
explain the unit-square convention for FILL geometry but say nothing about
stroke width needing the same tiny-fractional-value treatment, and no
counter-scaling exists to make an intuitive "3pt border" produce an actual
3pt border regardless of the shape's size. Fixed in this session's own
fixtures (`TestScenes.mixedContentScene`, the evidence generator) by using
small fractional values (`cornerRadius: 0.06-0.08`, `stroke width: 0.01`).
**Flagged, not fixed** (outside this fence) — a `spawn_task` suggestion
was filed for whoever owns `MKModel`/`MKRender` next.
